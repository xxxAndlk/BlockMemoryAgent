# 全能 Agent 提示词改造设计（方案 A：通用核心 + 编码条件段）

- 日期：2026-08-26
- 状态：已实施（2026-08-26，含 soul.md 偏离说明，见 §1）
- 范围：仅配置文本（`config/soul.md`、`config/roles.yaml`），零代码改动
- 触发问题：2026-08-26 fruit 工作区 CEO 战略任务中，用户提示词内嵌"开发者自检协议"，
  MetaAgent 忽略该协议、按任务层直接作答（见 `d:/data/demo/fruit/logs/tui/2026-08-26.log`）。
  诊断结论：提示词通道端到端字节级原样，无截断/过滤，是模型在编码强倾斜语境下做了任务层解读。

## 目标

1. 系统提示词从"编码专用"转为"通用 Agent"：非编码任务（分析/策略/文案/调研/规划）有一等公民流程。
2. 用户消息中的显式执行协议（身份声明、输出格式、自检流程）被字面完整遵从，不被默认流程覆盖。
3. 编码任务行为零回退：现有与 dispatcher 代码强耦合的纪律原文保留。

  （meta/domain/fixed/dynamic）的 system 提示词后，用户指示直接修改。已将其通用化：
  第 2 条改为"代码类产出用 RunCommand 机器校验、非代码产出对照验收标准纸面核对"，
  第 3 条"关键文件路径"改为"关键产出与文件路径"。registry.go 的 DomainAgent 兜底提示词
  （`defaultDomainAgentSystemPrompt`）同步了 roles.yaml 的两处措辞（文件注释要求双写同步）。
  代码改动后需重新编译 tui.exe（已执行）。
- 不改 dispatcher 的 WriteSpec 强制校验（非编码任务也必须先 WriteSpec，新流程以此为前提）。
- 不改 `fixed_roles` 六个叶子助手、不改 `dynamic_templates`、不改任何 Go 代码。

## 方案取舍

- 方案 A（采纳）：通用核心 + 编码专用条件段。编码纪律整体保留、套上"仅编码任务生效"的语境；
  新增非编码段。语义安全、diff 可审。
- 方案 B（否决）：全文重写为通用编排者。篇幅小，但与 dispatcher 强耦合的现有纪律
  （contract 字段、verify_levels、baseline 拒收、占位桩、接力熔断）会被稀释，编码能力回退风险大。

## 具体变更

### 1. `config/soul.md` — 领域中立化（实际为最小改写，非全文替换）

实施时发现 soul.md 的 30 行中仅两处编码倾斜（"涉及代码与系统改动"措辞、八荣八耻编码对联、
文件读取纪律的"代码区段"措辞），其余（沟通风格/上下文预算/多 Agent 协同/输出格式/安全）
均为领域中立的有效内容。故偏离原设计的"全文替换"，改为最小改写：

- "在涉及代码与系统改动时" → "在涉及系统改动或多步骤任务时"。
- "文件读取纪律" → "查证与读取纪律"；"不读兄弟任务的代码区段" → "不读与当前任务无关的
  文件区段"；"共享契约中已提供的代码、签名与行号" → "共享契约中已提供的内容"。
  工具预算等机制性条目原文保留。
- 八荣八耻八条改写为领域中立版（接口→事实、业务→需求、架构→规范、重构→行事等），
  保留荣/耻对联格式与"共享记忆已提供视为已查证"的括注。

### 2. `config/roles.yaml` — meta_agent.system_prompt

现状结构：身份头（L38-40）→【派发铁律】→【交付验收】→【思考过程展示】→【目标管理】。

**变更 a：身份头之后、【派发铁律】之前，插入新段（原文如下）：**

```
【通用铁律】（一切任务形态适用）
- 用户显式协议优先：用户消息中带有明确的执行协议（身份声明、输出格式、自检/分析
  流程、框架约束等）时，按其字面完整执行；与本文默认流程冲突时以用户协议为准。
  禁止把用户协议降格为"背景信息"而忽略。
- 先判任务形态：编码工程类（产出代码/技术配置/工程文件）适用【派发铁律】全部条目；
  非编码类（分析/策略/文案/调研/规划/问答）适用【非编码任务】段，编码专属的机器
  校验条目对其不生效。
```

**变更 b：【派发铁律】之后插入新段（原文如下）：**

```
【非编码任务】（分析/策略/文案/调研/规划类适用）
- spec 钉死四件事：目标原文、产出形态（一份方案/一篇报告/一组文案）、验收要点
  （纸面可逐条核对的陈述句）、调研结论（如有）。WriteSpec 强制校验对非编码任务
  同样生效，禁止跳过 spec 直接派发。
- 验收以纸面对照为准：acceptance 写可纸面核对的条目，verify_levels 省略
  （visual/runtime/integration 是代码产物的机器校验，非编码任务不适用）。
- 轻任务直达同样生效：单一产出物只派 1 个 domain 一竿子到底，不拆叶子。
- 无【机器校验】段属正常：回传摘要与 spec acceptance 逐条纸面对照后收口，
  终答声明核对口径与未通过项。
```

**变更 c：【交付验收】段开头补一句（在"所有领域 Agent 回传后……"之前）：**

```
非编码任务没有【机器校验】段，整品验收以本节 B 纸面对照为准。
```

**不变更**：【派发铁律】全部条目原文保留（其中契约 6 项、verify_levels、baseline、
占位桩、happy-path、接力熔断、美术路线等均与 dispatcher 代码强耦合，且条文本身
已带"UI/游戏类任务必须…"等条件措辞，对非编码任务自然不触发）。

    7. 非编码任务（分析/方案/文案/调研）：按 spec 钉死的产出形态直接产出，

## 风险与缓解

- 提示词变长 ~40 行：meta 是最大 token 消耗点，增量 <5% 可接受；命中前缀缓存时近零成本。
- 硬编码【执行纪律】块原为编码措辞且无条件追加到所有角色：已通用化（见"非目标"变更记录），
  残留风险消除；第 1 条的工具纪律（SearchInFiles/ListDir/ReadFile）对所有角色均适用，保留原文。
- "任务形态判断"依赖模型自觉：判断错了代价低（非编码任务套用编码条目多为空转条件，
  编码任务误判为非编码则丢失机器校验——由【通用铁律】中"产出代码/工程文件"的明确判据缓解）。
