多Agent协同智能体记忆管理系统设计文档（v2.0）

1. 项目背景与设计目标

1.1 行业痛点
当前 LLM Agent 框架普遍面临两个根本性挑战：
- 长上下文遗忘：当对话历史、工具输出、系统提示词堆积超过模型有效注意力范围时，模型对中间信息的提取准确率急剧下降，出现“迷失在中间”现象。
- 技能/Skill 选择困难：随着 Skill 库膨胀，Agent 难以在海量功能中快速精准定位所需技能，且重复、无关技能大量占用上下文和推理资源。

1.2 本项目目标
从零构建一套记忆原生、上下文纯净、Skill 敏捷的多 Agent 协同系统，实现：
- 主 Agent 上下文在连续工作一周后依然不溢出、不遗忘关键信息。
- 多话题并行工作时上下文完全隔离，仅注入与当前任务相关的记忆片段。
- Agent 能根据任务需求，由 LLM 自主选择 Skill，避免僵硬的路由规则。
- 记忆体系遵循“短期-项目-长期”分层管理，支持智能压缩和按需检索。

2. 核心设计理念

2.1 一切选择由 LLM 驱动
从 Skill 选择、话题总结、记忆压缩到 Agent 路由，所有决策均通过 LLM 推理完成，禁止硬编码逻辑，仅提供结构化上下文作为决策依据。

2.2 上下文即稀缺资源
将 LLM 上下文窗口视为昂贵的“工作内存”，所有记忆组件均围绕“如何以最小 token 提供最大信息密度”设计。

2.3 多 Agent 分级编排
- 主 Agent：唯一面向用户，负责任务理解、Agent 编排、上下文分发和全局状态管理。
- 领域 Agent (DomainAgent)：由主 Agent 按需动态生成，承载特定领域知识和 Skill 库，拥有独立上下文。
- 子领域/功能 Agent：由 DomainAgent 按需生成，执行单一职责的原子任务。

3.1 主 Agent 职责
- 接收用户输入，理解意图，必要时生成任务计划。
- 根据任务领域动态创建或唤醒对应的 DomainAgent，并为其装配专属的 Skill 库。
- 维护全局任务看板和话题工作区，通过事件和邮箱机制实现 Agent 间异步协同。
- 负责将记忆库中的相关信息组装成“最小必要上下文”下发给子 Agent。
- 执行上下文窗口监控，当某个 DomainAgent 上下文接近阈值时触发智能压缩或切换。

3.2 DomainAgent
- 拥有独立的会话上下文、私有记忆快照和专属 Skill 库。
- 只能通过主 Agent 提供的 Skill 库检索并使用工具。
- 可进一步生成 SubdomainAgent 处理子任务，或直接调用单一功能 Agent。
- 完成任务后向主 Agent 提交结构化结果，并释放/压缩上下文。

4. 记忆模块详细设计（核心）

记忆模块是本项目的灵魂，直接决定上下文纯净度和长期运行稳定性。

4.1 三层记忆存储
记忆层         | 存储引擎                  | 内容                                       | 生命周期
短期记忆       | Agent 上下文 + Redis       | 当前任务最近 N 轮对话、实时状态、待处理事件 | 随任务结束或压缩而释放
项目记忆       | PostgreSQL 向量库 (pgvector) | 项目文档、Skill 定义、会话块摘要、模块输出历史 | 与项目同生命周期，跨会话持久化
长期记忆       | PostgreSQL 向量库 + 元数据索引 | 跨项目的用户偏好、通用知识、成功案例模板     | 永久存储，带访问频率衰减

4.2 会话块 (Conversation Chunks) 机制
借鉴 MemPalace 的空间记忆思想，将所有对话历史按话题边界分割为独立的“会话块”。每个会话块包含：
- 话题摘要（LLM 自动生成）
- 关键实体与决策
- 原始对话向量嵌入
- 时间戳与活跃度评分

上下文注入规则：当新问题到来时，主 Agent 会：
1. 计算新问题与所有会话块的语义相关性（向量相似度 + 实体重叠 + 时间衰减）。
2. 仅选取得分最高的 1~2 个会话块（及其必要的前置依赖块），将其摘要和关键对话注入当前上下文。
3. 完全无关的会话块不予加载，即使它们在时间上最近。

4.3 智能压缩与遗忘
- 每经过 X 轮对话（可配置，默认 10 轮），主 Agent 触发一次后台压缩：调用轻量快速模型（如 GPT-4o-mini）对当前会话块进行摘要重写，保留关键事实和未解决问题，丢弃冗余细节。
- 私有记忆快照在 Agent 被切出时也会自动压缩，只保留“最近 K 步完整细节 + 远期抽象摘要”。
- 长期记忆采用 LRU + 重要性评分双重淘汰，低分且长期未访问的条目自动归档或删除。

4.4 连续工作一周不遗忘的实现方案
- 上下文总量控制：主 Agent 自身的上下文永远只包含“全局任务看板摘要（200 token） + 当前活跃话题块摘要（300 token） + 最近 3 轮必要交互”，总量控制在 1000 token 以内。
- 记忆外部化：所有历史和知识都存放在 PostgreSQL 向量库和 Redis 中，按需检索。主 Agent 的上下文本质是一个“指针集合”，而非数据仓库。
- 领域上下文隔离：每个 DomainAgent 在完成任务后可被完全销毁或压缩为项目记忆中的一条摘要，其上下文空间立即回收。
- Watchdog 机制：主 Agent 实时监控自身和活跃子 Agent 的上下文长度，一旦超过安全阈值（如 3000 token），强制触发压缩或切换。

5. Skill 管理策略

5.1 Skill 库定义
每个 Skill 是一个结构化对象：
{
  "skill_id": "web_search",
  "description": "搜索互联网信息",
  "usage_example": "搜索最新AI新闻",
  "tool_ref": "mcp_firecrawl",
  "domain": "信息检索"
}

5.2 Skill 库组织
- Skill 按领域（Domain）分组，形成领域 Skill 库。
- 初始化 DomainAgent 时，主 Agent 通过 LLM 从总 Skill 池中筛选出与该领域强相关的技能集合，去重后下发。
- 严禁将全局 Skill 库完整暴露给子 Agent，减少选择噪音。

5.3 LLM 驱动的 Skill 选择
当 DomainAgent 需要执行任务时：
1. Agent 在上下文中看到其专属 Skill 列表（仅名称和一句话描述）。
2. LLM 推理出最合适的 Skill，输出调用指令。
3. 若 Skill 不存在，Agent 可向主 Agent 请求“扩展技能”，主 Agent 二次检索后补充，但同样只添加必要的一个/几个技能。

6. 提示词体系

6.1 系统提示词设计
遵循分层注入、按需拼接原则，包含：
- 基础层（固定）：角色定义、安全准则、输出格式要求。
- 任务层（动态）：当前任务目标、上下文摘要、可用工具列表。
- 示例层（按需）：根据任务类型从示例库中选取 Few-Shot 案例，采用 Chain-of-Thought 引导复杂推理。

6.2 人格提示词 (soul.md)
提供一个独立的人格配置文件，用户可自定义：
“你是一个专业、耐心、细致的软件工程师助手。你的沟通风格简洁明了，喜欢用分点的方式回答问题。在面对不确定情况时，你会主动询问澄清，而不是猜测。”
该文件在主 Agent 初始化时加载，并可通过指令动态修改。

6.3 Temperature 动态调节
- 需要确定性输出（代码生成、数学计算）：Temperature = 0.1~0.2
- 需要创意输出（文案撰写、头脑风暴）：Temperature = 0.7~0.9
- 路由决策、总结压缩：Temperature = 0（贪心解码）

主 Agent 会根据任务类型在上下文中指示 LLM 调用参数。

7. 多 Agent 协同与任务看板

7.1 任务看板
每个活跃话题维护一个结构化的看板，存储于 Redis/PostgreSQL 中：
话题 ID: T-001
目标: 完成用户登录模块重构
状态: IN_PROGRESS
子任务:
  - 接口设计 (已分配给 backend_designer) [完成]
  - 数据库迁移 (已分配给 db_agent) [进行中]
  - 前端适配 (等待中)
全局约束: 需兼容旧版 API

7.2 邮箱通知
Agent 之间不直接共享上下文，而是通过事件邮箱通信：
- Agent A 完成一个里程碑，向邮箱投递一条“事件消息”，包含结构化输出摘要。
- 主 Agent 定期检查邮箱，将相关事件转化为注入目标 Agent 的上下文片段。
- 这种异步解耦保证了上下文不会因为多 Agent 并发而交叉污染。

7.3 协程与高性能
基于 Go 语言的协程模型，主 Agent 可以并发激活多个 DomainAgent，每个 Agent 在自己的 goroutine 中运行，共享记忆存储的连接池。任务看板通过原子操作保证状态一致性。

8. 技术选型

- 核心框架：go-kratos 开源的 Blades (Go)，利用其 ModelProvider / Agent / Tool 抽象快速搭建 leaf 执行与工具调用闭环；上层编排为自研三层图状态机。
- 语言：Go，保障高并发性能和部署简便性。
- 向量存储：PostgreSQL + pgvector 插件，兼顾结构化记忆与向量检索。
- 高速缓存：Redis，存放短期记忆、任务看板、会话快照。
- 模型接入：通过 Blades 的模型抽象层，支持多模型切换（快速模型用于压缩、路由；强推理模型用于核心任务）。
- 外部参考项目：
  - MemPalace：借鉴其空间记忆与主动回忆机制。
  - gbrain / llm_wiki：RAG 知识注入实现参考。
  - firecrawl：Web 搜索工具后端。

9. 开发路径与里程碑

Phase 1：记忆核心 (MVP)
- 实现主 Agent + 单 DomainAgent 的上下文隔离。
- 搭建 PostgreSQL 向量库，实现会话块的自动分割、摘要生成和相关性检索。
- 验证连续 20 轮对话后上下文长度平稳不增长。

Phase 2：多 Agent 协同
- 实现任务看板和邮箱通知系统。
- 支持主 Agent 动态生成/销毁 DomainAgent。
- 完成 Skill 库的领域绑定和 LLM 驱动选择。

Phase 3：智能压缩与长期记忆
- 实现 X 轮自动压缩，优化长期记忆淘汰策略。
- 接入 soul.md 和动态提示词体系。
- 性能测试：模拟一周连续交互，监控记忆占用和任务完成率。

Phase 4：扩展与工具集成
- 集成 MCP 协议支持外部工具。
- 接入 RAG 知识注入和 Web Search。
- 开发管理仪表盘，可视化记忆状态。

10. 测试计划
- 根据/test/测试项目设计与接口文档.md进行测试项目设计与开发，效果达标时可标志agent完成。

11. 结语

本系统通过多 Agent 分级编排 + 会话块隔离 + 记忆外部化 + LLM 全权决策，从根本上解决了长上下文遗忘和 Skill 爆炸问题。它不是一个简单的 Agent 脚手架，而是一套让 AI 获得“清晰记忆”和“专注力”的认知架构。在 Go + Blades 的技术基座上，我们将构建出首个真正能连续工作一周仍头脑清醒的自主 Agent 系统。
