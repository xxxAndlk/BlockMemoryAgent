## 1. 项目起源：Claude Code 的三个痛点

### 1.1 痛点一：上下文膨胀后模型变笨

Claude 3.5 Sonnet 标称 200K 上下文，但实际操作中：
- 当对话历史、工具输出、文件读取结果堆积后，模型对中间信息的提取准确率下降
- 明明刚才讨论过的方案，模型突然"忘了"
- 中间穿插的文件审查结果，在后期被忽略
- 代码修改时遗漏之前已确认过的约束

**根本原因**：不是上下文窗口不够大，而是**长上下文中的有效注意力会衰减**。LLM 的注意力机制在处理超长序列时，中间信息会被"稀释"。

**BlockMemoryAgent 的解法**：不依赖 LLM 记住一切。所有历史写入外部记忆库，LLM 的上下文永远只包含"当前任务 + 按需召回的 relevant 记忆"。无论运行多久，输入 LLM 的上下文总量保持稳定。

### 1.2 痛点二：话题污染

修复 CSS 问题时，中途问了一句"帮我查一下这个函数的文档"，然后回到 CSS 修复。但 LLM 上下文里有 50% 是函数文档查询的内容，导致：
- 修复方案中莫名其妙出现了不相关的代码
- 模型把之前无关话题的假设带入当前任务
- 需要手动不断提示"回到 CSS 问题"

**根本原因**：LLM 的上下文是一个**线性序列**，所有对话历史按时间顺序排列，没有时间线/话题线的隔离。无关信息会被模型"看到"并影响决策。

**BlockMemoryAgent 的解法**：话题隔离。切换话题时，旧话题被归档（压缩为摘要 + 写入长期记忆），新话题只加载自己的上下文 + 从归档中按需召回相关片段。不同话题的记忆互不污染。

### 1.3 痛点三：跨会话遗忘

Claude Code 的对话超过几百轮后质量下降，被迫开启新对话。但新对话里：
- 项目结构、代码风格、编码规范都丢失了
- 需要重新描述技术栈、项目约定
- 之前的讨论结论、决策原因需要重新解释

**根本原因**：没有**跨会话记忆持久化**机制。每次对话都是独立的上下文，没有机制自动提取关键知识供后续使用。

**BlockMemoryAgent 的解法**：会话结束后自动提取关键知识（用户偏好、技术决策、项目约定、成功案例），写入长期记忆库。新对话启动时，自动检索并注入相关历史知识。项目约定、代码风格、你的偏好--这些只会在第一次讨论时建立，之后永久可用。

## 2. 设计目标

基于以上三个痛点，BlockMemoryAgent 的核心目标不是"让模型支持更长的上下文"，而是：

1. **上下文恒定**：无论运行多久、多少轮对话，输入 LLM 的上下文始终控制在配置阈值内（由 `config.yaml` 的 `agent.context_window` 控制），通过外部化记忆 + 按需召回实现
2. **话题隔离**：多话题并行工作时，每个话题的上下文完全独立，仅注入与当前任务相关的记忆片段
3. **跨会话记忆**：关键知识在会话结束后自动提取并持久化，新会话自动召回，不再从零开始
4. **长时稳定运行**：理论上可以连续运行一周、一个月，上下文不膨胀，模型不衰减

## 3. 核心设计理念

### 3.1 上下文是稀缺资源，必须外部化

即使 LLM 支持 200K 上下文，有效注意力也只有一小部分。BlockMemoryAgent 的设计哲学：**永远不要依赖 LLM 记住超过当前任务需要的内容**。

所有历史对话、工具输出、文件快照都写入外部记忆库。LLM 的上下文是一个"指针集合"，只装载当前任务所需的片段。外部化记忆让上下文总量与运行时长解耦--运行一周和运行一小时，输入 LLM 的内容形态一致。

### 3.2 记忆分层：热点保留，冷记忆降级

不是所有记忆都值得长期保留。记忆的价值会随时间衰减：

```
时间线 ->

[最近 1 小时]     [最近 1 天]       [最近 1 周]       [超过 1 周]
    │                 │                  │                 │
    ▼                 ▼                  ▼                 ▼
  完整细节         完整细节            摘要 + 向量         摘要 + 向量
  （Redis）        （PG 原始轨迹）      （PG 长期记忆）      （PG 长期记忆）
  随时访问          断点续传/审计       跨会话召回           跨会话召回
  不压缩            不压缩              热点: 完整细节       冷记忆: 删除
```

**热点记忆**：频繁访问的记忆（如"用户偏好用 Vue 3"、"项目编码规范"）标记为热点，保留完整细节更长时间。

**冷记忆**：长期不访问的记忆（如"某次临时调试的日志分析"）自动降级为摘要，超过期限后删除。

### 3.3 话题即边界

每个话题/任务应有独立的上下文边界：
- 拥有独立的上下文（自己的对话历史、工具输出、文件状态）
- 拥有独立的记忆检索空间（只检索与当前话题相关的记忆）
- 话题切换时，旧话题归档，新话题从零开始（但可以从归档中召回相关片段）

**为什么不是时间线隔离？**

如果按时间线隔离（最近的 N 轮对话），那么"刚才问了一句函数文档"会出现在当前 CSS 修复的上下文里。按话题隔离则不会。当前实现以 `SwitchTopic` 轻量话题隔离落地：切换话题时取消运行中节点、旧树快照压缩为摘要写入 sharedKV、新话题从空树开始（详见 `项目说明.md`）。

## 4. 上下文管理策略

### 4.1 TokenBudget（上下文预算分配）

> **状态**：分段预算组装当前**未接入 ReAct 热路径**，下表为未来接线目标。当前 ReAct 主循环以 `windowMessages` 硬上限 + 记忆 Pipeline 步频压缩控制上下文（见 `项目说明.md` §4）。

输入 LLM 的上下文总量由 `config.yaml` 的 `agent.context_window` 控制，按固定比例动态分配各段预算：

| 段 | 比例 | 内容 | 说明 |
|----|------|------|------|
| SystemRole | 6% | soul.md + 角色定义 | 固定开销 |
| TopicGlobal | 12% | 话题目标与状态 | 跨 Agent 共享摘要 |
| SharedState | 25% | 上游 Agent 公开输出 | 依赖传递 |
| GlobalKB | 12% | 全局知识库召回 | 向量检索结果 |
| PrivateMemory | 25% | 本 Agent 的记忆/快照 | 私有记忆 |
| TaskQuery | 6% | 当前任务描述 | 当前查询 |
| Reserve | 14% | 防止溢出 | 安全边距 |
| **总计** | **100%** | | |

**为什么分段动态分配？**
- 1M 上下文模型虽能吞长序列，但注意力会衰减。分段预算避免某一段（尤其是历史记忆）吞掉全部窗口，保证当前任务、角色定义、关键依赖始终有固定配额。
- 当模型或成本允许时，只需改 `context_window`，各段位同比放大，无需逐段调参。

### 4.2 记忆注入规则

当新问题到来时，系统：
1. 分析当前任务的关键词
2. 从短期记忆检索最近 N 轮对话
3. 从长期记忆检索相关摘要
4. 按相关性排序，取 top K（受预算限制）
5. 按"系统提示 -> 召回记忆 -> 当前任务 -> 最近对话"的顺序拼接

**为什么不是"最近时间优先"？**
- 时间优先会把刚才无关的函数文档查询带入 CSS 修复
- 相关优先只注入与当前任务相关的记忆，时间无关

### 4.3 上下文溢出防护

即使控制了预算，仍需要防护机制：
- **硬 Token 预算**：每用户目标/每角色设上限，触达即暂停会话等用户续跑（与轮数上限正交）
- **滑动窗口 + 步频压缩**：`windowMessages` 硬上限裁剪历史，记忆 Pipeline 按步频触发 `compressHistory` 压缩旧事件
- **工具入参截断**：assistant 消息入史的工具入参（如 WriteFile 全文）截断，避免单轮 input 暴涨耗尽预算

## 5. 提示词体系

### 5.1 系统提示词分层

```
[系统提示词]
├── 基础层（固定）：角色定义、安全准则、输出格式
├── 全局记忆层（动态）：跨话题的共享知识（编码规范、用户偏好）
├── 当前任务层（动态）：当前任务描述、执行计划、已完成步骤
├── 召回记忆层（动态）：从长期记忆召回的相关片段
└── 当前对话层（动态）：最近若干轮对话
```

### 5.2 人格提示词（soul.md）

独立的人格配置文件，用户可自定义：

```markdown
你是一个专业、耐心、细致的软件工程师助手。

沟通风格：
- 简洁明了，喜欢用分点的方式回答问题
- 不确定时主动询问澄清，而不是猜测
- 代码修改后自动运行验证，不假设正确

编码规范：
- 优先使用 TypeScript，不用 any
- 组件使用 Composition API，不用 Options API
- 错误处理必须捕获，不忽略异常
```

soul.md 在会话启动时加载，经 `PersonaInjector` 注入 ReAct 系统提示词最前（见 `项目说明.md`）。

### 5.3 Temperature 动态调节

| 场景 | Temperature | 理由 |
|------|-------------|------|
| 计划生成 | 0.2 | 结构化输出，需要确定性 |
| 代码生成 | 0.1 | 代码必须正确，不容随机性 |
| 摘要生成 | 0.3 | 需要准确提取关键信息 |
| 用户对话 | 0.7 | 自然语言，需要一定的灵活性 |

## 6. 测试计划

### 6.1 核心指标

| 指标 | 目标 | 测试方法 |
|------|------|----------|
| 上下文恒定 | 运行 100 轮后，LLM 输入 token 数波动 < 20% | 自动化测试，记录每轮输入 token |
| 记忆不丢 | 100 轮后，记忆表记录数 = 100 | 查询数据库，验证记录完整性 |
| 话题隔离 | 切换话题后，新话题上下文不包含旧话题内容 | 人工检查 LLM 输入中的记忆片段 |
| 跨会话记忆 | 新会话启动后，能召回上一会话的关键知识 | 验证 LLM 响应中包含相关记忆 |
| 复杂任务成功率 | 复杂任务（写代码/重构）成功率 > 80% | 人工评估生成代码的正确性 |

## 7. 结语

BlockMemoryAgent 的核心目标不是"做一个比 Claude Code 更好的编程助手"，而是**解决 Claude Code 做不到的事情：长时稳定运行、话题隔离、跨会话记忆**。

它假设：
- LLM 的上下文窗口再大，有效注意力也是有限的
- 多话题并行时，话题隔离比时间线隔离更重要
- 跨会话记忆是长期使用的刚需，不是可选功能

它不做：
- 模型训练（我们不训练模型，只编排模型）
- 代码补全（这是 IDE 插件的事，不是 Agent 的事）
- 实时协作（这是多人编辑器的事，不是 Agent 的事）

它做：
- 让你的 Agent 可以连续工作一周，上下文不膨胀，模型不衰减
- 让你在多个话题之间自由切换，互不污染
- 让你每次开启新对话，都能自动召回之前的项目约定和编码规范

**一句话：BlockMemoryAgent 是 Claude Code 的"记忆外挂"--你用 Claude Code 做快速编辑，用 BlockMemoryAgent 做需要持续多天、多话题并行、跨会话记忆保持的长任务。**
