## 1. 项目起源：Claude Code 的三个痛点

### 1.1 痛点一：上下文膨胀后模型变笨

Claude 3.5 Sonnet 标称 200K 上下文，但实际操作中：
- 当对话历史、工具输出、文件读取结果堆积后，模型对中间信息的提取准确率下降
- 明明刚才讨论过的方案，模型突然"忘了"
- 中间穿插的文件审查结果，在后期被忽略
- 代码修改时遗漏之前已确认过的约束

**根本原因**：不是上下文窗口不够大，而是**长上下文中的有效注意力会衰减**。LLM 的注意力机制在处理超长序列时，中间信息会被"稀释"。

**BlockMemoryAgent 的解法**：不依赖 LLM 记住一切。所有历史写入外部记忆库，LLM 的上下文永远只包含"当前任务 + 按需召回的 relevant 记忆"。无论运行多久，输入 LLM 的上下文总量保持稳定。

### 1.2 痛点二：话题污染

修复 CSS 问题时，中途问了一句"帮我查一下这个函数的文档"，然后回到 CSS 修复。但 LLM 上下文里有 50% 是函数文档查询的内容，导致：
- 修复方案中莫名其妙出现了不相关的代码
- 模型把之前无关话题的假设带入当前任务
- 需要手动不断提示"回到 CSS 问题"

**根本原因**：LLM 的上下文是一个**线性序列**，所有对话历史按时间顺序排列，没有时间线/话题线的隔离。无关信息会被模型"看到"并影响决策。

**BlockMemoryAgent 的解法**：会话块隔离（SessionBlock）。每个话题/任务拥有独立的上下文块。切换话题时，旧话题被归档（压缩为摘要 + 写入向量库），新话题只加载自己的上下文 + 从归档中按需召回相关片段。不同话题的记忆互不污染。

### 1.3 痛点三：跨会话遗忘

Claude Code 的对话超过几百轮后质量下降，被迫开启新对话。但新对话里：
- 项目结构、代码风格、编码规范都丢失了
- 需要重新描述技术栈、项目约定
- 之前的讨论结论、决策原因需要重新解释

**根本原因**：没有**跨会话记忆持久化**机制。每次对话都是独立的上下文，没有机制自动提取关键知识供后续使用。

**BlockMemoryAgent 的解法**：会话结束后自动提取关键知识（用户偏好、技术决策、项目约定、成功案例），写入长期记忆库。新对话启动时，自动检索并注入相关历史知识。项目约定、代码风格、你的偏好——这些只会在第一次讨论时建立，之后永久可用。

## 2. 设计目标

基于以上三个痛点，BlockMemoryAgent 的核心目标不是"让模型支持更长的上下文"，而是：

1. **上下文恒定**：无论运行多久、多少轮对话，输入 LLM 的上下文始终控制在配置阈值内（由 `config.yaml` 的 `agent.context_window` 控制，当前默认 65536 token），通过外部化记忆 + 分段预算 + 按需召回实现
2. **话题隔离**：多话题并行工作时，每个话题的上下文完全独立，仅注入与当前任务相关的记忆片段
3. **跨会话记忆**：关键知识在会话结束后自动提取并持久化，新会话自动召回，不再从零开始
4. **长时稳定运行**：理论上可以连续运行一周、一个月，上下文不膨胀，模型不衰减

## 3. 核心设计理念

### 3.1 上下文是稀缺资源，必须外部化

即使 LLM 支持 200K 上下文，有效注意力也只有一小部分。BlockMemoryAgent 的设计哲学：**永远不要依赖 LLM 记住超过当前任务需要的内容**。

所有历史对话、工具输出、文件快照都写入外部记忆库。LLM 的上下文是一个"指针集合"，
各段按 `agent.context_window` 的固定比例分配预算：
- 系统角色段（~6%）：soul.md + 角色定义
- 话题全局段（~12%）：话题目标与跨 Agent 共享摘要
- 共享状态段（~25%）：上游 Agent 公开输出
- 全局知识库段（~12%）：向量检索结果
- 私有记忆段（~25%）：本 Agent 的 Episode/快照
- 当前任务段（~6%）：当前任务描述
- 预留缓冲（~14%）：防止溢出

默认 64K 预算足以容纳多个文件片段、较长对话历史和丰富记忆；如需更大上下文，
只需调整 `agent.context_window`，各段同比放大，无需逐段调参。

### 3.2 记忆分层：热点保留，冷记忆降级

不是所有记忆都值得长期保留。记忆的价值会随时间衰减：

```
时间线 →

[最近 1 小时]     [最近 1 天]       [最近 1 周]       [超过 1 周]
    │                 │                  │                 │
    ▼                 ▼                  ▼                 ▼
  完整细节         完整细节            摘要 + 向量         摘要 + 向量
  （Redis）        （PG 原始轨迹）      （PG 长期记忆）      （PG 长期记忆）
  随时访问          断点续传/审计       跨会话召回           跨会话召回
  不压缩            不压缩              热点: 完整细节       冷记忆: 删除
```

**热点记忆**：频繁访问的记忆（如"用户偏好用 Vue 3"、"项目编码规范"）标记为热点，保留完整细节更长时间。

**冷记忆**：长期不访问的记忆（如"某次临时调试的日志分析"）自动降级为摘要，超过期限后删除。

### 3.3 会话块隔离：话题即边界

每个话题/任务是一个独立的会话块（SessionBlock）：
- 拥有独立的上下文（自己的对话历史、工具输出、文件状态）
- 拥有独立的记忆检索空间（只检索与当前话题相关的记忆）
- 话题切换时，旧话题归档，新话题从零开始（但可以从归档中召回相关片段）

**为什么不是时间线隔离？**

如果按时间线隔离（最近的 N 轮对话），那么"刚才问了一句函数文档"会出现在当前 CSS 修复的上下文里。按话题隔离则不会。

### 3.4 智能路由：不要为简单任务开 Agent

80% 的日常交互是简单任务：
- "你好" / "谢谢" → 直接回答，不走任何 Agent 循环
- "帮我查一下这个文件的内容" → 直接执行 ReadFile，不生成计划
- "帮我运行这个测试" → 直接执行 RunCommand，不生成计划

只有 20% 的复杂任务（"帮我重构这个模块"、"写一个新的功能"）才进入 Plan-Execute-Reflect 循环。

**规则优先，LLM 兜底**：
- 简单任务：规则匹配（零成本）→ 直接回答
- 工具调用：关键词匹配（零成本）→ 直接执行
- 复杂任务：LLM 判断（兜底）→ 进入 Agent 循环

## 4. 系统架构

### 4.1 架构总览

```
┌─────────────────────────────────────────────────────────────┐
│  Layer 1: Router（智能路由）                                  │
│  - 规则判断：简单任务 / 工具调用 / 复杂任务                    │
│  - 简单任务 → 直接回答（轻量模型，不进入 Agent 循环）           │
│  - 工具调用 → 直接执行（不生成计划，直接跑工具）                │
│  - 复杂任务 → 进入 Agent Core（Plan-Execute-Reflect）         │
├─────────────────────────────────────────────────────────────┤
│  Layer 2: Agent Core（核心执行层）                             │
│  - Plan: 生成结构化执行计划（1-5 步 JSON）                      │
│  - Execute: 执行当前步骤（LLM 调用或工具调用）                   │
│  - Observe: 收集执行结果（成功/失败/输出）                    │
│  - Reflect: 评估是否偏离，是否调整计划，是否继续/终止              │
│  - 最大 3-5 轮后强制终止，防止无限循环                         │
├─────────────────────────────────────────────────────────────┤
│  Layer 3: Memory & Tools（记忆与工具层）                      │
│  - 短期记忆：Redis 热缓存（当前会话最近 N 轮对话）              │
│  - 中期记忆：PostgreSQL 执行轨迹（保留 7 天，用于调试/审计）      │
│  - 长期记忆：pgvector + 摘要（跨会话知识，热点保留/冷记忆降级）    │
│  - 工具：本地沙箱工具 + MCP 协议对接外部工具生态                  │
└─────────────────────────────────────────────────────────────┘
```

### 4.2 Router 层详解

```go
type TaskType int

const (
    TaskDirectAnswer TaskType = iota  // 寒暄/自我介绍/简单事实
    TaskToolCall                       // 查文件/读代码/跑命令
    TaskComplex                        // 写代码/重构/多步分析
)

func ClassifyTask(input string, history []Message) TaskType {
    // 第一步：规则匹配（零成本，覆盖 80%）
    if isGreeting(input) || isSimpleFact(input) {
        return TaskDirectAnswer
    }
    if isToolPattern(input) { // "查一下" / "读文件" / "运行命令"
        return TaskToolCall
    }
    // 第二步：轻量模型 LLM 判断（覆盖剩余 20%）
    return llmClassify(input, history)
}
```

**为什么规则优先？**
- 零成本：不需要调用 LLM，延迟 < 1ms
- 覆盖率高：日常对话中 80% 是简单任务或工具调用
- 确定性：规则不会"判断错误"，LLM 有时会误判

**LLM 兜底的场景**：
- 输入模糊，无法规则判断（"帮我处理这个"）
- 需要结合历史上下文判断（"继续刚才的工作"）

### 4.3 Agent Core 详解

#### Plan-Execute-Reflect 循环

取代纯 ReAct 循环，引入结构化规划和每步反思：

```
Plan  → 生成结构化计划（JSON 格式，1-5 步）
  │
  ▼
Execute → 执行当前步骤（LLM 调用或工具调用）
  │
  ▼
Observe → 收集执行结果（成功/失败/输出）
  │
  ▼
Reflect → 评估是否偏离目标，是否调整计划
  │
  └─→ 继续下一步 / 调整计划 / 终止
```

**与 ReAct 的区别**：

| 维度 | ReAct | Plan-Execute-Reflect |
|------|-------|----------------------|
| 规划 | 走一步看一步，无全局规划 | 先生成结构化计划，再按步骤执行 |
| 反思 | 无，每步后直接下一步 | 每步后评估是否偏离，可调整计划 |
| 计划调整 | 无，只能终止 | 可中途修改剩余步骤 |
| 循环保护 | 12 轮硬上限 + 重复调用/空转检测提前退出，可配置 | 按结构化计划分步执行，每步可配置重试 |
| 适合场景 | 简单单步任务 | 复杂多步任务（重构、写项目） |

#### 计划格式（结构化 JSON）

```json
{
  "steps": [
    {"id": 1, "action": "ReadFile", "target": "styles.css", "purpose": "检查当前样式"},
    {"id": 2, "action": "ReadFile", "target": "header.css", "purpose": "检查头部样式"},
    {"id": 3, "action": "WriteFile", "target": "styles.css", "purpose": "修复 padding 值"},
    {"id": 4, "action": "RunCommand", "target": "npx stylelint styles.css", "purpose": "验证修复"}
  ]
}
```

LLM 在 Plan 阶段看到完整的 1-5 步计划，而不是 ReAct 的"当前步 + 下一步推测"。这避免了 ReAct 的局部最优陷阱。

#### 执行与反思

每步 Execute 后，Reflect 阶段评估：
1. 上一步的结果是否成功？
2. 是否偏离了原始目标？
3. 是否需要调整剩余步骤？
4. 是否已经完成所有目标？（提前终止）

如果 Reflect 决定调整计划，会重新生成剩余步骤的 JSON，然后继续 Execute。

### 4.4 记忆层详解

#### 三层记忆存储

| 记忆层 | 存储引擎 | 内容 | 生命周期 | 写入方式 | 容量 |
|--------|----------|------|----------|----------|------|
| 短期记忆 | Redis | 当前会话最近 N 轮对话 | TTL: 1 小时 | 每轮同步 | N 轮（可配置） |
| 中期记忆 | PostgreSQL | 执行轨迹（原始对话 + 工具输出） | 保留 7 天 | 每轮同步 | 无限制 |
| 长期记忆 | PostgreSQL + pgvector | 关键知识摘要 + 向量 | 热点保留/冷记忆降级 | 会话结束异步 | 受磁盘限制 |

#### 写入机制（关键改进）

现有系统的记忆写入通过回调触发（`memCallback.OnEnd`），导致链路断裂（TODO 明确记载"数据库里没有一条记录"）。

**改进为显式调用**：

```go
func (a *Agent) Run(ctx context.Context, input string) (*Result, error) {
    // 1. 检索相关记忆
    memories := a.memory.Search(ctx, input, 5)
    
    // 2. 执行 Plan-Execute-Reflect
    result := a.loop(ctx, input, memories)
    
    // 3. 同步写入中期记忆（执行轨迹）
    // 确保不丢数据，失败立即报错，可重试
    if err := a.memory.SaveTrace(ctx, result.Trace); err != nil {
        log.Printf("写入中期记忆失败: %v，将重试", err)
        // 重试逻辑...
    }
    
    // 4. 异步写入长期记忆（摘要）
    // 不阻塞用户响应，失败只记录日志
    go func() {
        if err := a.memory.SaveSummary(ctx, result.Summary); err != nil {
            log.Printf("写入长期记忆失败: %v", err)
        }
    }()
    
    return result, nil
}
```

**为什么显式写入优于回调？**
- 回调容易被遗漏：执行路径有分支时，某条分支可能没触发回调
- 回调难以调试：不知道是否被触发，也无法在失败时重试
- 显式写入：在 `return` 前的最后一行，100% 执行，失败可重试

#### 压缩机制（Episode 两级简化）

Episode（私有记忆的最小单元）的压缩从原设计的四级（Raw → Standard → Compact → Marker）
简化为两级，降低阈值调优复杂度。

**简化为两级**：

```
原始记录（执行轨迹）          摘要（关键知识）
     │                            │
     │  保留 7 天                  │  永久保存（热点）
     │  用于调试/审计              │  或降级后删除（冷记忆）
     │                            │
     ▼                            ▼
┌─────────────┐            ┌─────────────┐
│  PostgreSQL  │            │  PostgreSQL  │
│  traces 表   │            │  long_term   │
│  完整对话    │            │  摘要 + 向量  │
│  工具输出    │            │  热点: 完整   │
│  执行结果    │            │  冷记忆: 删除 │
└─────────────┘            └─────────────┘
     │                            │
     │  7 天后自动删除             │  30 天后冷记忆删除
     │                            │  热点记忆保留更久
     ▼                            ▼
   释放空间                    释放空间
```

**Episode 压缩规则（`memory/compress.go`）**：
- `Raw`：高重要性（≥ `compress_importance_threshold`，默认 0.7）且新鲜
  （< `compress_age_hours`，默认 24h）的 Episode 保留完整 `FullObservation`。
- `Standard`：其余 Episode 丢弃 `FullObservation`，仅保留 `ObservationSummary`、
  `Facts`、`Importance` 等元数据，供后续召回。

> **注意**：Episode 的"两级压缩"与系统架构的"四层编排"是不同维度，互不冲突：
> - 两级压缩：Episode 在存储上的生命周期分层（Raw/Standard）。
> - 四层编排：复杂任务的结果向上汇总路径
>   `Assistant → SubDomainAgent（可选）→ DomainAgent → MetaAgent`。
>   SubDomainAgent 仅在 `RouteFullFourLayer` 路径下、且检测到跨子领域边界时才启用；
>   80% 的简单任务通过 `direct_tool` / `direct_assistant` / `create_domain` 路径完成，不进入第四层。

**为什么两级足够？**
- 原始记录保留 7 天：足够调试、审计、断点续传
- 7 天后自动删除：释放空间，不需要渐进式压缩
- 摘要永久保存（热点）：关键知识跨会话可用
- 冷记忆降级后删除：低价值信息不长期占用空间

**热点 vs 冷记忆**：
- 热点：频繁访问的记忆（用户偏好、项目约定），标记为热点，保留完整细节更长时间（如 90 天）
- 冷记忆：长期不访问的记忆（临时调试日志），降级为摘要，超过 30 天删除

#### 检索机制

**前期（当前阶段）**：关键词匹配 + 时间衰减
- 用关键词匹配召回相关记忆（简单、可靠、无需 embedding 模型）
- 时间衰减：越近期的记忆优先级越高

**后期（真实 embedding 接入后）**：向量相似度 + 关键词过滤 + 时间衰减
- 用 text-embedding-3 或 bge-m3 生成真实向量
- pgvector 做 cosine 相似度检索
- 关键词过滤作为前置筛选，减少向量检索范围

**为什么前期用关键词匹配？**
- 不需要额外模型（节省成本）
- 对于编程场景，关键词匹配（如"Vue 3"、"CSS 修复"、"padding"）召回率足够高
- 向量检索后期接入，不影响核心架构

### 4.5 工具层

#### 本地工具（沙箱内）

| 工具 | 功能 | 安全限制 |
|------|------|----------|
| ReadFile | 读取文件内容 | 只能读取工作目录内文件 |
| WriteFile | 写入/修改文件 | 只能写入工作目录内文件 |
| ListDir | 列出目录内容 | 只能列出工作目录内目录 |
| RunCommand | 运行命令 | 沙箱隔离，限制危险命令 |
| SearchInFiles | 文件内搜索 | 正则匹配，只读 |

#### MCP 协议（外部工具）

通过 Model Context Protocol 对接外部工具生态：
- `filesystem` MCP Server：文件操作（替代本地工具）
- `github` MCP Server：Issue/PR 管理
- `browser` MCP Server：网页浏览、截图
- `database` MCP Server：SQL 查询
- `slack` MCP Server：消息通知

**MCP 的优势**：
- 不需要自己维护工具实现
- 工具描述和 Schema 由 MCP Server 自动生成
- 社区生态无限扩展，新增工具只需配置

## 5. 上下文管理策略

### 5.1 TokenBudget（上下文预算分配）

输入 LLM 的上下文总量由 `config.yaml` 的 `agent.context_window` 控制（默认 65536 token），`ContextAssembler` 按固定比例动态分配各段预算：

| 段 | 比例 | 默认 64k 预算 | 内容 | 说明 |
|----|------|---------------|------|------|
| SystemRole | 6% | ~3.9k | soul.md + 角色定义 | 固定开销 |
| TopicGlobal | 12% | ~7.9k | 话题目标与状态 | 跨 Agent 共享摘要 |
| SharedState | 25% | ~16.4k | 上游 Agent 公开输出 | 依赖传递 |
| GlobalKB | 12% | ~7.9k | 全局知识库召回 | 向量检索结果 |
| PrivateMemory | 25% | ~16.4k | 本 Agent 的 Episode/快照 | 私有记忆 |
| TaskQuery | 6% | ~3.9k | 当前任务描述 | 当前查询 |
| Reserve | 14% | ~9.2k | 防止溢出 | 安全边距 |
| **总计** | **100%** | **context_window** | | |

**为什么分段动态分配？**
- 1M 上下文模型虽能吞长序列，但注意力会衰减。分段预算避免某一段（尤其是历史记忆）吞掉全部窗口，保证当前任务、角色定义、关键依赖始终有固定配额。
- 当模型或成本允许时，只需改 `context_window`，各段位同比放大，无需逐段调参。
- 对于编程场景，64k 可以容纳多个文件片段、较长对话历史和丰富记忆；如需处理更大代码库，可继续调高 `context_window`。

**Watchdog 阈值**
- `soft = context_window × 50%`：建议触发上下文压缩。
- `hard = context_window × 80%`：必须切换/驱逐当前 Agent。

### 5.2 记忆注入规则

当新问题到来时，系统：
1. 分析当前任务的关键词
2. 从短期记忆检索最近 N 轮对话（ Redis，O(1) ）
3. 从长期记忆检索相关摘要（关键词匹配，后期用向量）
4. 按相关性排序，取 top K（受 TokenBudget 限制）
5. 按"系统提示 → 召回记忆 → 当前任务 → 最近对话"的顺序拼接

**为什么不是"最近时间优先"？**
- 时间优先会把刚才无关的函数文档查询带入 CSS 修复
- 相关优先只注入与当前任务相关的记忆，时间无关

### 5.3 上下文溢出防护

即使控制了预算，仍需要防护机制：
- **Watchdog**：每轮监控上下文 token 数，接近阈值时触发警告
- **强制截断**：如果某轮输出导致上下文超过阈值，自动截断最早的记忆片段
- **会话切换**：如果当前任务上下文确实需要超过阈值（如"分析整个代码库"），自动拆分为多个会话块，分步处理

## 6. 多话题并行与隔离

### 6.1 会话块（SessionBlock）

每个话题/任务是一个独立的 SessionBlock：

```go
type SessionBlock struct {
    ID          string              // 块 ID（如 "block_css_fix_001"）
    Topic       string              // 话题名称（如 "CSS 修复"）
    Goal        string              // 任务目标
    Status      string              // active / archived / completed
    Messages    []Message           // 对话历史（仅本话题）
    ToolOutputs []ToolOutput        // 工具输出（仅本话题）
    MemoryIDs   []string            // 关联的长期记忆 ID
    CreatedAt   time.Time
    UpdatedAt   time.Time
}
```

### 6.2 话题切换

当用户切换话题时：
1. 当前 SessionBlock 标记为 `archived`
2. 提取关键知识，生成摘要，写入长期记忆
3. 创建新的 SessionBlock，从零开始
4. 新 SessionBlock 可以从长期记忆召回相关片段（如"刚才 CSS 修复时提到的编码规范"）

**为什么不是"在一个上下文里处理所有话题"？**
- 避免话题污染（CSS 修复的上下文里不会出现函数文档查询的内容）
- 每个话题的上下文更小，更聚焦，模型更不容易"变笨"
- 长期记忆的召回可以跨话题（如"编码规范"在 CSS 修复和 JS 重构中都会被召回）

### 6.3 跨话题/跨块知识共享

某些知识是跨话题的（如项目编码规范、用户偏好、技术栈），不应该被隔离：
- 这些知识在提取摘要时标记为 `global: true`
- 所有 SessionBlock 都会自动召回 `global` 记忆
- 非全局记忆只在本话题内召回

**跨块实时同步（R7/R8 实现）**：
- `state.MetaMemory` 是会话级调度记忆，由 `collectBlockResult` 在块完成时汇总各块结果生成。
- 新块创建时通过 `mergeSessionMetaMemory` 自动继承当前 `state.MetaMemory`，避免后续块遗忘前置决策。
- `collectBlockResult` 更新 `state.MetaMemory` 后，调用 `syncMetaMemoryToActiveBlocks` 把最新记忆推送到所有活跃块。
- 块完成切换前，通过 `Mailbox` 向其他活跃块发送 `MsgInfo`，由 `applyMailboxToBlock` 在目标 Agent 启动时消费并注入块级 `MetaMemory`。
- 这套机制让并行的 DomainAgent/SubDomainAgent 既能保持各自上下文隔离，又能按需感知相关块的进展。

## 7. 提示词体系

### 7.1 系统提示词分层

```
[系统提示词]
├── 基础层（固定）：角色定义、安全准则、输出格式
├── 全局记忆层（动态）：跨话题的共享知识（编码规范、用户偏好）
├── 当前任务层（动态）：当前任务描述、执行计划、已完成步骤
├── 召回记忆层（动态）：从长期记忆召回的相关片段
└── 当前对话层（动态）：最近 3 轮对话
```

### 7.2 人格提示词（soul.md）

独立的人格配置文件，用户可自定义：

```markdown
你是一个专业、耐心、细致的软件工程师助手。

沟通风格：
- 简洁明了，喜欢用分点的方式回答问题
- 不确定时主动询问澄清，而不是猜测
- 代码修改后自动运行验证，不假设正确

编码规范：
- 优先使用 TypeScript，不用 any
- 组件使用 Composition API，不用 Options API
- 错误处理必须捕获，不忽略异常
```

soul.md 在会话启动时加载，作为全局记忆注入所有 SessionBlock。

### 7.3 Temperature 动态调节

| 场景 | Temperature | 理由 |
|------|-------------|------|
| 路由判断 | 0 | 确定性输出，避免误判 |
| 计划生成 | 0.2 | 结构化 JSON，需要确定性 |
| 代码生成 | 0.1 | 代码必须正确，不容随机性 |
| 摘要生成 | 0.3 | 需要准确提取关键信息 |
| 用户对话 | 0.7 | 自然语言，需要一定的灵活性 |

## 10. 测试计划

### 10.1 核心指标

| 指标 | 目标 | 测试方法 |
|------|------|----------|
| 上下文恒定 | 运行 100 轮后，LLM 输入 token 数波动 < 20% | 自动化测试，记录每轮输入 token |
| 记忆不丢 | 100 轮后，中期记忆表记录数 = 100 | 查询数据库，验证记录完整性 |
| 话题隔离 | 切换话题后，新话题上下文不包含旧话题内容 | 人工检查 LLM 输入中的记忆片段 |
| 跨会话记忆 | 新会话启动后，能召回上一会话的关键知识 | 验证 LLM 响应中包含相关记忆 |
| 简单任务延迟 | 简单任务响应时间 < 1s | 自动化测试，测量路由到响应的时间 |
| 复杂任务成功率 | 复杂任务（写代码/重构）成功率 > 80% | 人工评估生成代码的正确性 |

### 10.2 测试场景

1. **长时运行测试**：连续 100 轮对话，混合简单任务、工具调用、复杂任务，验证上下文是否膨胀
2. **话题切换测试**：在 CSS 修复、JS 重构、文档编写之间切换，验证话题隔离和跨话题知识共享
3. **跨会话测试**：关闭会话后重新开启，验证是否能召回之前的编码规范和用户偏好
4. **记忆写入测试**：强制中断（kill -9）后重启，验证中期记忆是否完整（断点续传）
5. **并发测试**：多个话题并行处理，验证 SessionBlock 隔离不互相污染

## 11. 结语

BlockMemoryAgent 的核心目标不是"做一个比 Claude Code 更好的编程助手"，而是**解决 Claude Code 做不到的事情：长时稳定运行、话题隔离、跨会话记忆**。

它假设：
- LLM 的上下文窗口再大，有效注意力也是有限的
- 多话题并行时，话题隔离比时间线隔离更重要
- 跨会话记忆是长期使用的刚需，不是可选功能

它不做：
- 模型训练（我们不训练模型，只编排模型）
- 代码补全（这是 IDE 插件的事，不是 Agent 的事）
- 实时协作（这是多人编辑器的事，不是 Agent 的事）

它做：
- 让你的 Agent 可以连续工作一周，上下文不膨胀，模型不衰减
- 让你在多个话题之间自由切换，互不污染
- 让你每次开启新对话，都能自动召回之前的项目约定和编码规范

**一句话：BlockMemoryAgent 是 Claude Code 的"记忆外挂"——你用 Claude Code 做快速编辑，用 BlockMemoryAgent 做需要持续多天、多话题并行、跨会话记忆保持的长任务。**
