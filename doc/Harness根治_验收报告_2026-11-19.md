## 1. 最终结论

**整体验收：不通过。禁止把当前工作区作为“根治已完成”版本发布或部署。**

结论由两类事实共同决定：

1. **完成度不满足**：WP3～WP6 的关键生产链路仍缺失，实施记录也已主动承认语义编辑未接入、验收证据未接入、上下文/预算治理大部分未做、桌面 worker 未打包。
2. **已实现部分也不满足正确性门槛**：新增的 6 个负面验收用例全部失败，覆盖受保护验收文件篡改、空写集生产写入、外部删除漂移、非法 accepted、合同安全段截断、证据类型错配。

现有测试通过只能证明若干纯函数与手工构造 fixture 的局部行为，不代表真实桌面会话已经形成“合同 → 定位 → 授权 → 最小编辑 → 真实验收 → 用户接受 → 学习”的闭环。

## 4. 阻塞缺陷与复现证据

### P0-1：Shell 可篡改受保护验收文件，事务却报告“无变更”

- `checkpoint.go:34-38` 默认排除整个 `.bma`。
- `action_pipeline.go:404-445` 只根据快照 diff 检查 `.bma/verification`；被排除的目录不会进入 MutationManifest。
- 新增 `TestHarnessAcceptanceReviewProtectedShellMutation` 实测：guard 内容由 `original` 变为 `tampered`，工具结果仍 `Success=true`，`Mutated=false`、`RolledBack=false`，before/after 快照 ID 相同。
- 直接违反 I-VERIFY-2、R-22 和“守护测试篡改为 0”的发布硬门。

**返修要求**：只排除 checkpoint 私有存储等必要内部目录；verification、合同事件和其他需保护资源必须进入独立、不可被工作区排除规则吞掉的观察通道。Shell 写保护必须有执行前硬约束与执行后独立审计，不能依赖一个看不见该目录的快照。

### P0-2：真实生产合同没有写范围，full-auto 又把 ask 自动升级为 allow

- `agent/logical_task.go:63-80` 构造 `TaskInput` 时没有资源解析，Targets/WriteSet 始终为空。
- `action_pipeline.go:267-278,395-399` 在 full-auto 下把 ask 视为批准。
- 新增 `TestHarnessAcceptanceReviewEmptyWriteSetFailsBeforeExecution` 实测：`Executed=true`，生产文件先被改，再事后回滚。
- 这不是“空 WriteSet 不能执行生产写入”的语义；外部副作用更无法靠文件回滚撤销。
- 在 suggest/auto-edit 下则会直接拒绝，意味着真实 enforce 编码任务无法正常完成。事故回放通过是因为测试手工给了 WriteSet，不代表生产入口能生成它。

**返修要求**：先完成资源/语义目标解析与合同完善，再允许 enforce；空或不完整合同必须执行前拒绝或进入明确审批。full-auto 只能减少重复确认，不能把“合同未知”解释为“获得任意写权限”。

### P0-3：验收证据只按 ID 匹配，不检查 Kind，可能错误 verified

- `acceptance_eval.go:94-119,147-174` 用规则 ID 取证据，但没有验证 `Evidence.Kind == AcceptanceRule.Kind`。
- 新增 `TestHarnessAcceptanceReviewEvidenceKindMustMatchRule` 实测：`rule-gap` 要求 DOM，传入同 ID 的 static/build 成功证据，结果为 `verified`。
- 这正是本改造要根治的“构建通过被当成目标验收通过”的同类错误。

**返修要求**：证据必须绑定 task ID、contract revision/hash、rule/invariant ID、证据 Kind、采集器、时间和产物引用；任何维度不匹配都不得满足规则。

### P0-4：failed/cancelled 可进入 accepted，正面学习门存在非法入口

- `logical_task.go:603-606` 明确允许 `failed/cancelled → accepted`。
- 新增 `TestHarnessAcceptanceReviewFailedTaskCannotBeAccepted` 实测状态变成 `accepted`。
- `evolver.go` 只检查 accepted，因此失败任务可能产生正面学习。
- 同时正常任务主要停留 active，`Accept` 只允许 verified/delivered-unverified；WP3 又没有生产状态迁移，导致正常接受链路也未闭环。

**返修要求**：仅允许 `verified/delivered-unverified → accepted`；failed/cancelled 必须经明确重新激活、重新执行与重新验收。补 API 级状态矩阵和 Evolver 负面对拍。

### P1-1：外部删除未被识别为 drift，会被回滚重新创建

- `checkpoint.go:485-499` 只在 `os.Lstat` 成功时检测漂移，目标已被外部删除时没有处理分支。
- 新增 `TestHarnessAcceptanceReviewExternalDeletionIsDrift` 实测：`Drifted=[]`，文件被重新创建，`Restored=[src/a.css]`。
- 纯权限漂移也主要依赖 hash 比较，存在覆盖外部元数据变化的风险。

**返修要求**：把“存在性、文件类型、symlink、内容 hash、mode”全部纳入 after 后当前状态比较；外部删除同样属于用户新修改，不得擅自恢复。

### P1-2：部分恢复/漂移仍可能被上层记录为完整 rolled_back

- `Restore` 通常把失败、blob 缺失和漂移放入报告并返回 nil error。
- `action_pipeline.go:353-375` 在 `restoreErr == nil` 时无条件写 `rolled_back` 并设置 `out.RolledBack=true`，即使 `Failed/Unavailable/Drifted` 非空。
- 这会造成磁盘仍残留越界修改，审计却声称事务已回滚。

**返修要求**：只有全部目标恢复到期望状态才是 RolledBack；任何失败、缺失、漂移或结果不确定都进入 ManualRecoveryRequired，并在 outcome/event/UI 一致呈现。

### P1-3：合同创建/读取失败在 enforce 下 fail-open

- `agent/logical_task.go:80-84` 对 `EnsureTask` 错误只记日志并返回 nil。
- `action_pipeline.go:408-417` 把 nil contract 当 legacy，设置 `allowAllFiles=true`。
- 新合同任务遇到存储或合同错误时会失去写范围保护，与“legacy 仅限真实旧会话”不同。

**返修要求**：显式区分 legacy fallback 与合同系统故障。enforce 下合同应存在但加载失败时，生产写入必须 fail-closed，并给出可恢复错误。

### P1-4：合同块截断会直接切断 WriteSet、Invariant 和纪律段

- `logical_task.go:865-877` 注释称“不截断不变量/写集段”，实现却直接保留前 N 个 rune。
- 新增 `TestHarnessAcceptanceReviewContractBlockKeepsSafetySections` 实测只剩 `inv-gap-`，完整不变量 ID 与纪律段消失。
- 默认预算 2200 runes，长合同可真实触发。

**返修要求**：按字段做结构化预算；Goal、WriteSet、ExcludedSet、active Invariants 与纪律不得被通用字符串截断。超限应压缩展示非安全字段、分页或拒绝生成不完整合同，而不是删掉安全约束。

### P1-5：审计与外部副作用语义仍不完整

- `action_pipeline.go:152-164` 事件写入是 best-effort，PG 失败仍继续执行。
- 网络、数据库、进程等副作用只有注释，普通成功路径未统一记录 `external_side_effects_not_reverted`。
- `CapabilitiesMutateFiles` 不把 network/database 当作需要相应资源授权与副作用审计的独立事务类别。
- 并发写同一资源、stale contract/base drift、blob 固定 `.tmp` 并发写入均没有合格专项证据。

**返修要求**：enforce 下权威审计失败不得静默成功；外部副作用单独授权与标记；补并发、重启、事件重放与恢复测试。

## 6. 桌面打包与灰度结论

1. `bma-app.ps1` 和安装脚本没有 `semantic-edit`/`semantic_worker_path` 相关载荷与注入；worker 不会随当前桌面包交付。
2. 默认配置为：`logical_task_mode=shadow`、`action_transaction_mode=off`、`semantic_edit_mode=off`、`contract_verification_mode=shadow`。
3. 因而默认安装不会改变原有工具写行为，也不会启用语义编辑或真实合同验收。这是可回退的灰度基础，不是根治功能已经生效。
4. 新三表已加入 schema 初始化和会话删除清单，但真实迁移、owner 隔离、重启恢复与删除均未做隔离真库验收。
5. 当前新增验收测试位于被 `.gitignore:37` 忽略的 `/test` 下；后续交付时必须显式纳入版本控制或移到约定可跟踪位置，避免测试证据没有随代码交付。
6. 当前实现全部仍在未提交工作区，且包含多文件既存改动；后续返修应拆分提交并保留明确变更边界。

## 7. 返修顺序与重新验收门

### 第一阶段：先修执行安全与真实性（必须最先完成）

1. 修复受保护目录观察/授权逃逸，新增 Shell、WriteFile、插件三类篡改用例。
2. 禁止 full-auto 把空/未知合同自动扩权；完成生产资源解析后再谈 enforce。
3. 区分 legacy 与合同系统错误，enforce 下合同绑定失败 fail-closed。
4. 修复外部删除/权限/类型/symlink 漂移；部分恢复一律 ManualRecoveryRequired，不得虚报 rolled_back。
5. 补审计写失败、外部副作用、并发与崩溃恢复场景。

### 第二阶段：修合同与验收状态机

1. 合同块结构化装配，安全字段永不丢失。
2. 证据绑定 Kind、revision/hash、task/target 与采集产物；杜绝 static 冒充 DOM。
3. 接受状态只允许 verified/delivered-unverified；补正常交付到 accepted 的生产迁移。
4. 接入重启恢复、事件重放、Refine 权限收口和撤销语义，避免只扩权不收口。

### 第三阶段：完成 WP3～WP6 生产接线

1. AcceptanceRunner 使用合同化 AcceptanceRequest，接真实构建、DOM、截图和集成证据。
2. PatchPlan 接入 EditFile/WriteFile，形成定位、唯一性、指纹、最小替换、复验闭环。
3. 完成 repo map、ToolCatalog/SearchTools、observation externalization 与 LogicalTask 硬预算。
4. 完成管理查询、Restore UI、合同/不变量/变更清单展示与 accepted 后学习闭环。
5. 桌面包携带 worker 和依赖，使用包内 Node 做离线冒烟。

### 重新验收最低条件

- 本报告 6 个负面用例全部通过，并补齐同类边界，不得删除或放宽 oracle。
- 后端、test 模块、worker 全量 deterministic 测试全绿。
