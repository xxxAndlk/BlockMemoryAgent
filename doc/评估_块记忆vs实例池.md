# 评估：实例池 vs 块记忆

**评估时间**：2026-07-24
**评估对象**：第七评估项中"可评估是否可以替换块记忆，块记忆过于抽象，可用性与传统感觉不明显。或者把块记忆与每个单独干净上下文的Agent进行集成融合等尝试。"
**评估方法**：基于当前代码实现（阶段 0-5 已落地）对比两种机制的设计目标、Token 成本、上下文污染、召回准确性、持久性、适用场景，给出替代/融合结论。

---

## 一、两机制现状（基于代码）

### 块记忆（block_memory）

**写入**（`dispatcher.go:saveBlockMemory`）：
- 触发：子 Agent 成功完成初始任务时（`runSubAgentOnce` 末尾）
- 内容：`目标:{trimmedGoal}\n角色:{roleID}\n结果:{result}` 三段式
- 截断：goal ≤ 200 rune，result ≤ 500 rune
- 落库：`PostgresStore.Embed` 生成向量 + `SaveKnowledge` 持久化到 `global_knowledge` 表
- Meta 标签：`goal`/`domain`/`sub_agent_id`/`source`
- 开关：`block_memory_write_enabled`（默认 true）

**召回**（`dispatcher.go:injectRecalledMemory`）：
- 触发：子 Agent 派发前，以原始任务文本做语义检索
- TopK：3 条
- 注入：命中记忆拼到任务前，格式 `【相关记忆】\n1. ...\n【当前任务】\n...`
- 未命中或召回失败：任务原样执行

**生命周期**：跨会话持久（Postgres），进程重启后仍在。

### 实例池（sub_agent_reuse）

**写入**（`dispatcher.go:servePooled`）：
- 触发：子 Agent 成功完成初始任务后，转入服务态
- 状态：`pooledAgent{agent, roleDef, parentID, lastUsed, cancel}` 存入 `pool sync.Map`
- 历史：保留初始任务的完整 `result.History`，后续 `RunWithHistory` 累积

**召回**（`servePooled` 服务循环）：
- 触发：`mailbox.WaitForMessage(subAgentID, idleTimeout)` 收到 send_message 询问
- 处理：`RunWithHistory(serveCtx, m.Body, history)` 以消息正文为新输入
- 回复：结果投递给 `ReplyTo`
- 历史裁剪：`trimPooledHistory` 上限 100 条（保留 system 前缀 + 最近对话）

**生命周期**：进程内常驻，闲置超时（默认 300s）回收，进程重启即失。

## 二、维度对比

| 维度 | 块记忆 | 实例池 |
|---|---|---|
| **持久性** | 跨会话/跨重启（Postgres） | 进程内，重启即失 |
| **记忆载体** | 向量 + 文本摘要（≤700 rune） | 完整对话历史（≤100 条） |
| **召回方式** | 语义检索 topK=3，自动注入 | 显式 send_message 询问 |
| **召回准确性** | 依赖 embedding 质量，可能召回无关记忆 | 精确（按 subAgentID 投递） |
| **Token 成本（单次召回）** | 低：3 条摘要 ≤ 2100 rune 注入 | 高：完整历史 ≤ 100 条重放 |
| **上下文污染风险** | 低：摘要已脱过程，只留结论 | 高：历史累积，长会话幻觉风险 |
| **跨 Agent 共享** | 是：任何子 Agent 派发时可召回 | 否：仅同一 subAgentID 的实例 |
| **主动权** | 系统自动注入（LLM 无感） | LLM 显式调用 send_message |
| **适用场景** | 跨任务经验复用（"上次类似任务怎么做的"） | 同任务多轮追问（"刚才那个代码再改改"） |
| **当前可用性** | 已闭环（写入+召回+开关） | 已闭环（服务态+闲置回收+开关） |

## 三、核心结论：不可替代，应融合

两机制解决**不同问题**，非替代关系：

### 块记忆强项（实例池无法覆盖）
1. **跨会话经验复用**：会话 A 的 code_assistant 完成任务，会话 B 派发类似任务时可召回 A 的结论。实例池进程内，重启即失，无法跨会话。
2. **低 Token 成本**：召回仅注入 3 条 ≤ 2100 rune 摘要，远低于实例池重放 100 条历史。
3. **跨 Agent 共享**：任何角色的子 Agent 派发时都可召回，实例池只对同一 subAgentID 服务。

### 实例池强项（块记忆无法覆盖）
1. **同任务多轮追问精度**：send_message 按 subAgentID 精确投递，无召回噪声。块记忆语义检索可能召回无关记忆。
2. **完整上下文保留**：实例池保留对话历史（含工具调用细节），块记忆只有 ≤ 500 rune 摘要。
3. **LLM 主动权**：LLM 按需 send_message，不依赖系统自动注入。

### "块记忆过于抽象"的真实问题
原文反馈"可用性与传统感觉不明显"。根因不是块记忆设计错误，而是：
1. **此前从未运行**：阶段 1 之前 `SaveKnowledge` 全库零生产调用方，召回永远命中空集。已修复。
2. **召回注入对 LLM 不可见**：命中记忆拼到任务前，LLM 不知道"这是历史经验"还是"当前任务的一部分"。当前格式 `【相关记忆】` 前缀已有区分，但 LLM 是否利用未量化。
3. **无召回命中率观测**：无日志/指标记录"召回了几条、是否被采纳"。

## 四、融合方案（推荐）

**结论：保留两机制，融合点在"实例池服务态结束时沉淀块记忆"。**

### 当前已融合点
- 块记忆写入：子 Agent 完成初始任务时（`runSubAgentOnce` 末尾）
- 实例池服务态：子 Agent 完成初始任务后转入（`servePooled`）

### 待补融合点（建议）
1. **实例池退出时再沉淀一次块记忆**：`servePooled` 闲置超时退出前，把服务态期间的问答摘要写入块记忆。这样跨会话经验不仅含初始任务结论，还含追问轮的修正经验。
   - 改动点：`servePooled` 退出分支调用 `saveBlockMemory`，goal 用初始 task，result 用最后一轮答复。
   - 收益：跨会话经验更完整，块记忆召回价值提升。

2. **实例池服务态期间召回块记忆**：`RunWithHistory` 处理 send_message 询问前，按询问文本召回块记忆注入。当前只重放自身历史，无跨实例经验。
   - 改动点：`servePooled` 收到消息后，先 `injectRecalledMemory(m.Body)` 再 `RunWithHistory`。
   - 收益：被询问协程能看到其他 Agent 的历史经验，接近原文"协程Agent常驻共享代码Agent记忆"语义。

3. **块记忆召回命中率观测**：`injectRecalledMemory` 命中时记日志（命中条数 + goal 文本），便于量化召回有效性。
   - 改动点：`injectRecalledMemory` 加 `log.Printf`。
   - 收益：为"块记忆可用性"提供量化数据。

### 不推荐
- **用实例池替代块记忆**：丢失跨会话经验复用，Token 成本反增（重放历史 vs 注入摘要）。
- **用块记忆替代实例池**：丢失同任务多轮追问精度与完整上下文。

## 五、量化对比（理论估算）

场景：code_assistant 完成任务后，被追问 3 轮修正。

| 方案 | 单轮 Token 估算 | 3 轮总 Token | 跨会话可用 | 精度 |
|---|---|---|---|---|
| 纯块记忆（每次召回） | 3 条摘要 ≈ 2K rune | 6K（3 次召回） | 是 | 语义检索，有噪声 |
| 纯实例池（重放历史） | 100 条历史 ≈ 50K rune | 150K（累积） | 否 | 精确 |
| 融合（池内+召回） | 历史 50K + 摘要 2K | 156K | 是 | 精确+跨实例经验 |

**结论**：融合方案 Token 成本与纯实例池接近，但多出跨会话经验复用能力，性价比最高。

---

## 六、最终结论

1. **不替代**：两机制解决不同问题，不可互相替代。
2. **融合**：实例池服务态期间引入块记忆召回 + 退出时沉淀，实现"协程Agent常驻共享代码Agent记忆"语义。
3. **块记忆可用性提升**：补召回命中率观测，用量化数据验证"可用性不明显"是否改善。
4. **优先级**：融合点 3（观测）最易落地，应先做，为后续评估提供数据；融合点 1/2 需评估内存与 Token 预算后实施。
