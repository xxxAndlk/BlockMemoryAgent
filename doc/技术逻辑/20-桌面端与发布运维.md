# 20 桌面端与发布运维

> 本章对应 Windows 桌面壳、版本化发布脚本、健康门禁与 Docker 媒体适配。主要代码：`backend/cmd/desktop`、`internal/buildinfo`、`bma-app.ps1`、`tools/app/launch.ps1`、`docker/docker-compose.yml`、`docker/minimax-media`。
>
> 早期 `dist.ps1`／`install.ps1` 和旧部署文档仍有历史价值；本章描述当前已核对的 `bma-app.ps1` 版本化布局与桌面行为。

## 20.1 模块边界

桌面发布链分四层：

| 层 | 职责 | 不应承担的职责 |
|---|---|---|
| `bma-server` | HTTP API、SSE、Agent 与全部业务子系统 | 不负责窗口和托盘 |
| `bma-desktop` | WebView2 窗口、托盘、后端探测与进程生命周期 | 不实现会话／Agent 业务规则 |
| `bma-app.ps1` | 打包、安装、更新、启停、状态、回滚 | 不替代数据库迁移与业务测试 |
| Docker／媒体适配 | PostgreSQL、Redis、open_design、MiniMax 协议桥 | 不等于桌面进程管理器 |

`tools/app/launch.ps1` 是安装后启动辅助；仓库根 `bma-app.ps1` 是发布运维主入口。

## 20.2 Windows 桌面外壳

`backend/cmd/desktop` 使用 WebView2 展示本地 Web UI，默认后端地址为 `127.0.0.1:10010`。

启动顺序：

1. 请求 `/api/health`，确认是否已有健康后端；
2. 若未就绪，读取安装目录 `app/current.json`，启动该版本目录中的 `bma-server.exe`；
3. 最多等待 90 秒健康就绪；
4. 使用 WebView2 打开窗口；
5. WebView2 不可用时退化 Edge／Chrome `--app`；
6. 再不可用时退化系统默认浏览器。

健康探测优先意味着同机已有匹配服务时可复用，但发布更新不能只靠“端口有响应”判断新版本已启动，因此更新流程还会检查 build.version。

### 关窗与托盘

- 关闭窗口默认只是隐藏到托盘，后端继续运行；
- 托盘“退出（停止后台）”才停止后端；
- 单实例互斥体按安装目录命名，允许不同安装目录有独立实例语义；
- 停止后端时按可执行文件路径限制在该安装目录，避免误杀其他 BMA 实例。

因此“关了窗口”不能作为后端已停止、端口已释放或更新可以安全覆盖的证据。

## 20.3 版本化安装布局

当前采用不可变版本目录与指针：

```text
<安装目录>/
  app/
    current.json          # 当前版本指针
    versions/
      <版本 A>/           # 该版本二进制与只读发布内容
      <版本 B>/
      ...
  config/                 # 用户配置，按安装逻辑只补缺
  plugins/                # 用户插件与运行扩展
  workspace/              # 默认工作目录与用户产物
  logs/                   # 运行日志
```

具体目录由脚本参数和既有安装决定，以上是职责布局而非要求所有历史安装逐字一致。核心原则是：

- 版本内容放在 `app/versions/<版本>`，更新生成新版本目录；
- `current.json` 决定桌面壳启动哪个版本；
- 配置、插件、workspace、logs 是用户数据，不应随版本替换被清空；
- 回滚切换回 previous，而不是重新拼装旧二进制。

单实例与进程停止都按安装目录隔离，支持同机多个安装目录时减少互相误伤。

## 20.4 打包与敏感数据边界

`bma-app.ps1 pack` 构建前端和服务端、桌面端等三个二进制。只有显式 `pack -Test` 才额外运行 `go test ./...`；普通 pack 成功只表示构建与打包流程完成，不能宣称全量测试通过。

打包明确排除运行时数据和秘密，包括：

- `.env`；
- `models.json` 等含模型连接／密钥引用的本机配置；
- `user_profile.md`；
- `plugins.installed.yaml`；
- `skills_learned` 等学习产生的数据。

安装／更新采用“只补缺、不覆盖既有用户数据”的策略。不要把仓库模板中的密钥、Token、画像、工作区产物或本机路径打进公开包。

构建通过 ldflags 注入：

- `buildinfo.Version`；
- `buildinfo.Commit`；
- `buildinfo.BuiltAt`。

`/api/health` 暴露 build 信息，供状态检查和更新门禁使用。

## 20.5 `bma-app.ps1` 命令面

| 命令 | 用途 | 关键注意事项 |
|---|---|---|
| `pack` | 构建前端与二进制、生成版本包 | `-Test` 才附加 Go 测试 |
| `install` | 安装版本并补齐用户数据 | 不覆盖既有配置与数据 |
| `update` | 部署新版本、健康门禁、必要时回滚 | 必须核对 build.version |
| `deploy` | 面向目标目录的一体化构建／部署入口 | 参数以脚本当前定义和 `Get-Help` 为准 |
| `start` | 启动当前安装 | 使用 current 指针 |
| `stop` | 停止本安装目录后端 | 按可执行路径限定，避免误杀 |
| `restart` | 重启当前安装 | 重启后仍需健康检查 |
| `status` | 查看进程、版本与健康状态 | 端口健康不等于任意版本都正确 |
| `rollback` | 回滚到 previous | 保留用户数据与版本目录 |

更新默认保留 3 个版本。保留数量是磁盘与回滚深度的折中，不表示数据库可以无条件跨任意旧版本回退；涉及迁移时仍须评估数据兼容性。

## 20.6 更新健康门禁与回滚

更新流程不能只等待端口：

```text
启动新版本
   ▼
请求 /api/health
   ▼
健康 status 正常？
   ├─ 否 → 判定失败 → 回滚 previous
   └─ 是
       ▼
build.version == 期望版本？
   ├─ 否 → 可能命中旧进程／旧实例 → 判定失败并回滚
   └─ 是 → 更新成功，保留 previous
```

双重校验是为了避免旧进程占用端口造成“假更新成功”。运维排查应同时看：

- `current.json` 指向；
- `/api/health` 的 build；
- 本安装目录进程路径；
- 托盘后台是否仍在运行；
- 对应版本与后端日志。

更新失败自动回滚 previous。回滚成功表示服务版本切回，不等于外部生成任务、用户数据或已执行数据库迁移都被事务性撤销。

## 20.7 Docker Compose 当前组成

`docker/docker-compose.yml` 当前包含：

| 服务 | 职责 |
|---|---|
| `postgres` | PostgreSQL 与 pgvector 数据面 |
| `redis` | 热数据、事件／快照等 Redis 数据面 |
| `open_design` | 设计台及相关媒体生成服务入口 |
| `minimax-media` | MiniMax 图像／视频协议适配桥 |

`computer_use` 已改为按需 Docker transport 插件，不是常驻 Compose 服务。端口、密码、API Token 与外部服务参数以当前 compose 和本地配置为准；文档不复制秘密值。

启动基础设施仍使用仓库 Makefile／Compose 入口，但桌面版本更新与容器数据面是两套生命周期，不应把 `bma-app.ps1 update` 当作自动升级所有外部 Docker 服务的保证。

### 自带运行时与正式安装包（2026-11-14）

桌面版要做到"装上就能用"，就不能把 PostgreSQL 与 Redis 的准备成本转嫁给用户。本轮按商业桌面应用的常规形态落地：**安装包 + 自带运行时 + 独立数据目录**。

- **自带运行时**：`installer/fetch-runtime.ps1` 下载三样东西到 `dist\runtime-cache\`（不进 git）：PostgreSQL 16 免安装版（EDB binaries zip）、pgvector 0.8.7 的 Windows 预编译包、Redis 5.0.14.1 for Windows；`bma-app.ps1 pack` 解压裁剪后打进包的 `runtime\`（去掉 include/doc/静态库/pg_upgrade/pgbench 后 122MB）。pgvector 的两个位置都要放对：控制文件与 SQL 在 `share\extension\`，动态库在 `lib\`（Windows 版 pkglibdir 就是 `lib\`）。
- **当子进程跑**（`backend/cmd/desktop/runtime.go`）：外壳负责首次 `initdb` → `pg_ctl start` → 建库 → `CREATE EXTENSION vector` → 起 Redis → 等就绪 → 把生效的 DSN/Redis 写回 `.env`。这与 Postgres.app、pgAdmin 的做法一致：服务端二进制随包、应用自己管生命周期。数据目录 `%LOCALAPPDATA%\BlockMemoryAgent\data\{pg,redis}`，实例口令与端口记在同目录的 `instance.json`（跟数据走：换安装目录、重装都不换口令，否则已初始化的数据目录会认证失败）。
- **与开发实例隔离**：自带实例默认端口 55432 / 56380（开发实例是 5432 / 6380），数据各在一份。开发实例里的历史数据用 `bma-app.ps1 migrate-data -Target <安装目录> -FromDsn <源库 DSN>` 一次性搬过去（pg_dump/pg_restore 随包）。
- **正式安装包**（`installer/blockmemoryagent.iss`，Inno Setup 6）：per-user 安装到 `%LOCALAPPDATA%\Programs\BlockMemoryAgent`（不需要管理员）；铺程序 + `runtime\` + `docker\`；`config\` 与 `.env` 只在缺失时种子化，升级绝不覆盖；开始菜单与桌面快捷方式、注册卸载项；目标机缺 WebView2 运行时则静默补装（内置引导程序）；卸载前调 `BMA-Desktop.exe --stop` 停掉后端与内置运行时；用户数据（数据库、日志、工作目录）卸载时默认保留。产物约 78MB。
- **依赖优先级**：`ensureAllDeps` 先看安装包里有没有 `runtime\`——有就用自带运行时（目标机免装 Docker），没有才走 Docker 路径；`.env` 里显式配了远程 PostgreSQL/Redis 时一律不接管。

### 原生媒体栈：免 Docker 的生图/生视频（2026-11-15）

桌面版要做到"目标机器只装 Windows 就能用"，媒体能力就不能依赖 Docker 容器。daemon 上游是编译后的完整应用镜像，vendor 不进安装包；但 ui_design 桥实际只用到 9 个 HTTP 端点，因此按同一协议实现了一个原生替身：

- `backend/cmd/mediaservice`（`bin\mediaservice.exe`）：实现 `/api/media/config`、`/api/media/models`、`/api/projects`（建/列）、`/api/projects/{id}/files`（上传/下载）、`/api/projects/{id}/media/generate`、`/api/projects/{id}/media/tasks`。任务模型与 daemon 一致（`taskId` + `status` + `file.fileName`），桥无需改动。
- 配置来源仍是 `.env` 媒体段，**槽位名与映射照抄容器 entrypoint**（`custom-image` / `nanobanana` / `aihubmix` / `volcengine` / `grok`，含 URL 归一与能力声明），避免出现"两套配置语义"。
- 随包 Node（`runtime\node\node.exe`）以 **stdio** 方式起 ui_design 桥；`plugins.yaml` 的 ui_design 段在打包时改写成 stdio，路径用**整串**占位符 `${BMA_NODE_EXE}` / `${BMA_MEDIA_BRIDGE}`（配置插值只认整串 `${VAR}`，嵌在路径中间会原样保留）。安装时 `config\plugins.yaml` 只在"用户没改过"时随版本更新。
- 仓库 `.env` 里的媒体地址指向容器服务名（`minimax-media:8787`）→ 随包带 **MiniMax 适配桥**（零依赖单文件 Node 服务）作本地进程顶替；原生媒体服务把该主机名改写为回环。
- 能力边界：纯文本生成（t2i/t2v）与 OpenAI 兼容的参考图通道（`image` 字段传 data URL）已通；本地编辑、Gemini 生图、方舟视频等上游特有形状仍需容器 daemon。

### 首启向导与自动更新（2026-11-15）

- **首启向导**：`.env` 里模型 Key / 嵌入 Key 仍是占位值时，外壳先弹引导页（模型 Key、模型接口地址、嵌入地址与 Key），填完写进 `.env` 再继续启动；可「稍后再说」（相关能力降级）。已配置过的一律不弹窗。模型注册表随包带**去密钥模板**（只含 `${VAR}` 引用），安装时缺失才铺。
- **自动更新**：更新地址写在 `.env` 的 `BMA_UPDATE_URL`（一个 JSON：`version`/`url`/`sha256`/`notes`）。启动后后台检查一次，托盘另有「检查更新」；发现新版 → 询问 → 下载 → 校验 sha256 → 静默运行安装包 → 退出旧版。没配地址就不检查。

### 桌面版依赖自举（2026-11-14）

后端是严格启动：PostgreSQL／Redis 连不上直接退出（装配依赖失败即 `os.Exit(1)`），而 pgvector 只能跑在容器里。此前安装包不含 `docker/`，桌面版没有自己的依赖编排，用户必须先手工开 Docker Desktop、手工 `compose up`——「双击即用」不成立。

现在：

- **包内自带编排**：`pack` 把 `docker/docker-compose.yml` 与四个镜像构建上下文（`open-design-daemon`、`minimax-media`、`open-design-mcp`、`ui-preview-mcp`）打进版本目录，`install` 覆盖到 `<安装目录>\docker\`。compose 文件与仓库同源（项目名 `bma`、卷名 `docker_postgres_data`／`docker_redis_data`／`bma-open-design-data` 固定），因此桌面版与开发实例**共用同一套容器与数据卷**：数据不丢、端口不冲突。
- **外壳负责自举**（`backend/cmd/desktop/deps.go`）：探测依赖 → 引擎不可用则拉起 Docker Desktop 并等就绪 → `compose up -d postgres redis` → 轮询等 PG／Redis 真正可用（用真实驱动 ping，能区分「库没起」与「账号／库名不对」）→ 再起后端。失败一律给出可读原因与可执行动作。
- **等待不再空转**：后端进程提前退出（严格启动 fail-fast）时立即判失败，并把后端日志尾部摆到错误页，而不是旧版那样闷等 90 秒才报「未就绪」。错误页带「重试启动」按钮。
- **启动过程可见**：依赖自举期间窗口显示进度页（拉镜像可能耗时数分钟），就绪后原地切到 UI——只有一个窗口，无进度窗／主窗抖动。
- **媒体栈放后台**：open_design daemon、minimax-media 桥与两个插件镜像体积大、构建慢，不进启动关键路径；失败只落 `logs\media_setup_*.log`，插件按既有降级语义处理（不可用但不阻断）。镜像就绪后调 `POST /api/plugins/reload` 换 keeper。
- **脚本启动器同源**：`tools/app/launch.ps1` 起后端前调 `BMA-Desktop.exe --ensure-deps`（结果写 `app\deps.json`），依赖实现只有 Go 一份，避免 PowerShell／Go 双实现漂移。
- **媒体配置单点应用**：`<安装目录>\.env` 媒体段改完后跑 `.\bma-app.ps1 media -Target <安装目录>`（对齐 `docker/bma-plugin.sh media`：重建桥镜像 → 重建 `open_design` 容器让 entrypoint 重写 `media-config.json` → 换 `ui_design` keeper）。

手工兜底（自举失败时）：`docker compose -f <安装目录>\docker\docker-compose.yml up -d postgres redis`。

## 20.8 MiniMax 媒体协议适配

`docker/minimax-media/server.js` 是零第三方 npm 依赖的 Node 适配桥。它把 MiniMax 图像／视频协议翻译成 open_design daemon 已支持的接口形状：

- OpenAI 风格图像请求；
- grok 风格视频请求；
- 视频 v1／v2 相关调用；
- 异步任务轮询；
- 上游错误透传；
- 健康检查不回显 Key。

它解决的是协议适配，不是模型质量证明，也不把 MiniMax 变成 OpenAI 官方服务。Compose 注释中的外部模型或 API 参数示例不应写成本项目已实测结论；实际可用模型、额度和结果取决于外部服务及本地配置。

媒体结果进入 Workflow 时仍受 19 章限制：程序可检查部分格式／尺寸，文本评委不看像素，视觉质量需要人审。

## 20.9 故障排查顺序

| 现象 | 优先检查 |
|---|---|
| 窗口关了但端口仍占用 | 托盘后台仍在运行；用托盘退出或本安装 stop |
| 桌面打开失败 | 后端 health、current.json、90 秒等待日志、WebView2 与浏览器退化 |
| 桌面报「依赖未就绪」 | `app\deps.json` 的 error/hint；Docker 是否在跑；端口 5432／6380 是否被占 |
| 更新显示成功但功能仍旧 | health 中 build.version 是否真为期望值，是否命中其他安装实例 |
| stop 影响其他实例风险 | 核对可执行文件路径过滤和安装目录互斥体，不按端口盲杀 |
| 更新后配置丢失疑虑 | 检查用户数据目录与“只补缺”逻辑，不从版本包恢复秘密 |
| 更新失败 | 看门禁失败原因和 previous 回滚结果，不反复覆盖用户目录 |
| 媒体桥错误 | 看上游错误透传、任务轮询与配置；健康检查不会展示 Key |

## 20.10 验证边界

本章来自桌面 Go 源码、发布 PowerShell、Compose 和 Node 适配代码的静态核对；2026-11-14 的依赖自举改动另做了本机实测（见 `doc/变更.md` 同日条目）：冷启动部署（停 Docker Desktop + 停后端）下自举按序完成、门禁通过、桌面外壳内 UI 正常渲染、错误页给出真实原因与重试按钮、媒体栈与插件 keeper 随之重建。

未覆盖的部分：多安装目录并存时的隔离、跨机器分发与首次装机（无 Docker 场景）的完整验收、外部 MiniMax 请求与生成质量。

执行发布验证时，至少分别记录：

1. 前端构建与三个二进制构建；
2. `pack -Test` 的测试结果（如启用）；
3. 新装与保留用户数据的升级；
4. 健康 status 与 build.version 双门禁；
5. 失败回滚和版本保留；
6. 关窗、托盘退出与多安装目录隔离；
7. Docker 服务及媒体桥的独立冒烟结果；
8. 依赖自举：`app\deps.json` 的步骤记录、冷启动（Docker 未运行）与依赖缺失（DSN 指错）两条失败路径。
