# 20 桌面端与发布运维

> 本章对应 Windows 桌面壳、版本化发布脚本、健康门禁与 Docker 媒体适配。主要代码：`backend/cmd/desktop`、`internal/buildinfo`、`bma-app.ps1`、`tools/app/launch.ps1`、`docker/docker-compose.yml`、`docker/minimax-media`。
>
> 早期 `dist.ps1`／`install.ps1` 和旧部署文档仍有历史价值；本章描述当前已核对的 `bma-app.ps1` 版本化布局与桌面行为。

## 20.1 模块边界

桌面发布链分四层：

| 层 | 职责 | 不应承担的职责 |
|---|---|---|
| `bma-server` | HTTP API、SSE、Agent 与全部业务子系统 | 不负责窗口和托盘 |
| `bma-desktop` | WebView2 窗口、托盘、后端探测与进程生命周期 | 不实现会话／Agent 业务规则 |
| `bma-app.ps1` | 打包、安装、更新、启停、状态、回滚 | 不替代数据库迁移与业务测试 |
| Docker／媒体适配 | PostgreSQL、Redis、open_design、MiniMax 协议桥 | 不等于桌面进程管理器 |

`tools/app/launch.ps1` 是安装后启动辅助；仓库根 `bma-app.ps1` 是发布运维主入口。

## 20.2 Windows 桌面外壳

`backend/cmd/desktop` 使用 WebView2 展示本地 Web UI，默认后端地址为 `127.0.0.1:10010`。

启动顺序：

1. 请求 `/api/health`，确认是否已有健康后端；
2. 若未就绪，读取安装目录 `app/current.json`，启动该版本目录中的 `bma-server.exe`；
3. 最多等待 90 秒健康就绪；
4. 使用 WebView2 打开窗口；
5. WebView2 不可用时退化 Edge／Chrome `--app`；
6. 再不可用时退化系统默认浏览器。

健康探测优先意味着同机已有匹配服务时可复用，但发布更新不能只靠“端口有响应”判断新版本已启动，因此更新流程还会检查 build.version。

### 关窗与托盘

- 关闭窗口默认只是隐藏到托盘，后端继续运行；
- 托盘“退出（停止后台）”才停止后端；
- 单实例互斥体按安装目录命名，允许不同安装目录有独立实例语义；
- 停止后端时按可执行文件路径限制在该安装目录，避免误杀其他 BMA 实例。

因此“关了窗口”不能作为后端已停止、端口已释放或更新可以安全覆盖的证据。

## 20.3 版本化安装布局

当前采用不可变版本目录与指针：

```text
<安装目录>/
  app/
    current.json          # 当前版本指针
    versions/
      <版本 A>/           # 该版本二进制与只读发布内容
      <版本 B>/
      ...
  config/                 # 用户配置，按安装逻辑只补缺
  plugins/                # 用户插件与运行扩展
  workspace/              # 默认工作目录与用户产物
  logs/                   # 运行日志
```

具体目录由脚本参数和既有安装决定，以上是职责布局而非要求所有历史安装逐字一致。核心原则是：

- 版本内容放在 `app/versions/<版本>`，更新生成新版本目录；
- `current.json` 决定桌面壳启动哪个版本；
- 配置、插件、workspace、logs 是用户数据，不应随版本替换被清空；
- 回滚切换回 previous，而不是重新拼装旧二进制。

单实例与进程停止都按安装目录隔离，支持同机多个安装目录时减少互相误伤。

## 20.4 打包与敏感数据边界

`bma-app.ps1 pack` 构建前端和服务端、桌面端等三个二进制。只有显式 `pack -Test` 才额外运行 `go test ./...`；普通 pack 成功只表示构建与打包流程完成，不能宣称全量测试通过。

打包明确排除运行时数据和秘密，包括：

- `.env`；
- `models.json` 等含模型连接／密钥引用的本机配置；
- `user_profile.md`；
- `plugins.installed.yaml`；
- `skills_learned` 等学习产生的数据。

安装／更新采用“只补缺、不覆盖既有用户数据”的策略。不要把仓库模板中的密钥、Token、画像、工作区产物或本机路径打进公开包。

构建通过 ldflags 注入：

- `buildinfo.Version`；
- `buildinfo.Commit`；
- `buildinfo.BuiltAt`。

`/api/health` 暴露 build 信息，供状态检查和更新门禁使用。

## 20.5 `bma-app.ps1` 命令面

| 命令 | 用途 | 关键注意事项 |
|---|---|---|
| `pack` | 构建前端与二进制、生成版本包 | `-Test` 才附加 Go 测试 |
| `install` | 安装版本并补齐用户数据 | 不覆盖既有配置与数据 |
| `update` | 部署新版本、健康门禁、必要时回滚 | 必须核对 build.version |
| `deploy` | 面向目标目录的一体化构建／部署入口 | 参数以脚本当前定义和 `Get-Help` 为准 |
| `start` | 启动当前安装 | 使用 current 指针 |
| `stop` | 停止本安装目录后端 | 按可执行路径限定，避免误杀 |
| `restart` | 重启当前安装 | 重启后仍需健康检查 |
| `status` | 查看进程、版本与健康状态 | 端口健康不等于任意版本都正确 |
| `rollback` | 回滚到 previous | 保留用户数据与版本目录 |

更新默认保留 3 个版本。保留数量是磁盘与回滚深度的折中，不表示数据库可以无条件跨任意旧版本回退；涉及迁移时仍须评估数据兼容性。

## 20.6 更新健康门禁与回滚

更新流程不能只等待端口：

```text
启动新版本
   ▼
请求 /api/health
   ▼
健康 status 正常？
   ├─ 否 → 判定失败 → 回滚 previous
   └─ 是
       ▼
build.version == 期望版本？
   ├─ 否 → 可能命中旧进程／旧实例 → 判定失败并回滚
   └─ 是 → 更新成功，保留 previous
```

双重校验是为了避免旧进程占用端口造成“假更新成功”。运维排查应同时看：

- `current.json` 指向；
- `/api/health` 的 build；
- 本安装目录进程路径；
- 托盘后台是否仍在运行；
- 对应版本与后端日志。

更新失败自动回滚 previous。回滚成功表示服务版本切回，不等于外部生成任务、用户数据或已执行数据库迁移都被事务性撤销。

## 20.7 Docker Compose 当前组成

`docker/docker-compose.yml` 当前包含：

| 服务 | 职责 |
|---|---|
| `postgres` | PostgreSQL 与 pgvector 数据面 |
| `redis` | 热数据、事件／快照等 Redis 数据面 |
| `open_design` | 设计台及相关媒体生成服务入口 |
| `minimax-media` | MiniMax 图像／视频协议适配桥 |

`computer_use` 已改为按需 Docker transport 插件，不是常驻 Compose 服务。端口、密码、API Token 与外部服务参数以当前 compose 和本地配置为准；文档不复制秘密值。

启动基础设施仍使用仓库 Makefile／Compose 入口，但桌面版本更新与容器数据面是两套生命周期，不应把 `bma-app.ps1 update` 当作自动升级所有外部 Docker 服务的保证。

## 20.8 MiniMax 媒体协议适配

`docker/minimax-media/server.js` 是零第三方 npm 依赖的 Node 适配桥。它把 MiniMax 图像／视频协议翻译成 open_design daemon 已支持的接口形状：

- OpenAI 风格图像请求；
- grok 风格视频请求；
- 视频 v1／v2 相关调用；
- 异步任务轮询；
- 上游错误透传；
- 健康检查不回显 Key。

它解决的是协议适配，不是模型质量证明，也不把 MiniMax 变成 OpenAI 官方服务。Compose 注释中的外部模型或 API 参数示例不应写成本项目已实测结论；实际可用模型、额度和结果取决于外部服务及本地配置。

媒体结果进入 Workflow 时仍受 19 章限制：程序可检查部分格式／尺寸，文本评委不看像素，视觉质量需要人审。

## 20.9 故障排查顺序

| 现象 | 优先检查 |
|---|---|
| 窗口关了但端口仍占用 | 托盘后台仍在运行；用托盘退出或本安装 stop |
| 桌面打开失败 | 后端 health、current.json、90 秒等待日志、WebView2 与浏览器退化 |
| 更新显示成功但功能仍旧 | health 中 build.version 是否真为期望值，是否命中其他安装实例 |
| stop 影响其他实例风险 | 核对可执行文件路径过滤和安装目录互斥体，不按端口盲杀 |
| 更新后配置丢失疑虑 | 检查用户数据目录与“只补缺”逻辑，不从版本包恢复秘密 |
| 更新失败 | 看门禁失败原因和 previous 回滚结果，不反复覆盖用户目录 |
| 媒体桥错误 | 看上游错误透传、任务轮询与配置；健康检查不会展示 Key |

3. 新装与保留用户数据的升级；
