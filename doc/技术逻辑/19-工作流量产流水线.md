# 19 工作流量产流水线

> 本章对应 `internal/workflow`、`internal/server/workflow.go`、`internal/bootstrap/workflow.go` 与 `migrations/014_workflow.sql`。
>
> Workflow 的目标是把 Agent 打样形成的生产方法固化为配方，对名册中的多件素材执行“件 × 阶段”的批量生产。它不是普通聊天、DAG 定时任务或 Flow 节点图的别名。

## 19.1 模块边界与核心抽象

| 抽象 | 含义 | 真相源 |
|---|---|---|
| Recipe／配方 | 阶段、提示词、契约、锚点、校验和参数的生产定义 | `<workdir>/.bma/workflows/*.yaml` |
| Roster／名册 | 一行一件的待生产对象，可内联 JSON 或引用 YAML／JSON 文件 | run 创建参数及其引用文件 |
| Run | 一次配方与名册的批量执行 | `workflow_runs` |
| Unit／Cell | 一件在某个阶段的一次 attempt | `workflow_units` |
| Anchor／锚点 | 静态配方与前置已采纳阶段共同提供的参考约束 | 配方与 done 单元的 `anchor_out` |
| Attempt | 同一单元的第 N 次生成；重摇新增而非擦旧 | `idem_key=run/item/stage#attempt` |

Run 创建时将配方全文快照到 `workflow_runs.recipe_yaml`。之后修改 YAML 不应重写历史 run 的生产依据。

### 与其他编排的区别

- 普通子 Agent：开放任务、自主 ReAct，父子 Mailbox 回传。
- Flow：节点图串行执行，节点审批。
- DAG：定时和依赖触发。
- Workflow：有界名册、多阶段、逐件并发、程序／模型／人三层校验、重摇与预算。

## 19.2 配方与名册

### 配方

`recipe.go`、`prompt.go` 等负责读取和解释配方。配方可定义阶段链、每件输入如何进入提示词、输出契约、程序校验、锚点传递和默认参数。

保存配方时版本自动递增。`workflow_freeze` 与反馈生成的是草案，需用户确认／编辑后才成为文件，不允许模型静默覆盖生产配方。

### 名册

`roster.go` 支持：

- run 参数中的内联 JSON；
- YAML 或 JSON 文件；
- 一行一件；
- 任意槽位平铺到该项输入；
- `stages` 按件裁剪执行阶段。

预检要求 item ID 唯一，并校验阶段引用，避免运行到中途才因名册结构错误大面积失败。

## 19.3 数据模型与状态机

PostgreSQL 只有两张核心表：

- `workflow_runs`：run 状态、配方快照、名册／参数、预算与终态信息；
- `workflow_units`：item、stage、attempt、产物、校验、人审、幂等键等单元轨迹。

状态更新使用带旧状态条件的乐观迁移，避免并发回调把已推进状态覆盖回去。

### Run 状态

```text
pending → running → done
             ├────► paused ─► running
             ├────► failed
             └────► aborted

终态 run 在后续 reroll 时可以复活，回到可调度状态。
```

| 状态 | 含义 |
|---|---|
| `pending` | 等待活跃槽，按 FIFO 提升 |
| `running` | 正在调度件与阶段 |
| `paused` | 用户暂停或预算达 cap，可续跑 |
| `done` | 所有必需单元达到完成条件 |
| `failed` | 失败或打样期熔断 |
| `aborted` | 用户中止 |

### Unit 状态

| 状态 | 含义 |
|---|---|
| `pending` | 等待执行 |
| `running` | 当前 attempt 执行中 |
| `done` | 已采纳，可向后继阶段提供锚点 |
| `needs_review` | 需要人工裁决；评委不可用／解析失败也进入此态 |
| `failed` | 当前单元失败或重摇耗尽 |
| `skipped` | 按件或人工决定跳过 |

一个 unit 表示一次 attempt；重摇会新增 attempt，不删除被否决的历史。产物 attempt 路径也避免覆盖被否版本，以便审查和对账。

## 19.4 调度与恢复

每个活跃 run 有一个调度 goroutine：**件间并发，件内阶段串行**。后继阶段依赖前置阶段的采纳产物与锚点，因此不能把同一件的所有阶段无条件并行。

| 配置 | 当前默认 | 含义 |
|---|---:|---|
| `workflow.max_active_runs` | 4 | 全局活跃 run 数，超出进入 pending |
| `workflow.default_concurrency` | 2 | 件间默认并发；配方 params 与 run 参数可覆盖 |
| `workflow.budget_cap_default` | 500 | 生成与评委轻量调用的默认估算预算 |
| `workflow.judge_timeout_ms` | 30000 | 单次模型评委超时 |

重启恢复：

1. 将 `running` unit 复位为 `pending`，保留原幂等键；
2. 恢复 `running` run；
3. `pending` run 按 FIFO 提升；
4. 从 done 单元的 `anchor_out` 重建后继所需锚点。

数据库 attempt 复用能减少重复推进，但**不能承诺外部生成工具绝对没有重复副作用**。在进程已调用外部服务、尚未写最终状态时崩溃，外部系统是否重试取决于该工具与服务的幂等能力。

## 19.5 单单元执行链

```text
提示词与锚点合成
       ▼
调用生成工具
       ▼
程序校验 exists/path/format/dimensions
       ▼
文本轻量评委（提示词 + 契约 + 路径）
       ▼
采纳／重摇／needs_review
       ▼
人工 accept/reject/reroll/skip
       ▼
done 单元输出 anchor_out，供后继阶段使用
```

### 程序校验

`check.go` 支持：

- `exists`：产物是否存在；
- `path_template`：路径是否符合约定；
- `format`：格式与魔数等检查；
- `dimensions`：图像尺寸；PNG 可结合网格尺寸与 alpha 等约束。

PNG 有尺寸、网格和透明通道相关支持，JPEG 等格式有格式／魔数检查；video 不做图像式尺寸校验。程序校验只验证明确规则，不等于语义质量验收。

### 文本轻量评委

`judge.go` 的评委只看提示词、契约和路径等文本信息，**不读取像素、不真正观看图片或视频**。

- 评委不可用或结果解析失败时转 `needs_review`，不静默放行。
- 视觉品味、画面内容、动作自然度等仍需要人审或未来真实视觉校验。
- 不能把“通过 judge”写成“完成视觉质量验收”。

### 锚点传播

锚点来自静态配方和前置阶段的已采纳产物。只有满足条件的 done 单元才能向后传递 `anchor_out`，重摇被否版本不应替代已采纳锚点。

## 19.6 重摇、人审、预算与熔断

### 重摇

默认单单元重摇上限为 2。重摇创建新 attempt 并保留旧产物，适用于程序校验、评委或人审认为当前结果不达标的情况。

重摇耗尽可派真子 Agent 升级处理，但 v1 只记录升级 Agent ID，**不会自动回收该 Agent 的产物**；unit 仍保持待审或失败，需要后续人工／流程处理。

### 人审动作

`POST /api/workflow/units/:uid/:action` 支持：

| 动作 | 语义 |
|---|---|
| `accept` | 采纳当前 attempt，unit 进入 done，可传播锚点 |
| `reject` | 否决，必须提供理由 |
| `reroll` | 生成新 attempt；终态 run 也可因此复活 |
| `skip` | 跳过该单元，按 run 完成规则继续汇总 |

人审历史与重摇 attempt 共同保留，不能只保存最后一次结果。

### 预算

预算按生成与评委的轻量调用估算。达到 cap 时 run 进入 `paused`，可在运行页提高额度后续跑。它是调用量控制，不是精确人民币成本结算，也不涵盖所有外部工具的隐藏费用。

### Fail-fast

打样期熔断默认开启：前 5 个进入终态的 cell 中，`failed` 与 `needs_review` 合计达到 3 个，run 失败并回到打样期语义，避免明显错误配方继续烧完整名册。

## 19.7 冻结、反馈与漂移

### `workflow_freeze`

从最近成功生成轨迹提取配方草案：

1. 收集已成功的提示词、工具参数与生产路径；
2. 模型只负责参数化与结构化；
3. 形成 YAML 草案；
4. 用户确认／编辑后落盘，保存时版本递增。

模型不能绕过确认通道直接冻结生产配方。

### `workflow_feedback`

聚合适当失败原因与人审反馈，生成 v+1 YAML 草案。它不直接落盘，也不意味着反馈已自动改进当前 run；需用户审查草案后保存并创建新运行。

### 漂移检测

`drift.go` 使用提示词向量与同阶段质心的余弦距离，阈值为 0.4。其语义是：

- best-effort 提示；
- 不阻断运行；
- 不跨重启持久化；
- 不是图像内容漂移检测，也不是配方正确性的硬门禁。

## 19.8 Agent 工具与 HTTP API

### Agent 工具

| 工具 | 用途 | 确认边界 |
|---|---|---|
| `workflow_freeze` | 从成功轨迹生成并确认配方 | 经会话确认通道 |
| `workflow_run` | 创建／启动批量 run | 经会话确认通道 |
| `workflow_status` | 查询 run 与单元进度 | 查询能力 |

### HTTP 端点（11）

| 方法与路径 | 用途 |
|---|---|
| `GET /api/workflow/recipes` | 配方列表 |
| `GET /api/workflow/recipes/:id` | 配方详情 |
| `PUT /api/workflow/recipes/:id` | 保存配方并递增版本 |
| `POST /api/workflow/runs` | 创建 run，保存配方快照 |
| `GET /api/workflow/runs` | run 列表 |
| `GET /api/workflow/runs/:id` | run、名册和单元详情 |
| `POST /api/workflow/runs/:id/pause` | 暂停 |
| `POST /api/workflow/runs/:id/resume` | 续跑／配合提额 |
| `POST /api/workflow/runs/:id/abort` | 中止 |
| `POST /api/workflow/runs/:id/feedback` | 聚合反馈并生成下一版草案 |
| `POST /api/workflow/units/:uid/:action` | accept／reject／reroll／skip 人审 |

Web `/workflow` 负责配方与 run 入口，`/workflow/runs/:id` 展示名册 × 阶段网格、联系表与人审操作。

## 19.9 降级、限制与测试锚点

当前限制应作为调用契约的一部分：

- v1 没有可靠的升级子 Agent 产物自动回收；
- 文本评委不看像素，视觉质量靠人审；
- 预算是轻量调用估算，不是全成本账单；
- 重启复用数据库 attempt，不保证外部服务 exactly-once；
- 漂移检测只提示、不阻断、不持久；
- 配方与反馈草案需要用户确认，不能静默自改生产定义；
- 视频没有图像尺寸式校验。

测试源码覆盖采纳与锚点传播、重摇、人审、预算、熔断、暂停／中止和升级等路径。PostgreSQL 冒烟测试在没有 `WORKFLOW_PG_DSN` 时默认跳过；因此“测试文件存在”也不能推断真实 PG 已验证。本次环境无 Go 工具链，未执行任何测试。

修改本模块时至少同时检查：配方版本、run 快照、attempt 幂等键、锚点重建、状态乐观迁移、人审动作、预算恢复、前端网格与对应测试。
