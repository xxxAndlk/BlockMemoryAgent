# 17 长期记忆与决策轴

> 本章补充 2026-10 月后的长期记忆生命周期与用户决策多轴化。主线代码：`internal/agent/memory_*`、`decision_*`，`internal/store/long_term_memory.go`、`session_decisions.go`，迁移 `018`、`019`。
>
> 与旧章关系：06／10 中的画像、项目偏好、旧块记忆和早期决策账本仍有背景价值；本章所述 items/events、多轴替换和撤回语义以当前实现为准。

## 17.1 模块边界

这里有两套相关但不同的机制：

1. **长期记忆治理**：把跨会话的用户偏好、项目经验等视为有生命周期的条目，支持候选、激活、隔离、替换、撤回、恢复和审计。
2. **会话决策轴**：把当前会话中的用户指令按执行模式、素材、视角、验收等轴记录，解决“新指令只改一个维度，却误删其他约束”的问题。

旧块记忆是另一套历史机制。当前 `agent.block_memory_write_enabled: false`，不要把 `global_knowledge`、旧召回代码或 `blackboard_uptake` 当作本章长期记忆主链。

主要协作关系：

```text
真实用户消息 ──► 撤回识别／执行 ──► LongTermMemoryStore
                                      │
SessionEvolver ─► 候选生成 ─► 准入 ───┤
                                      ├─► long_term_memory_items（当前状态）
人工编辑／迁移 ───────────────────────┤
                                      └─► long_term_memory_events（只追加审计）

真实用户消息 ──► 决策识别 ──► session_decisions（axis + source_message_id）
                                    │
                                    └─► 分段预算注入 ReAct 尾部指令块
```

## 17.2 写入、撤回与装配入口

### 写入模式

`config/config.yaml` 的 `memory.write_mode` 控制 SessionEvolver 的自动写入：

| 模式 | 行为 |
|---|---|
| `off` | 不运行 SessionEvolver，不生成并晋升偏好／项目经验／经验技能候选 |
| `shadow` | 允许生成候选，但只写 `evolution_log` 供审计，不修改现行长期记忆文件／技能数据 |
| `enforce` | 通过确定性准入门后才写入现行记忆；不是模型说“值得记”就直接生效 |

当前默认是 `shadow`。准入关注长期意图、已验证、未被否决和可复用性，目的是阻止一次性任务参数、试验过程与失败半成品进入长期上下文。

### 撤回模式

`memory.retraction_mode` 当前为 `enforce`。它与 `write_mode` 解耦：即使自动写入为 `off` 或 `shadow`，真实用户消息中的明确撤回仍在当轮执行，避免旧污染因“影子模式”而永远无法移除。

`off` 是撤回服务故障时的紧急回滚口，不是常规隐私／治理策略。

### 装配与降级

`internal/bootstrap/memory_lifecycle_wire.go` 负责把生命周期服务、会话入口、存储和管理 API 接起来。PostgreSQL 不可用时可使用内存仓储，生命周期操作仍能工作，但**不具备同等重启持久性**；不能把“接口可用”写成“数据已持久保存”。

## 17.3 权威数据与状态机

### 两张表的分工

- `long_term_memory_items`：当前状态投影，保存条目内容、作用域、key、状态、revision、来源与墓碑相关信息。
- `long_term_memory_events`：只追加审计流，记录候选、状态变化、撤回、隔离、恢复及防复活判断等事件。

状态迁移带 revision 乐观锁；PostgreSQL 实现中状态更新与审计事件在同一事务内提交。管理面不提供物理删除端点，删除语义通过 `retracted` 与墓碑实现。

### 条目状态

| 状态 | 含义 | 是否进入现行注入视图 |
|---|---|---|
| `candidate` | 候选、疑似重复或需进一步治理 | 否 |
| `active` | 当前有效 | 是 |
| `quarantined` | 因歧义、污染或疑似问题被隔离 | 否 |
| `superseded` | 已被同 key 新条目替代 | 否 |
| `retracted` | 用户或人工治理撤回，保留墓碑 | 否 |

**只有 `active` 进入注入视图。** 候选、隔离、替换和撤回都不能继续以“现行记忆”身份影响模型。

### 作用域与覆盖

- 条目分全局与项目作用域。
- 项目键由工作目录规范化得到，避免同一路径因写法不同形成多个项目。
- 同一 `memory_key` 下，项目条目覆盖全局条目。
- 同 key 替换将旧条目标为 `superseded`，不是简单把两份矛盾内容一起注入。

## 17.4 撤回、隔离与恢复

撤回只从**真实用户消息入口**触发，模型或工具文本不能冒充用户撤令。支持的定位方式包括：

1. 明确条目 ID；
2. 精确文本；
3. 同 key 替换；
4. 匹配有歧义时先隔离，等待进一步确认。

定位不可靠时返回对账提示，不假报“已撤回”。这一约束同时保护用户意图与审计可信度。

恢复不是物理复活一行旧数据那么简单：恢复必须遵守状态迁移和 revision 检查，并保留事件。墓碑用于阻止相同内容在后续自动演化中重新出现。

### 防复活

- items／events 中保留的撤回墓碑用于判断历史否定。
- 相同 hash 或同 key 高相似候选只能落为 `candidate`。
- 对疑似复活记录 `resurrection_suspect`，而不是重新激活。

因此，`enforce` 也不意味着可以绕过用户的既往撤回。

## 17.5 旧 Markdown 迁移与人工编辑

迁移逻辑在 `memory_import.go` 等代码中，目标是把旧文件中的不同来源行转成有明确生命周期的数据，而不是全部激活：

| 旧行类型 | 迁移语义 |
|---|---|
| 人工维护行 | 可迁为 `active`，并标记为已验证来源 |
| 带时间戳的自动沉淀行 | 迁为 `quarantined`，等待治理 |
| 归档行 | 成为 `retracted` 墓碑，防止旧内容复活 |

人工对记忆文件做全量编辑时，`SyncHumanEdit` 对比并同步新增与撤回。这里不是把整份 Markdown 再盲写回数据库，而是把人工编辑转换为可审计的变化。

## 17.6 会话决策多轴模型

迁移 `018_session_decision_axes.sql` 为 `session_decisions` 增加 `axis` 与 `source_message_id` 等语义。同一轴上的新指令可替换旧行，不同轴的指令并存。

当前轴包括：

| 轴 | 例子 | 新指令的影响 |
|---|---|---|
| 执行模式 | “只回答，不要执行” | 只改变执行方式，不删除技术路线或验收标准 |
| 素材来源 | 指定图片／视频／文件来源 | 改素材约束，不自动改交付形式 |
| 动画方式 | 指定动画技术或运动方式 | 只替换动画轴 |
| 角色／参考资产 | 更换角色、形象、参考文件 | 可使依赖旧参考资产的审批失效 |
| 视角 | 正视、侧视、俯视等 | 保留其他制作约束 |
| 锚点审批 | 对锚点／参考方案的批准 | 独立于后续技术路线 |
| 关键姿态审批 | 对关键姿态的批准 | 参考资产变化后才按规则失效 |
| 验收标准 | 分辨率、数量、测试或质量门槛 | 不因“继续”而重置 |
| 交付形式 | 文件、网页、视频、代码等 | 只修改交付轴 |
| 无轴普通指令 | 普通任务说明 | 作为一般决策保留，不强塞进错误维度 |

关键解释规则：

- “继续”表示沿用既有路线，不新增一条路线。
- 对产物效果的反馈，不应自动否决整条技术路线。
- 路线变化不会隐式清除已存在的审批；参考资产变化才会使旧审批失效。
- 账本注入采用分段预算，优先保留各轴与最新指令，不再用一个整体尾部截断把早期关键约束全部切掉。

决策账本不是长期记忆：它服务于当前会话指令完整性，长期记忆服务于跨会话生命周期治理。

## 17.7 管理 API

当前长期记忆管理端点：

| 方法与路径 | 用途 |
|---|---|
| `GET /api/memory/items` | 查询条目及状态 |
| `GET /api/memory/items/:id` | 查看单条详情 |
| `GET /api/memory/items/:id/events` | 查看该条目的只追加事件 |
| `POST /api/memory/items/:id/retract` | 撤回并留下墓碑 |
| `POST /api/memory/items/:id/quarantine` | 隔离可疑条目 |
| `POST /api/memory/items/:id/restore` | 按状态与 revision 规则恢复 |

没有物理删除端点。实现位于 `internal/server/memory_admin.go`，Web `/memory` 是管理视图之一。

## 17.8 降级、限制与常见误读

- 内存仓储只能提供进程内语义，重启后持久性不同于 PostgreSQL。
- `shadow` 只约束自动写入，不关闭撤回。
- `candidate` 不是“稍弱的 active”，不会进入现行注入视图。
- 有管理页面不代表可以物理擦除审计；当前设计强调墓碑与事件。
- 自动评委／模型可生成候选或建议，但状态准入、撤回与迁移由确定性代码和存储约束保证。
- 旧画像／项目偏好文件、旧知识库和新长期记忆之间仍存在历史兼容路径，修改注入逻辑时要同时检查来源优先级与去重。
