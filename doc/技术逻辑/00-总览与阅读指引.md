## 0.1 这是什么系统

BlockMemoryAgent：Go 编写的多 Agent 编排系统（Go 1.25，基于 go-kratos/blades 的 ReAct 循环）。

一句话架构：**用户 → 会话（三档位）→ 顶层 Agent（fast=doc_assistant / daily=domain / cluster=meta）→ ReAct 循环 + 工具 → 子 Agent 递归派发（meta→domain→叶子，三层）→ mailbox 异步回传 → 看板/树/台账状态维护 → 事件流（SSE/TUI）→ 交付**。

三大支柱：

1. **ReAct 循环**（`internal/agent`）：LLM 生成 → 工具调用 → 结果回填 → 重复；状态全在 history 里（无状态 Agent 实例）。
2. **派发与生命周期**（`internal/domain/subagent`）：Dispatcher 是唯一调度器，管树/计数/心跳/暂停/失败分类/spec/看板/台账。
3. **记忆与存储**（`internal/domain/memory` + `internal/store` + PostgreSQL/pgvector/Redis）：事件流、块记忆（跨会话外脑）、共享记忆（会话内 KV/spec）、任务看板。

适配器两个：HTTP 服务端（`internal/server`，Web 前端消费）与 TUI（`internal/tui`，bubbletea）。

## 0.3 分层与包依赖（客观图）

由 `go list` 实测的 internal 包依赖（去第三方）：

```
main.go / cmd/*        → bootstrap, config, logging, server, tui
bootstrap              → agent, plugins(+mcpbridge), domain/{memory,subagent,tool,role},
                         embed, retriever, runtime, server, store, userprofile, skill,
                         board, dag, mailbox, project, logoutput, pkg/{config,prompts}
server                 → agent, domain/subagent, domain/tool, model, plugins, runtime,
                         store, dag, logger, server/eventkind
tui                    → agent, board, dag, orchestrator, domain/tool, server, logger
agent                  → board, domain/{orchestrator,role,tool}, mailbox, middleware, model,
                         project, skill, store, userprofile, logger, server/eventkind
domain/subagent        → agent, board, orchestrator, role, tool, mailbox, skill, project, logger
domain/memory          → agent（pipeline 面向 agent 的 MemoryPipeline 接口）
domain/tool            → config, project
domain/role            → model, tool, pkg/config
store                  → embed, orchestrator, pkg/{enums,types}
model                  → logger, pkg/config, pkg/types
plugins                → config, domain/tool, skill, plugins/{bundle,mcpbridge}
middleware / mailbox / board / soul / dag / logoutput / orchestrator / project  → 零 internal 依赖（叶子）
runtime                → board, config, mailbox, skill, soul
pkg/*                  → 只依赖 pkg/*（pkg/types → pkg/enums）
```

要点：

- `pkg/*` 不依赖 `internal/*`；`internal` 里无环（如 `agent ↔ domain/memory` 靠接口反转：memory 依赖 agent 声明的 `MemoryPipeline` 接口）。
- `agent` 包直接 import `store`/`userprofile`/`server/eventkind`（历史沿革），改这些包签名时注意 agent 是消费方。
- `bootstrap` 是唯一"全知"装配层：所有回调（treeFn/boardFn/liveFn/…）都在这里接线。

## 0.4 推荐代码阅读顺序

1. `main.go` → `internal/bootstrap/bootstrap.go`（Build 启动序，看谁 new 了谁）。
2. `internal/agent/agent.go`（Facade 接口，先看对外能力面）→ `internal/agent/service_react.go`（会话服务，从 CreateSession/Send 进入）。
3. `internal/agent/react_agent.go` + `react_types.go`（核心循环）。
4. `internal/domain/subagent/dispatcher.go`（派发核心；配合 `idle_pool.go`）。
5. `internal/domain/tool/registry.go` + `builtin.go`（工具与守卫）。
6. 外围按需：memory / model / store / server / plugins / tui / web。

## 0.5 全局术语表

| 术语 | 含义（代码锚点） |
|---|---|
| MetaAgent | cluster 档顶层 Agent，角色 ID=`meta`，实例 ID=sessionID；负责拆分派发与汇总 |
| DomainAgent | 领域执行者，角色 ID=`domain`（合成角色，实例名 `<领域名>领域Agent`）；daily 档顶层也是它 |
| 叶子助手 | 固定角色（code_assistant/ui_assistant/scout/light/…），只执行不再派发 |
| 档位 gear | `fast`(doc_assistant 直达) / `daily`(domain 顶层) / `cluster`(meta 全装)，会话级手动切换 |
| 思考强度 thinking | `off/low/medium/high`，会话级覆盖顶层 Agent |
| 热驻 hot resident | domain 完成后进 idle 槽保留上下文，可被 reuse_agent_id 复用 |
| 看板 board | 会话级任务计划/状态（write_plan / plan_execute 落板；TUI/Web 计划面板数据源） |
| 台账 ledger | Dispatcher 机器维护的派发状态流水，注入 Meta 上下文（task_ledger.go） |
| spec | WriteSpec 写的结构化任务规范（goal/acceptance/constraints/files/verify_levels/contract），派发前强制门 |
| 共享记忆 | 会话内 KV（WriteSharedMemory），派发时注入子 Agent 前缀；spec 是其固定槽位 |
| 块记忆 | 跨会话知识沉淀（global_knowledge 表 + 向量），子 Agent 完成时写入、派发时按目标召回 |
| 黑板 | 块记忆的 scope 检索模式（parent_id+task_domain 过滤，兄弟产出共享） |
| mailbox | 进程内异步消息（子→父回传、用户注入、跨 Agent 问答），有留痕 |
| worktree | git worktree 隔离派发（子 Agent 在副本工作，产出 patch 经 merge_worktree 合入） |
| 幽灵/哨兵错误 | `errPaused`/`errPartialReturn`/`errUnverified`/`errVerifyMissing`/`errSmokeFailed` 等 |
| 三层 Agent 树 | meta → domain → 叶子；`CanCall` 拒绝 domain→domain 平级 |
| 四态状态语义 | done / failed / cancelled / **delivered-unverified**（产出未验证，黄态） |

## 0.6 一次任务的全景数据流

（细节见第 14 章，这里是骨架）

1. **创建**：`POST /api/sessions`（或 TUI 输入）→ `ReactService.CreateSession` → 建会话记录（PG session_history + 内存 registry）→ 按 gear 选顶层角色 → 构造顶层 `ReActAgent`（meta/domain/doc_assistant）→ goroutine `runSession`。
2. **执行循环**：见第 02 章。上下文每轮 = 系统提示（冻结）+ 压缩视图 + 尾部动态段（时间/看板/空闲清单/台账/块记忆召回）。
3. **派发**：顶层调 `call_sub_agent(s)` → Dispatcher 校验（参数/spec/依赖门/同名/复用/限额）→ 建子 Agent（工具白名单/引擎/心跳）→ 注册树 + 看板 + 台账 → goroutine 跑。
4. **回传**：子 Agent 完成/失败 → `notify`（结构化失败标记 + 遗产清单 + 落盘摘要）→ 父 mailbox → 父下一轮 `drainMailbox` 注入 → 模型整合。
5. **沉淀**：子 Agent 结果 → factExtractor 提取 → 块记忆（向量）落库；失败 → salvage 打捞槽位 + 父通知。
6. **验收**：spec verify_levels 驱动冒烟/集成/运行时/视觉机器校验 + 验收条目计分；不达标反馈重试 1 轮；未验证三态化（黄）。
7. **事件流**：每一步经 `LiveEvent` → `ReactService.handleLiveEvent` → 事件落库（PG session_events / Redis 热写）+ SSE 推 Web / TUI 订阅。
8. **交付**：顶层无 tool_calls 且无未决子 → 终答 → 会话置 completed → 通知（webhook/浏览器）。

## 0.7 改动某处时先看哪一章

- 改 ReAct 循环行为（守卫/裁剪/提示词）→ 02。
- 改会话状态/HTTP 会话端点/澄清/档位 → 03（+ 09 路由）。
- 改派发/心跳/暂停恢复/失败语义/spec → 04。
- 加/改工具、守卫、沙箱 → 05。
- 改记忆召回/压缩/embedding → 06。
- 换模型/加 provider/思考强度 → 07。
- 加插件/MCP → 08。
- 改前端渲染或事件分类 → 13（+ 09 的 SSE 帧格式）。
- 改表结构/Redis key → 10（+ migrations）。
- 查"某机制还在不在/是死代码吗"（verifyloop、DAG 推进、soul 温度、广播邮箱…）→ 15.4 已退役机制清单。
