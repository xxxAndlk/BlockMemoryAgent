## 11.1 board 看板

会话级任务台账（`board/board.go`，743 行，**零持久化**）。

- `TaskStatus`：pending / in_progress / blocked / done / failed / **delivered-unverified**（与树 Unverified 对应）。
- `BoardStatus`：new/in_progress/done/failed/delivered——**纯派生**（recomputeStatusLocked），不直接赋值。
- `SubTask{ID,Title,Domain,Status,Assignee,Result,Constraint,Acceptance,DependsOn,UpdatedAt}`；`TaskBoard{mu, TopicID, Status, Tasks map, Order[]}`；`Manager{boards map[topicID]}`（Get/GetOrCreate/Remove）。
- 流程：`AddSubTask`（ID=`<topicID>_t<n>`，**按 Title 幂等**，新任务直接 in_progress）→ `SetPlan`（校验：ID 唯一 → 依赖已知 → 三色 DFS 环检测 → 已有任务**保留 Status/Result** 只更新 Domain/Acceptance——重提计划不抹进度）→ `DependsDone`（依赖门）→ `Assign` → `MarkDone/Failed/Unverified/Blocked`（走统一 transition + 重算板级）→ `TakeoverFrom`（迁旧 Domain 非 Done 任务，标题追加"（曾失败，由 X 接力完成）"，状态重置 pending，清 Assignee）→ `Snapshot`/`Brief(6)`（默认最多 6 条 + 接管提示段）。
- 读写方：写=subagent 的 write_plan/boardUpdate/boardAssign/派发与接力/终态三态映射；读=boardInjectingPipeline（meta 每轮注入，`Brief(6)`）、legacy 清单、HTTP board 端点。
- **坑**：只在内存（进程重启即丢）；Title 幂等静默返回旧对象；TakeoverFrom 改写标题；Brief 只 6 条（有意截断防膨胀）。

## 11.2 mailbox 邮箱

进程内异步消息总线（`mailbox/mailbox.go`，409 行）。**全进程唯一一个实例**（bootstrap.go:254），Dispatcher 与 ReactService 共享——"每 Agent 一个邮箱"的说法不成立，是同一 Mailbox 里以 agentID 为 key 的多个 inbox。

- `MessageType`：milestone / **dependency（保留未用）** / request / reply / info / escalate。
- `Message{ID("msg_HHMMSS_seq"), From, To, Type, Subject, Body, Payload, Priority, Status, CreatedAt, ReadAt, ReplyTo, ThreadID, FilesModified}`。
- `Mailbox{mu, inbox map[string][]*Message, bcast, closed map, seq, trace}`。
- 流程：`Send`（To 空或 "*" 走广播桶；closed 收件人 → `ErrRecipientClosed` 死信；**trace 锁外调用传拷贝**）→ `Peek`（不消费）/`Drain`（unread → read + ReadAt）/`Count` → `Purge`（**同时标记 closed**——被清空的 Agent 后续收信走死信）/`Reopen`（复活必需）。
- 消费侧翻译（react_agent）：escalate 加 `[升级]` 前缀；`drainMailbox` 对 `From!=user && Type=request` 分类 `peer_ask` 事件。
- 留痕：bootstrap 注入 trace——**异步 goroutine** 写 `agent_events`（type=mailbox）；跳过广播与 From=user/dispatcher。
- 线程配对（ReplyTo/ThreadID）纯透传，mailbox 不校验。
- **坑**：广播桶/Forward 生产无消费方（死代码）；Purge 后必须显式 Reopen；trace 异步可能丢/乱序；Drain 即已读。

## 11.3 orchestrator 实例树

Agent 实例的**权威元数据层**（`domain/orchestrator/tree.go`，479 行；持久化 `store/agent_tree_store.go`）。

- `Status`：Running/Done/Failed/Cancelled/Paused/Idle/Unverified。
- `Node{ID, SessionID, ParentID, RoleID, Name, Goal, Status, Domain, 时间戳, Error, Result}`；`Tree{mu, nodes map, 根, cancel funcs, store}`。
- 方法：`Register`（幂等）/`SetCancel`/`Finish`/`FinishUnverified`（终态 **no-op 幂等**）/`Pause`（仅 Running→Paused）/`Resume`（仅 Paused→Running）/`Idle`（Running→Idle）/`Wake`（Idle→Running）/`Reopen`（四终态→Running，清 Error/FinishedAt——复活返工入口）/`Cancel`（三态→Cancelled + 调 cancelFunc）/`StopRunning`（**只调 cancelFunc 不改状态不落盘**——停 LLM 但语义状态不变）/`LoadFromStore`（重启合并，**Idle 降级为 Done**）/`EndCurrentTopic`/`Snapshot`。
- persistNode：2s 超时 **best-effort 吞错误**。
- **坑**：
  1. `parseStatus`（agent_tree_store.go:120-136）**没有 unverified/delivered-unverified 分支** → 该状态落库重启读回 fallback 成 Running（round-trip 断裂，重启后出现"僵尸运行"）。
  2. cancelFunc 不持久化（重启后 Cancel 只做状态迁移）。
  3. Paused/Idle 仍可被 finishWithStatus 终结（不被终态守卫挡）。
  4. 运行期 Idle 是"热驻待复用"，与 LoadFromStore 的 Idle→Done 降级语义不同。

## 11.4 domain/role 角色系统

roles.yaml 的运行时唯一可信来源（registry.go 325 行 + loader 30 + model_tools 241 + tools 167）。

- `Get` 三分支：**meta**（合成 RoleDefinition；默认工具表 27 项，yaml `meta_agent.tools` 非空时**整体覆盖**——生产已收窄 40→22，去掉 HTTPGet，因其"永远优先被选中"压过需挂载的 web_search）；**domain**（提示词空用内置兜底；白名单含 call_sub_agent(s)/map_sub_agents/读写执行全套/escalate_gear）；**其他**（dynamic 先于 fixed）。
- `reservedRoleIDs`：meta/domain 禁动态注册；动态角色必须 `Type=Dynamic`（**禁止运行时创建新编排者**）且 SystemPrompt 非空。
- **CanCall**：meta/domain 可调 Fixed/Dynamic；**Meta→Domain 放行、Domain→Domain 拒绝**（防递归）；固定角色须把调用方列进 `Parents`（写错拼写即静默拒绝）。
- `CallableFixedRoles` 供 call_sub_agent 的 Description 动态生成。
- 模型工具（**角色级**）：`list_models` / `set_role_model`（45s 超时；目标排除 meta 与 lightweight）；**`set_agent_model`（实例级）不在此包，在 dispatcher.RegisterControlTool**——两者粒度不同别混。
- 角色工具：`create_role`（动态注册入口）/`list_roles`。
- **坑**：domain 提示词 Go 常量与 yaml 两处并存（改一处需同步）；真正闸门 roleToolGate 在 dispatcher（本包只提供静态白名单）。

## 11.6 dag 任务图

DAG 调度（dag.go 463 + runner 81 + store 41 + toposort 16）：按依赖拓扑序推进，每个 ready 任务经 `SessionLauncher` 派独立会话；简化 interval（仅 `Ns/Nm/Nh`）；HTTP 管理端点六条。

- `Scheduler{mu, dags, running, launcher, store, tick}`；`tick`（10s，bootstrap 注入）逐 DAG 判定 interval → Trigger + SaveDAG。
- **`MarkCompleted` 零调用方（repo-wide 验证）→ 下游任务永远不会放行、running 永不排空——当前 DAG 实际只跑"第一波 ready 任务"**（本组件最大未完成点）。
- dag.SessionLauncher 生产实现=SessionManager.LaunchSession；`dag_jobs` 表仅 Go DDL 建。

## 11.8 soul 人格

（soul.go 229 + classifier 53 + temperature 47）：`Persona{Name, Content}`；`Loader` 用 atomic.Pointer（RCU）持有当前人格；`Inject` 把人格拼为系统提示**前缀**（唯一生产用处：bootstrap → react_agent persona 注入）；`Name` 取 soul.md 首行（顶栏展示）。

- **classifier（任务分类）与 temperature（按任务调温）生产休眠**——无任何生产调用方；温度现由模型配置决定。
- RCU：Reload 对运行中 Agent 安全，但**已注入的提示词前缀不追溯更新**。

## 11.9 runtime 聚合器与 testserver

- **runtime.Runtime**（runtime.go 119）：打包 Boards/Mailbox/Skills/Soul/AgentCfg 供上层取用；`New` 先填默认实现再套 Options——**纯聚合无业务逻辑、不做生命周期管理**；若 bootstrap 漏注入某项会静默用默认件（排查时先确认各字段实际来源）。
