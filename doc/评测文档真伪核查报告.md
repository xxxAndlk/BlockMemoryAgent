### 改造 1 - 子 Agent 回传结构化协议（SubAgentResult）

**评测声称**：Mailbox 存自然语言 summary，MetaAgent 只能"读作文"做聚合。

**代码真相**：**PARTIAL**

**判定**：**真小缺口**。结构化通道已存在但未启用。父 Agent 确实能收到失败通知（NL 形式），不是"信息断链"。

### 改造 2 - MetaAgent 任务状态机 + 30% 失败聚合

**评测声称**：MetaAgent 无状态跟踪，无失败率判断，需 `taskTracker` + 30% 阈值硬聚合。

**代码真相**：**TRUE - 真缺口**

**判定**：**真缺口**。但评测方案的 "30% 失败率硬阈值" 是**任意数字**，无证据支撑。强制终止循环可能误杀可恢复任务（verifyloop 已能修复部分失败）。

**必要性**：**中**。建议保留 LLM 自主判断，仅补充：显式注入"当前各子任务状态摘要"到上下文，让 LLM 基于结构化信息决策，而非硬编码 30% 阈值。

### 3. 子任务状态摘要注入（改造 2 简化版）

**目标**：让 MetaAgent 在每轮 LLM 调用前看到"当前各子任务状态汇总"，而非依赖 LLM 从散乱 NL mailbox 文本中自行提取。无 30% 硬阈值，LLM 自主决策。

**文件**：`backend/internal/agent/react_agent.go`

**设计**：

1. 在 `RunWithHistory`（`react_agent.go:182-369`）作用域内新增状态追踪：

   ```go
   type subTaskStatus struct {
       subAgentID string
       role       string
       status     string // "success" | "timeout" | "failed" | "running"
       lastBody   string // 截断前 200 rune
   }
   taskStatuses map[string]*subTaskStatus // key: subAgentID
   ```

   通过 `call_sub_agent` 工具返回或 `pendingChecker` 获取已派发子 Agent ID 与 role 列表，初始化为 `running`。

2. 在 mailbox drain 处（`react_agent.go:274` 附近，`mailboxMessageToReact` 调用前后），按 `message.Sender`（或对应字段）匹配 `taskStatuses`，根据 Body 文本分类：
   - 含 "超时" 或 "已终止" -> `timeout`
   - 含 "失败" 或 "FAIL" -> `failed`
   - 否则 -> `success`

   NL 字符串匹配基于 `formatSubAgentFailure`（`dispatcher.go:634`）已控文本，可精确匹配。

3. 在 `summarizeWindow` 或 system prompt 注入前，若 `taskStatuses` 非空，追加一段 system context：

   ```
   [子任务状态汇总]
   - sub_a (code_assistant): 成功
   - sub_b (test_assistant): 超时已终止
   - sub_c (domain): 运行中
   当前共 3 个子任务，1 个失败，1 个运行中。
   ```

   格式简洁，让 LLM 基于结构化汇总判断是否继续派发、是否向用户报告部分失败。

4. **不**引入硬阈值终止逻辑，**不**修改 `maxIter=50`，**不**改动 `pendingChecker`。

**不做**：不实施改造 1 的 `SubAgentResult` 结构化协议（dispatcher 不写 Payload）。NL 文本匹配足够；未来若需更精确可再升级。

## 追加核查：3 项生产级提案（P0/P1/P2）

### 提案 1 - 原子化工作区快照与自动回滚（P0）

**评测声称**：WriteFile/RunCommand 直接改盘，错误变更只能靠 git revert（Agent 主动）。应在 WriteFile 前自动创建 `.snapshots/{session_id}_{timestamp}.tar.gz`，verifyloop FAIL 或 call_sub_agent 超时触发 `restore_snapshot`。

**代码真相**：**TRUE - 真缺口**
- `internal/domain/tool/executor.go:214` `writeFile` 直接 `os.WriteFile`，无备份。
- grep `snapshot|rollback|restore|backup` 在 `internal/domain/tool/` 与 `internal/domain/subagent/` **0 命中**。
- `internal/store/snapshot_store.go:27` 存的是 `AgentSnapshot`（agent 记忆状态），非文件系统。
- `workspace/` 仅有用户产物，无 `.snapshots/`。
- dispatcher FAIL 路径（`dispatcher.go:500-503`）仅 `notify` 父 mailbox，无 restore。

**判定**：**真缺口，但方案设计有风险**

方案问题：
1. **每次 WriteFile 创建 tar.gz 过重** - WriteFile 频繁，snapshot 开销可能超过工具本身。应改为"每 goal 开始时全量 snapshot"或"每 N 次 WriteFile 增量 snapshot"。
2. **verifyloop FAIL 自动 restore 危险** - FAIL 不总意味着代码坏，可能是测试环境问题（依赖缺失/网络/超时）。自动 restore 会丢弃有效工作。应仅 timeout 触发，或交 LLM 决策。
3. **workspace/ 是否 git 仓库未明确** - 若已纳入 git，`git stash` + `git checkout` 比 tar.gz 更轻、更可靠。

**必要性**：**中**。推荐降级方案：
- 在 `tool/executor.go` 加 `snapshotGoalStart(ctx, sessionID, goalID)` 钩子，每 goal 开始时全量 tar.gz 一次（非每 WriteFile）。
- 加 `RestoreSnapshot` 工具暴露给 MetaAgent，由 LLM 决策是否回滚（而非自动）。
- 仅 `call_sub_agent` 超时且无 partial 输出时才自动 restore。

### 提案 2 - 跨 Goroutine 分布式追踪 OpenTelemetry（P1）

**评测声称**：session_logs 记录单次 LLM I/O，但 MetaAgent 派发子 Agent 的 goroutine 间无 Trace ID 关联。应初始化 OTLP Exporter，Root Span -> dispatcher -> Child Span，暴露 `/api/sessions/{id}/trace` 返回 Jaeger JSON。

**代码真相**：**TRUE - 真缺口**
- grep `go.opentelemetry|otel|trace.Span|traceparent` 全 `backend/` **0 命中**。
- session_logs schema（`internal/store/schema.go:67-82`）列：`id, session_id, agent, level, phase, message, prompt, response, input_tokens, output_tokens, model, latency_ms, created_at, meta_json`。**无 trace_id/span_id/parent_id**，仅 `session_id` + 自由文本 `agent` 字段。
- `dispatcher.go:460-463` 子 Agent ctx 是 `context.Background()` + `tool.WithSessionID`，**不携带 parent span/关联 ID**。parent ID 仅用于格式化 `subAgentID = parentID/roleID-seq`（line 449）。

**判定**：**真缺口，但 OTel 过重**

方案问题：
1. **OTel 依赖重** - 引入 `go.opentelemetry.io/otel` + OTLP exporter，增加二进制体积与启动复杂度。单节点部署不一定需要 Jaeger。
2. **sub_agent_id 已编码父子关系** - `parentID/roleID-seq` 格式天然可解析父子链。session_logs 加 `parent_sub_agent_id` 列 + 前端树状展示，即可解决"哪个子 Agent 耗时飙升"排障，无需 OTel。
3. **/api/sessions/{id}/trace 端点** - 可基于 session_logs + sub_agent_id 关系直接构造调用树 JSON，无需 Jaeger 格式。

**必要性**：**中低**。推荐降级方案：
- `schema.go` session_logs 加 `parent_sub_agent_id VARCHAR` + `dispatch_seq INT` 列。
- `dispatcher.go` `notify`/`Dispatch` 时将 `parentID` 写入 ctx，session_logger 读取并落库。
- `/api/sessions/{id}/trace` 端点返回基于 session_logs 的调用树 JSON（非 Jaeger 格式）。
- 仅在多节点部署或需对接外部可观测性平台时再升级 OTel。

### 提案 3 - 硬 Token 经济学预算（P2）

**评测声称**：maxIter=50 防死循环但无 Token 上限。"优化整个项目"可能烧百万 Token 才被 maxIter 截断。应在 `config.yaml` 加 `agent.token_budget_per_goal: 100000`，`RunWithHistory` 每次调用后累加 `usage.TotalTokens`，超预算强制终止。

**代码真相**：**TRUE - 真缺口（但被部分缓解）**
- `react_agent.go:79` `maxIter: 50` 默认；循环 guard 在 line 205。
- `react_agent.go:240-246` 每次 LLM 调用后 emit `LiveEventTokenUsage{InputTokens, OutputTokens}`，**仅 emit 不累加**。
- `service_react.go:846-848` `LiveEventTokenUsage` 仅写 `store.addEvent(..., "token_usage", ...)` 供前端展示，无 cap 检查。
- 无 `TokenBudget`/`token_budget` 配置字段。
- **部分缓解**：`config.go:156` `ContextExplodeHardLimit` 限制单次输入 token；输出由模型 max_tokens 限。所以总 token ≤ 50 * (input_cap + output_cap)。**非完全无界**，但 50 * cap 仍可能很高。

**判定**：**真缺口，方案合理且低复杂度**

方案评估：
1. **实现简单** - `RunWithHistory` 加 `cumulativeTokens int` 变量，每轮加 `resp.Message.TokenUsage.TotalTokens`，超 `a.tokenBudget` 则 break 并返回"Token 预算耗尽"消息。约 15 行代码。
2. **配置清晰** - `config.yaml` 加 `agent.token_budget_per_goal: 100000`，默认 0（不限）。
3. **无副作用** - 不影响正常流程，仅兜底极端 case。

**必要性**：**高**。推荐直接落地：
- `config.go` `AgentConfig` 加 `TokenBudgetPerGoal int `yaml:"token_budget_per_goal"` // 0 = 不限`。
- `react_agent.go` `ReActAgent` 加 `tokenBudget int` 字段，`RunWithHistory` 加 `cumulativeTokens` 累加 + 超限 break。
- 超限时返回 `[系统] Token 预算耗尽（已用 {cumulativeTokens} / {budget}）。已完成部分：{lastAnswer}`。
- 配合 `LiveEventTokenUsage` 事件，前端可实时显示预算条。

**状态**：**已写入文档落地**（2026-07-28）。`doc/TODO.md` #8 记录完整实施步骤（含 file:line 改动点 + 验证命令）；`doc/项目说明.md` §4.6 / §6 config 列表 / §设计要点 #17 三处文档化机制、配置字段、设计动机。代码尚未编码，待后续按 TODO #8 实施。
