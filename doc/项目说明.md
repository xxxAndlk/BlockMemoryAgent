# BlockMemoryAgent 项目说明

> 从零开始理解本项目的导览文档。基于当前代码实际状态（已迁移到 go-kratos Blades）编写。

## 1. 这是什么

BlockMemoryAgent 是一个 **Go 多 Agent 编排系统**，核心理念：用"单一 ReAct 主循环 + 异步子 Agent 工具分发"解决长上下文遗忘和 Skill 爆炸问题。

- **ReAct 主循环**：MetaAgent 运行单一 LLM → 工具循环；层级关系通过 `call_sub_agent` 工具递归涌现
- **异步子 Agent 分发**：`call_sub_agent` 起 goroutine，结果通过 `Mailbox` 异步回灌父 Agent
- **两段事件流记忆**：主 Agent 事件 + 子 Agent 事件，无压缩 / 无 RAG / 无向量检索
- **三层存储**：PostgreSQL（会话历史/事件）+ Redis（工作区热缓存）+ pgvector（保留，未来可接 RAG）
- **双入口**：HTTP Web UI（Vue SPA）+ bubbletea TUI
- **leaf 执行**：go-kratos Blades（`ModelProvider` + 原生 function-calling）
- **上层编排**：自研 ReAct 循环 + 工具注册表（不依赖图状态机）

一句话定位：不是 Agent 脚手架，而是一套让 AI 拥有"清晰记忆"和"专注力"的认知架构。

## 4. 核心架构

### 4.1 ReAct 主循环与异步子 Agent

```
User
 │
 ▼
MetaAgent (ReAct loop)
 │  LLM.Generate(system prompt + history + tools)
 │  ├─ 工具调用：ReadFile / WriteFile / RunCommand / ...
 │  └─ call_sub_agent(role_id, task) ──► goroutine
 │                                      │
 ▼                                      ▼
回答用户                        DomainAgent / fixed role (ReAct loop)
                                    │
                                    ├─ 工具调用
                                    └─ call_sub_agent(...) ──► Assistant
                                                               │
                                                               └─ 工具调用
```

**关键设计**：
- **单一主循环**：`internal/agent/react_agent.go` 中 `ReActAgent.RunWithHistory` 实现 LLM → 工具 → 结果 → 循环，直到纯文本回答。
- **层级即调用栈**：MetaAgent 调 `call_sub_agent(domain_agent, ...)`，DomainAgent 再调 `call_sub_agent(code_assistant, ...)`；Go 调用栈本身就是层级关系，无需 `CallStack`/`SessionBlock`/`NextAction` 状态机。
- **异步分发**：`internal/domain/subagent/dispatcher.go` 中 `call_sub_agent` 工具起 goroutine 跑子 Agent，立即返回 `sub_agent_id`；子 Agent 完成后把摘要推 `Mailbox`。
- **Mailbox 轮询**：父 Agent 每轮 LLM 前 `Drain` 自己的邮箱，把子 Agent 摘要注入上下文。
- **角色权限**：`domain/role.Registry.CanCall` (`pkg/config/role_config.go`) 限制谁能调谁；`roles.yaml` 的 `can_be_called` / `parents` 字段直接映射工具可用性。
- **事件流记忆**：`domain/memory.Pipeline` 记录 `tool_call` / `call_sub_agent` / `sub_agent_summary` / `answer` 事件；`Assemble` 注入最近 N 条作为上下文。

### 4.2 执行引擎（已重构为 ReAct）

> 历史：`internal/graph/ThreeLayerGraph` 四层状态机已删除。原 `MetaAgentNode` / `DomainAgentNode` / `SubDomainAgentNode` / `AssistantNode` / `router.go` / `role_factory.go` 等代码已移除，逻辑折叠进 ReAct 主循环 + `call_sub_agent` 工具。

`internal/agent/react_agent.go`：

```go
for i := 0; i < maxIter; i++ {
    messages := memory.Assemble(role, agentID, history)
    resp := llm.Generate(ctx, system, messages, tools.Schema())
    history = append(history, assistantMessage(resp))

    if resp has no tool calls {
        memory.Write(answer)
        return result
    }

    for _, tc := range resp.ToolCalls {
        result := tools.Dispatch(ctx, tc)
        memory.Write(tool_call)
        history = append(history, toolResultMessage(result))
    }
}
```

### 4.2 图执行引擎 (`internal/graph/three_layer_graph.go`)

`ThreeLayerGraph.Invoke()` 是状态机循环（max 200 步）：

```
current = "MetaAgent"
loop:
  node = resolveNode(current)           # 静态节点 or 动态实例节点
  state = node.Invoke(ctx, state)       # 节点返回新状态 + NextAction
  next = determineNext(current, state)  # 根据 NextAction 路由
  if NextAction == Finish: return
  current = next
```

**NextAction 控制信号** (`pkg/types/types.go:106`)：
- `Continue` — 回到上层（Assistant→DomainAgent→MetaAgent）
- `Switch` — 跳到 `TargetRoleID`
- `Escalate` — 进 `EscalationHandler` 仲裁
- `Finish` — 进 `sinkerNode` 终止

**节点类型**：
- 静态：`MetaAgentNode` / `EscalationHandlerNode` / `sinkerNode`
- 动态：`DomainAgentNode` / `SubDomainAgentNode` / `AssistantNode`（按实例 ID 解析，`resolveInstanceNode` `:224`）

### 4.3 Leaf 执行：Blades 工具循环 (`internal/domain/tool/`)

ReActAgent 直接使用 Blades 原生 function-calling：

```go
req := &blades.ModelRequest{
    Instruction: blades.SystemMessage(system),
    Messages:    history,
    Tools:       toolRegistry.Schema(),
}
resp, _ := llm.Generate(ctx, req)
```

`domain/tool.Registry.Schema()` 用 `tools.NewFunc` 为每个内置工具生成 JSON schema；`Registry.Dispatch` 通过名称查找并执行工具，复用 `Executor` 沙箱实现。

**11 个内置工具** (`internal/domain/tool/builtin.go`)：
- 文件/命令：`ReadFile` / `WriteFile` / `ListDir` / `RunCommand` / `SearchInFiles`
- HTTP：`HTTPGet` / `HTTPPost`
- Git：`GitDiff` / `GitStatus` / `GitLog` / `GitBlame`

子 Agent 工具 `call_sub_agent` 由 `domain/subagent.Dispatcher` 注册到同一注册表，实现任意深度递归。

**Mock 路径**：`ReactService.SetModelProvider` 支持注入 mock `blades.ModelProvider`；生产环境通过 `model.ModelFactory.GetBladesProvider` 获取真实 provider。启动期 `VerifyConnectivity` 会校验 LLM 连通性。

### 4.4 记忆系统 (`internal/domain/memory/`)

ReAct 架构采用**两段事件流**，不再使用 4 阶段管线：

| 阶段 | 文件 | 职责 |
|---|---|---|
| Write | `pipeline.go` | 追加 `MemoryEvent` 到 agent 事件流，可选持久化 |
| Assemble | `pipeline.go` | 注入最近 N 条事件作为系统上下文 |

**事件类型**：
- `tool_call` — 工具名、输入、输出
- `call_sub_agent` — 调用了哪个子 Agent、任务摘要
- `sub_agent_summary` — 子 Agent 完成摘要（来自 Mailbox）
- `answer` — 最终用户回答

**Legacy 保留**：`internal/memory/write.go` 仍负责 Episode 持久化，但已不在 ReAct 主循环热路径上。`compress.go` / `search.go` / `assembler.go` / `snapshot.go` / `callback.go` / `block_vector.go` / `workspace_adapter.go` 已删除。

**启动期维度校验**：`ValidateEmbeddingDimension` 校验 `global_knowledge.embedding` 列维度与配置一致，不一致 `log.Fatalf`（避免维度不匹配导致 SaveKnowledge 静默失败）。pgvector 表保留，未来可重新接入 RAG。

### 4.5 运行时聚合 (`internal/runtime/runtime.go`)

单一 `Runtime` 结构，进程级共享，注入到 graph 节点：

```go
type Runtime struct {
    Boards   *board.Manager      // 任务看板（MetaAgent 建，所有 Agent 观察全局状态）
    Mailbox  *mailbox.Mailbox    // 跨 Agent 消息（广播 + 定向转发）
    Skills   *skill.Registry     // Skill 池 + 按领域装配子集
    Soul     *soul.Loader        // 人格 (soul.md) + 温度策略
    Watchdog *watchdog.Watchdog  // 上下文长度看门狗
}
```

- **Board** (`internal/board/`)：MetaAgent 在 `handleInitial` 创建 `TaskBoard`，顶层子任务 = 推断的领域名。Agent `MarkDone`/`MarkFailed`
- **Mailbox** (`internal/mailbox/`)：跨 Agent 事件。`processMailbox` 处理广播桶并按领域扇出；`meta_sync.go` 在块完成时主动向其他活跃块发 `MsgInfo`，Domain/SubDomain Agent 启动时通过 `applyMailboxToBlock` 消费并注入块级 `MetaMemory`。
- **Skill** (`internal/skill/`)：`Pool` → `FilterByDomain` → LLM `AssembleSet`(≤8) → `Registry.Bind(agent)`；只把子集 brief 注入 assistant system prompt
- **Soul** (`internal/soul/`)：`soul.md` 人格注入 + 按任务类型选温度（路由 0 / 代码 0.15 / 创意 0.8）
- **Watchdog** (`internal/watchdog/`)：每轮 `MetaAgentNode.Invoke` 顶部 `runWatchdog` 评估上下文规模，超软阈值建议压缩

## 5. 启动流程

`backend/main.go` 仅做 flag 解析、文件日志、HTTP 监听与优雅关闭；所有依赖装配委托 `internal/testserver.BuildHandler`（生产二进制与集成测试共用同一份 wiring）。`BuildHandler` 内部步骤：

```
1. flag 解析 (-config -roles -env -soul -skills)
2. config.LoadEnvFile(.env) → config.Load(config.yaml)
3. store.NewPostgresStore(dsn)   # 失败则启动失败并明确报错
   store.NewRedisStore(addr,...)  # 同上
   store.EnsureSessionHistorySchema      # 幂等自动建 session_history
   store.EnsureSessionEventsSchema       # 幂等自动建 session_events
   store.EnsureInitialMemorySchema       # 幂等自动建 001 记忆/知识表 + step_count 列
   # 注：005 session_logs 与 006 meta_memory 列不在自动迁移覆盖内，需按顺序应用 migrations/*.sql；
   #     004_memory_write_failures.sql 为历史遗留死信表。
4. pkgconfig.LoadRoleConfig(roles.yaml)
5. model.NewModelFactory(roleCfg).WarmUp(ctx)  # 预热 meta+domain 模型
6. graph.NewRoleRegistry + NewRoleFactory
7. skill.LoadFromYAML(skills.yaml)  # 失败则启动失败
8. runtime.New(soulPath, skillPool)
9. graph.NewMetaAgentNode + NewEscalationHandlerNode + sinkerNode
   builder.SetModelFactory/SetRuntime/AddNode → Build()
10. server.NewSessionManager(graph, registry)
    sessionMgr.RestoreSessions(ctx, 50)  # 从 session_history 恢复历史
11. memory.NewSnapshotManager(redis, pg)  # 快照管理器
12. server.NewAPIHandler 注入各依赖
13. mux 注册路由 → http.ListenAndServe(:10010)
14. 等待 SIGINT/SIGTERM → 关闭
```

**严格启动原则**：配置文件（config/roles/env/soul/skills）缺失，或 PostgreSQL / Redis / LLM 后端不可达，服务器启动失败并明确报错。所有基础设施必须在启动前可用。

## 6. 配置文件

### `config/config.yaml` — 基础设施
- `postgres.dsn` / `pgvector.{enabled,dimensions,index_type}` / `redis.{addr,password,db,snapshot_ttl_days}`
- `http.addr`（默认 `:10010`）
- `memory.{write_batch_size,snapshot_interval}`
- `agent.{tool_call_max_rounds,retry_count,context_window,stall_steps,max_repeat_fingerprint,session_timeout_min}`
- `agent.{snapshot_summary_count,snapshot_open_issue_threshold,summary_max_runes,fact_max_sentences,compress_importance_threshold,compress_age_hours}`
- `plugins.{mcp,rag,computer_use}.enabled`（P3-5）：插件开关，默认关闭

### `config/roles.yaml` — 角色定义与 Embedding
- `meta_agent`：MetaAgent 模型 + system_prompt + `max_blocks`(10) + `summary_interval`(5)
- `domain_agent`：所有 DomainAgent 共用模型
- `lightweight_model`：轻量模型（历史总结、检索 query 改写等）
- `embed`：文本嵌入模型配置（已从 `config.yaml` 迁移到此处）
  - `provider: pseudo`（默认，字符哈希，零外部依赖）
  - `provider: openai`（OpenAI 兼容端点，如 text-embedding-3-small）
  - `provider: local`（本地 ollama / xinference 等 OpenAI 兼容服务）
  - `embed.model` 向量维度需与 `pgvector.dimensions` 一致
- `fixed_roles[]`：固定助手（code_assistant/ui_assistant/test_assistant/doc_assistant/prompt_reviewer），每个含独立 `model_config` + `can_be_called` + `skills` + `parents`
- `dynamic_templates[]`：LLM 动态创建角色时的模板（domain_template / assistant_template）
  - 可为每个模板独立配置 `model_config`（P3-4）；未配置时动态创建的角色回退到 `domain_agent` 模型
  - `assistant_template` 默认与 DomainAgent 共用模型；如需临时助手使用独立模型，取消 `model_config` 注释并填写

**`model_config.provider` 取值与协议映射**：

三种 provider 分别使用对应原生 SDK/协议，不再统一转成 OpenAI 兼容端点：

| provider | 协议/SDK | 默认端点 | 适用后端 |
|---|---|---|---|
| `openai`（或留空） | OpenAI 兼容协议，`blades/contrib/openai` | `https://api.openai.com/v1` | OpenAI、DeepSeek、Kimi、豆包/火山方舟、Azure OpenAI 兼容端点等 |
| `ollama` | Ollama 原生 `/api/chat`，Ollama Go SDK | `http://localhost:11434` | 本地 ollama |
| `anthropic` | Anthropic 原生 Messages API，Anthropic Go SDK | `https://api.anthropic.com` | Claude 系列 |

因此：
- OpenAI 兼容后端统一配置 `provider: openai`。
- Claude 配置 `provider: anthropic`，`base_url` 指向 Anthropic 原生端点。
- 本地 ollama 配置 `provider: ollama`，默认无需 API Key。

### `config/skills.yaml` — Skill 池（可选）
每个 Skill：`skill_id` / `name` / `description` / `domain`(逗号分隔, `*` 通配) / `tool_ref` / `tags`。DomainAgent 按 domain 筛子集。

### `config/soul.md` — 人格（可选）
文本文件，`Soul.Inject(prompt)` 在 LLM 调用前注入。缺失非致命。

### `.env`
`OPENAI_API_KEY` / `OPENAI_BASE_URL` / `POSTGRES_DSN` / `REDIS_ADDR` / `REDIS_PASSWORD` / `HTTP_ADDR`

## 7. 运行方式

```bash
# 1. 起 PG + Redis
docker compose -f docker/docker-compose.yml up -d

# 2. 应用数据库迁移（按顺序应用 migrations/*.sql 中所有文件）
for f in migrations/*.sql; do psql "$POSTGRES_DSN" -f "$f"; done
# 注：BuildHandler 启动时幂等自动建 session_history/session_events/001 记忆表，
#     但 005 session_logs 与 006 meta_memory 列不在自动迁移覆盖内，必须手动应用。

# 3. 配 .env
cp .env.example .env  # 填 OPENAI_API_KEY / POSTGRES_DSN / REDIS_ADDR

# 4. 构建 web（首次）
cd web && pnpm install && pnpm build   # 产物到 web/dist/

# 5. 启动 HTTP 服务（主入口）
cd backend && go run .

# 6. 其他入口
go run ./backend/cmd/demo         # CLI 三层流演示
go run ./backend/cmd/tui          # bubbletea TUI
go run ./backend/cmd/memory-console  # 记忆检查
```

## 9. 数据模型（核心类型 `pkg/types/`）

- `RoleDefinition` — 配置层角色（id/name/type/system_prompt/skills/model_config/can_be_called/parents）
- `RoleInstance` — 运行时实例（id/role_def_id/session_id/domain/status/parent_id/children）
- `RoleType` — `meta`/`domain`/`subdomain`/`fixed`/`dynamic`
- `ThreeLayerState` — 图全局状态（SessionID/ActiveBlocks/CurrentBlockID/CallStack/RoleInstances/NextAction）
- `SessionBlock` — 会话块（domain/goal/agents/events/task_results/subdomain_*）
- `Episode` — 情节记录（action/observation/facts/importance/topic_bound/tool_calls）
- `AgentOutput` — Agent 公开输出（summary/data_refs/known_issues/validated）
- `TokenBudget` — 上下文预算（SystemRole/TopicGlobal/SharedState/GlobalKB/PrivateMemory/TaskQuery/Reserve），按 `agent.context_window` 比例动态分配
- `CompressionLevel` — Raw/Standard
- `RelevanceScore` — SemanticSim/EntityOverlap/TemporalDecay/CausalChain/FinalScore

## 10. 关键设计决策

1. **Blades 仅在 leaf**：上层 graph 状态机自研，因为 Blades 的 Flow/Graph 抽象无法表达 CallStack/SessionBlock/Escalate 四层嵌套语义。Blades 负责"单 Agent + 工具循环"这块通用能力。

2. **记忆分两层**：Blades `Session`（in-memory）管叶子 ReAct 短上下文；自研 4 阶段管线管长期记忆（PG/Redis/pgvector）。Episode 存储按设计文档简化为 2 级压缩（Raw/Standard），由 `compression_level` 列区分。

3. **会话块隔离**：每个 DomainAgent 一个 `SessionBlock`，上下文不串。这是"专注力"的核心——单个 Agent 只看自己领域的记忆，不被其他领域污染。

4. **跨块记忆同步（R7/R8）**：隔离不等于失忆。块完成时通过 `Mailbox` 主动通知其他活跃块；新块创建 / Agent 启动时自动继承 `state.MetaMemory`；`collectBlockResult` 更新会话级 MetaMemory 后同步到所有活跃块。实现"块内聚焦、块间可见"的折中。

5. **完成门控**：当 LLM 在最终输出中声称已写入文件（如"已写"/"created"/"saved"），但工具结果中没有成功的 `WriteFile` 时，返回 `Error: "missing WriteFile result"`，由上层触发重试；不再使用 `"[失败:...]"` 魔法字符串前缀做控制流。

6. **串行派发助手**：`dispatchAssistantsSerial`（`domain_agent.go:224`）——子任务常有依赖（"启动游戏"依赖"写代码"），并行会导致后续任务找不到前置产物。串行虽慢但成功率高。

7. **严格启动**：`config.yaml` / `roles.yaml` / `.env` / `soul.md` / `skills.yaml` 任一配置文件缺失，或 PostgreSQL / Redis / LLM 后端不可达，启动即失败并明确报告缺失/不可达项。不再支持零配置降级启动。

8. **SSE 实时性**：`ProgressCallback` 把 graph 每步（思考/意图/工具调用/token）实时推给 Web/TUI，`server/tui_broadcaster.go` 镜像到 SSE 订阅者。

9. **5 路径路由瘦身**（`router.go`）：80% 简单任务（纯 QA / 单工具 / 单领域）不进入四层编排。规则层零 LLM 成本覆盖 60%+，LLM 兜底用轻量模型，安全兜底 `RouteCreateDomain` 保持原有复杂任务行为零回归。

10. **SubDomain 自适应**：`shouldSplitToSubDomains` 从恒 `false` 改为读 `state.EnableSubdomain` + `detectSubdomainBoundaries`（规则 + 可选 LLM），仅 `RouteFullFourLayer` 启用第四层，避免单领域任务不必要的 overhead。

11. **Plan-and-Execute + Self-Reflection**（`plan.go`，feature flag 默认关）：DomainAgent 多任务时调重量模型生成 `ExecutionPlan`（步骤列表 + tool_hint），按步骤顺序派发助手，支持断点续行（`PendingGoals`/`MarkDone`）；`CommonExecuteAssistantTask` 内置 `reflectOnResult` 轻量模型评估，不达标带反馈重试一次（仅一次防死循环）。

12. **死循环防护**：多层渐进告警，LLM 调用追踪器（`llm_tracker.go`）统一覆盖超时/慢速模式/Token 统计，按天分割日志。

> 注：原决策"DomainAgent 归档复用"（`store/domain_archive.go`）已在 P1-1/P0-5 删除，合并为单一块记忆机制。

13. **默认关闭的机制为预留扩展**：SubDomainAgent（`full_four_layer`）、Plan-and-Execute（`plan_enabled`）、Self-Reflection（`reflection_enabled`）、DAG 调度（`dag_enabled`）、Board/Watchdog/CmdQueue 等当前默认关闭或仅占位，代码保留是因为它们对应后续能力（跨子领域并行、计划执行、定时任务、Agent 间协作），并非当前主干的必需路径。启动时不激活这些机制不会影响核心 MetaAgent → DomainAgent → Assistant 流程。
    - 例外：`Mailbox` 虽由 `Runtime` 初始化，但当前已被 `meta_sync.go` 用于跨块结果通知（R7）；`MetaMemory` 跨块注入（R8）也已默认启用。

## 15. 常见问题

**Q: 没有 API Key 能跑吗？**
不能。启动时会校验 LLM 连通性，无 key 或后端不可达会启动失败。需要配置有效的 OPENAI_API_KEY 与 OPENAI_BASE_URL。

**Q: 必须装 PostgreSQL + Redis 吗？**
必须。两者缺失会导致启动失败。请通过 docker compose 启动并应用 migrations 后再运行服务。

**Q: Web UI 怎么构建？**
`cd web && pnpm install && pnpm build`，产物到 `web/dist/`，`main.go` 直接 serve。开发模式可 `pnpm dev` 起独立 Vite 服务，API 代理到 `:10010`。

**Q: 怎么加新助手角色？**
在 `config/roles.yaml` 的 `fixed_roles[]` 加一项，设 `type: fixed` + `model_config` + `system_prompt` + `can_be_called: true`。重启生效。

**Q: 怎么加新工具？**
在 `internal/graph/blades_tools.go` 加 input struct + `tools.NewFunc` 包装，handler 内调 `ToolExecutor` 新方法（在 `tool_executor.go` 实现）。

**Q: 向量模型怎么配置？**
在 `config/roles.yaml` 的 `embed` 段配置（已从 `config.yaml` 迁移）：

```yaml
embed:
  provider: pseudo          # pseudo（默认）| openai | local
  model: ""                 # openai/local 时填写，如 text-embedding-3-small、bge-m3、doubao-embedding
  api_key: ${EMBEDDING_API_KEY:""}
  base_url: ${EMBEDDING_BASE_URL:""}
  batch_size: 1
```

- `provider: pseudo` 为字符哈希，零外部依赖，适合测试/开发。
- `provider: openai` 调用 OpenAI 兼容 `/v1/embeddings`，适用于 OpenAI、DeepSeek、豆包/火山方舟等。
- `provider: local` 同样走 OpenAI 兼容协议，用于 ollama、xinference 等本地服务。
- 向量维度必须与 `pgvector.dimensions` 一致。

豆包 Embedding 示例：

```yaml
embed:
  provider: openai
  model: doubao-embedding        # 你在方舟开通的 Embedding 模型名
  api_key: ${EMBEDDING_API_KEY}
  base_url: https://ark.cn-beijing.volces.com/api/v3
  batch_size: 1
```

**Q: 怎么用本地 ollama 跑模型？**
在 `config/roles.yaml` 对应角色的 `model_config` 中：

```yaml
model_config:
  provider: ollama
  model: qwen2.5:14b        # 你本地 pull 的模型名
  api_key: ""
  base_url: "http://localhost:11434"   # Ollama 原生 /api/chat，不需要 /v1 后缀
```

ollama 需已启动。Embedding 如需走本地，使用 `embed.provider: local` 并配 `base_url: http://localhost:11434/v1`（Embedding 仍走 OpenAI 兼容协议）。

**Q: 豆包（火山方舟/火山引擎）模型怎么配？**
豆包提供 OpenAI 兼容接口，统一按 `provider: openai` 配置，把 `base_url` 指向豆包方舟的兼容端点：

```yaml
model_config:
  provider: openai
  model: doubao-lite-4k      # 或你开通的豆包模型名
  api_key: ${DOUBAO_API_KEY} # 方舟 API Key
  base_url: https://ark.cn-beijing.volces.com/api/v3  # 以你开通的地域端点为准
  temperature: 0.5
  max_tokens: 4096
```

Embedding 同理：

```yaml
embed:
  provider: openai
  model: doubao-embedding   # 你开通的豆包 Embedding 模型名
  api_key: ${DOUBAO_API_KEY}
  base_url: https://ark.cn-beijing.volces.com/api/v3
```

只要对方端点兼容 `/v1/chat/completions` 与 `/v1/embeddings`，就不需要单独实现 provider。

**Q: Moonshot / Kimi 模型怎么配？**
Kimi 提供 OpenAI 兼容接口，统一按 `provider: openai` 配置：

```yaml
model_config:
  provider: openai
  model: kimi-K2.7-code          # 或 kimi 系列其他模型名
  api_key: ${KIMI_API_KEY}       # Moonshot API Key
  base_url: https://api.moonshot.cn/v1
  temperature: 0.5
  max_tokens: 4096
```

> 注意：不要把 `provider` 写成 `anthropic`，也不要把 `base_url` 写成 `https://api.deepseek.com/anthropic`。`anthropic` provider 仅用于通过 OpenAI 兼容网关访问 Claude，不适用于 Kimi。

**Q: Plan-and-Execute / AgentPlan 用的是什么模型/协议？**
项目内的 Plan-and-Execute（`internal/graph/plan.go`）调用的是 `domain_agent.model_config` 配置的模型；Self-Reflection 调用 `lightweight_model`。实际协议由对应 `model_config.provider` 决定：`openai` 走 OpenAI 兼容协议，`anthropic` 走 Anthropic Messages API，`ollama` 走 Ollama 原生 /api/chat。

**Q: 温度怎么动态调？**
`soul.Temperature(kind, default)` 按任务类型（Routing/Code/Creative）选温度，`BladesClient.GenerateWithOptions` 临时构造新 provider 完成（`openai.NewModel` 构造廉价）。
