- 依据：2026-10-22～24 日后端日志、会话 #65/#66、当前媒体配置、实际图像/动画产物、WorkBuddy 本地留存产物与记录

## 0. 实施方式

本方案分三阶段，必须按顺序做：

1. **P0 安全止血**：不再制造新记忆污染，不再错选媒体通道，不再批量盲抽，不再把全局最新文件误当任务产物。
2. **P1 核心修复**：多轴决策账本、媒体能力路由、关键姿态门禁、干净媒体上下文。
3. **P2 质量验收**：动作专项指标、真实媒体冒烟、同预算 WorkBuddy 对擂。

不要先换语言模型，不要先增加提示词长度，不要先跑 16 帧，不要先做全量付费 A/B。P0 的单元测试和零付费验证通过后，再进入 P1。

## 1. 目标与非目标

### 1.1 目标

1. 主执行语言模型继续使用 DeepSeek1017，不以换模型代替系统修复。
2. 保留并正确使用现有图像/视频模型，按真实能力选择通道。
3. 立绘达到 WorkBuddy 最佳锚点水平，动画和指令稳定性可验证地不低于 WorkBuddy。
4. 新指令只修改它明确指向的约束，不误伤角色、视角、审批门和验收标准。
5. 一次性任务指令、试验参数、失败半成品不再自动晋升为长期记忆。
6. “指标全过但视觉不合格”不得被判定为完成。

### 1.2 非目标

- 不强迫把正面 45° 改成侧视。
- 不把单图 warp 用于所有动作；它只保留为呼吸、待机、轻微摆动路线。
- 不承诺纯文本评委能判断像素审美。
- 不复制 WorkBuddy 的所有产物；其部分 `run16` 帧也存在断腿，必须选最佳合格参考。
- 不在代码、文档或日志中写入媒体密钥。
- 不物理删除历史记忆和决策底账；纠错采用归档、状态标记和追加新记录。

## 2. 已确认根因

### 2.1 角色合同被破坏

WorkBuddy 使用原始参考图做 `image1` 并设置 `input_fidelity: medium`，保留了墨黑兽体、赤褐云纹、火焰鬃毛、鳞节卷尾等设计。

BMA 在 `2026-10-23.log:161948` 自行改成“赤红褐色豹形身躯”，后续又围绕红色虎纹角色反复生成。问题首先不是画功，而是画的已不是同一只角色。

### 2.2 参考图不等于局部编辑

当前链路：

```text
od_image_generate(reference)
→ OpenDesign image
→ MiniMax subject_reference
```

相关代码：

- `docker/open-design-mcp/server.js:432-450`
- `docker/minimax-media/server.js:203-223`

当前没有向上游提供保真度、编辑强度、遮罩、姿态控制、多参考图、seed、negative prompt。提示词中的“其它部分逐像素不变，只改腿”没有接口保障。

### 2.3 视频协议被 Agent 错选

当前可用链路是 `grok → minimax-media`，但会话 #66：

- 强制 `volcengine`，得到 401：`2026-10-23.log:567041`
- 强制 `openai`，得到 AIHubMix key 缺失：`2026-10-23.log:569742`

这是路由错误，不是 H3 质量结论。

### 2.4 产物对账不可靠

`docker/open-design-mcp/server.js:342-351` 在任务缺文件名时从整个项目取最新文件；`:456` 使用该兜底。并发任务可能拿到同一文件。

“不同提示词同 MD5”是异常信号，但不能直接证明提示词被忽略。现有结果缺少完整 `task_id → request → file` 对账，Agent 在错误诊断上继续重试。

### 2.5 动画工艺缩水

SKILL 的主线是：

```text
基准立绘 → 相位表 → 逐帧生图 → 归一化 → 体检 → 图集
```

见项目技能 `quadruped-beast-gait/SKILL.md:11-13`。

最终实际却退化为单底图 `cv2.remap` 形变，再跑 normalize/audit/pack。单图 warp 无法可靠生成新姿势、新遮挡关系和缺失纹理，不适合作为奔跑主路线。

### 2.6 指标替代视觉质量

当前指标主要证明可打包、不闪、不重复，不证明“像奔跑”。画布裁剪、尾巴运动、旋转起播点都可能改变指标而不改善动作。

`metrics.md:3-4` 已要求换体型重新标定，`:18-20` 已说明狰的固定髋宽区域可能量错，但实际仍被当通用阈值使用。

### 2.7 记忆与摘要越权

- `SessionEvolver` 自动写用户偏好、项目经验和技能，缺少确定性准入：`backend/internal/agent/evolver.go:173-247`。
- 新路线会覆盖所有旧 route：`backend/internal/agent/decision_ledger.go:289-305`，导致不同维度约束被误撤销。
- 路线识别只做关键词包含：`:592-601`，“你不用开始工作”也可能被当成路线变化。
- 压缩器被要求生成【已定决策】：`backend/internal/bootstrap/bootstrap.go:1783-1799`，可从工具记录中虚构用户目标。
- 归档小节已经排除注入，当前污染主要来自仍位于现行小节的自动条目，不是简单恢复旧归档 bug。

## 3. 目标架构

### 3.1 指令权威顺序

```text
最新真实用户原文
> 当前会话多轴决策与已批准审批门
> 已批准计划及验收标准
> 人工维护的项目约定
> 已验证的项目经验
> 稳定用户偏好
> 历史压缩摘要（仅执行状态）
> 工具输出和试验记录
```

摘要不得创造决策，工具输出不得修改路线，长期偏好不得覆盖当前会话指令。

### 3.2 媒体调用链

```text
用户目标
→ 媒体资产合同
→ 当前阶段（anchor / keyframe / inbetween / video）
→ 能力解析（auto provider）
→ 参数支持校验
→ 上游生成
→ task_id 级产物清单
→ 独立视觉门/用户审批
→ 下一阶段
```

不支持的能力必须在收费调用前明确报错，不允许静默忽略参数。

### 3.3 动画生产链

```text
原始参考与角色合同
→ 单张锚点
→ 用户批准锚点
→ 4 个关键姿态
→ 关键姿态视觉审批
→ 中间帧或运动视频
→ normalize
→ 动作专项 audit
→ pack
→ 游戏内实际尺寸预览
→ 同预算盲评
```

## 4. P0：安全止血

## 4.1 长期记忆改为 shadow 模式

### 修改点

- `backend/internal/config/config.go`
- `config/config.yaml`
- `backend/internal/agent/evolver.go`
- `backend/internal/bootstrap/evolver.go`

新增配置：

```yaml
memory:
  write_mode: shadow # off | shadow | enforce
```

语义：

- `off`：不调用 SessionEvolver，不写偏好、项目经验、经验技能。
- `shadow`：允许生成候选，只写 `evolution_log`，不得修改 `user_profile.md`、`project_preferences.md`、`skills_learned/` 和 `learned_skills`。
- `enforce`：允许写入，但必须通过确定性准入门，不是仅靠 LLM 自我判断。

第一版默认 `shadow`。验证稳定后，再把人工确认过的条目纳入现行记忆。

### enforce 准入规则

1. 全局用户偏好必须含明确长期意图，例如“以后、始终、记住、我的偏好是”。
2. 当前任务的一次性选择不得写全局画像。
3. 项目经验必须同时满足：已落地、已验证、用户未否决、可复用。
4. `mixed/failed` 只记录失败档案，不晋升为现行经验。
5. 试验参数必须带适用角色、参考图 hash、验证证据和状态；缺任一项只进试验记录。
6. 被否决内容只能进入 rejected/archive，不得换措辞复活。
7. 每次写入保留 source session、来源消息、时间、验证状态。

### 测试

- 普通“用 D 版”不写全局偏好。
- “不走视频抽帧”只形成当前项目/会话约束，不变成跨项目永久禁令。
- `shadow` 下三个存储面完全不变。
- `mixed` 会话不产生现行项目经验。
- 已归档方案不能以近义句重新进入现行小节。

## 4.2 清理现行污染，保留审计底账

只手工整理，不写脚本物理删除。

1. 先备份：
   - 部署目录 `config/user_profile.md`
   - 项目 `.bma/project_preferences.md`
2. 全局画像只保留跨项目稳定偏好；具体角色、动画路线、单次工具选择移到项目或会话层。
3. 项目经验中将以下内容移入试验/归档：
   - 未验证的 duty、bob、单底图形变参数；
   - 已修复但仍写成“需修改”的问题；
   - 某张参考图专属处理链；
   - 被后续指令替换的方案。
4. 保留归档小节，禁止重新注入。

验收：新会话的 system prompt 不再出现与当前资产合同冲突的旧路线。

## 4.4 删除全局最新文件兜底，建立 task 级清单

### 修改点

## 5. P1：核心修复

## 5.1 单路线账本改为多轴账本

### 决策轴

至少支持：

```text
execution_mode     execute | answer_only | discuss
asset_source       existing | ai_image | video | mixed
animation_method   frame_generate | warp | video_frames
identity           当前角色/参考资产合同
view               当前视角
approval_anchor    pending | approved | rejected
approval_keyframe  pending | approved | rejected
acceptance         当前验收标准
delivery           当前交付形式
```

### 数据库迁移

新增 `migrations/018_session_decision_axes.sql`：

```sql
ALTER TABLE session_decisions
    ADD COLUMN IF NOT EXISTS axis VARCHAR(32) NOT NULL DEFAULT '',
    ADD COLUMN IF NOT EXISTS source_message_id VARCHAR(128) NOT NULL DEFAULT '';

CREATE INDEX IF NOT EXISTS idx_session_decisions_axis
    ON session_decisions (session_id, axis, status, id DESC);
```

`session_decisions` 已有 `owner`，必须保留并继续写入，不得破坏 append-only 和状态归档语义。

同步修改：

- `backend/internal/store/schema.go`
- `backend/internal/store/session_decisions.go`
- `backend/internal/agent/decision_ledger.go`
- `backend/internal/agent/session_react.go`
- `backend/internal/agent/service_react.go`

新增 `SupersedeAxis`，只允许替换同 axis 的 active 行。旧 `Supersede` 不再用于全部 route 一刀切。

### 行为规则

1. “重新 AI 生图”只改 `asset_source`。
2. “不用开始工作，告诉我……”只改 `execution_mode=answer_only`，不撤销动画路线。
3. “继续”不新增路线，继承当前状态。
4. “用 D 版”更新 identity 的当前候选，不得换成其他参考图。
5. “短视频抽帧”只改 `animation_method`；后续“不走视频”再替换同一轴。
6. “幅度太小”是当前产物反馈，不等于否决整个技术路线。
7. 新指令未明确撤销的审批门、视角和验收标准继续有效。
8. 冲突只发生在同轴；跨轴不得互相覆盖。

### 注入修正

`decisionBlockMaxRunes` 当前为 1400，不能通过整体尾部截断丢掉最新指令。

- 必留：当前各轴、最新真实指令、当前审批门、验收标准。
- 可裁：旧参考、旧 superseded 历史。
- rejected/superseded 只保留必要条数。
- 截断顺序必须确定性测试，不能最后再截整个 block。

## 5.2 压缩摘要只保留执行状态

修改 `backend/internal/bootstrap/bootstrap.go:newHistorySummarizer`：

新结构：

```text
【执行状态】已完成、未完成、当前阻塞
【产物】文件路径、用途、hash/task_id（有则保留）
【失败与未验证】真实错误、尚未证明的假设
【文件要点】路径、行号、函数/常量、实际读取结论
```

规则：

1. 删除让摘要器生成【已定决策】的要求。
2. 用户决策只从 `session_decisions` 读取。
3. 工具-only 片段不得生成用户目标。
4. 合并旧摘要时携带当前否决轴，不得复活已否决路线。
5. 每段保留来源消息范围，便于对账。
6. 压缩摘要只作历史数据，权威级低于当前账本。

回归样例：只有 ReadMedia 调用时，不得出现“用户要求压缩历史”之类新目标。

## 5.3 媒体能力路由

### 能力模型

至少区分：

```text
t2i
subject_reference
image_edit
inpaint
multi_reference
input_fidelity
negative_prompt
seed
t2v
i2v
aspect
duration
```

### 配置方式

媒体模型、网关、key 仍只放现有 `.env` 媒体段，不在 `config.yaml` 再建模型配置。

可在同一媒体段增加非敏感能力声明，例如：

```bash
IMAGE_CAPABILITIES=t2i,subject_reference,aspect
VIDEO_CAPABILITIES=t2v,i2v,aspect,duration
```

由 `docker/open-design-daemon/entrypoint.sh` 写入对应 provider 的 `capabilities`，桥在 `fetchMediaDefaults` 一并读取。

未声明时采用保守能力集，不得默认宣称 image_edit/inpaint 可用。

### 工具参数

`od_image_generate` 增加：

- `operation`: `t2i | subject_reference | image_edit | inpaint`
- `input_fidelity`（仅支持时允许）
- `negative_prompt`（仅支持时允许）
- `seed`（仅支持时允许）
- `stage`: `asset | anchor | keyframe | inbetween`

现有 `reference` 保留兼容：

- 有 `subject_reference` 时映射到该操作；
- 只有 `image_edit` 时映射到编辑；
- 两者都不可用时本地报错。

不得只增加 schema 而在适配层静默丢弃参数。

### 当前 MiniMax 行为

- `image-01` 继续走 `subject_reference`。
- 对要求“只改腿、其它不变”的 `image_edit/inpaint` 请求，当前通道若不满足能力，必须返回 `capability_unsupported`。
- 需要真正局部编辑时，配置具备该能力的通道；这与评价模型强弱无关。

### 画幅和实际参数

- `aspect` 按上游能力补充 `3:2`、`2:3`，或在 schema 层明确禁止。
- `patch-image-size.js` 同步增加对应尺寸映射，禁止未知比例静默变方图。
- 返回实际 width/height，不只返回请求 aspect。

## 5.4 阶段审批硬门

复用现有 `ask_user`/会话挂起机制，不能只靠提示词说“先给用户看”。

修改：

- `backend/internal/domain/tool/ask_user.go`
- `backend/internal/agent/service_react.go`
- `backend/internal/agent/decision_ledger.go`
- 媒体工具调用前的权限/门禁位置

流程：

1. 锚点生成后先 `ShowArtifact`。
2. 再发起带 `asset_gate=anchor` 的审批，会话进入 awaiting_clarify。
3. 批准写 `approval_anchor=approved`；拒绝保持 anchor 阶段。
4. 未批准前，`stage=keyframe/inbetween` 和运动视频生成全部本地拒绝。
5. 关键姿态采用同样的 `approval_keyframe` 门禁。
6. 后续改路线不得隐式清除批准；换参考图 hash 时才使旧批准失效。

## 5.5 干净媒体上下文

不为美术任务复用数十次失败后的长上下文。

每个新角色/新动作创建独立媒体子任务，只携带：

- 当前角色合同；
- 已批准参考图及 hash；
- 当前阶段；
- 当前验收标准；
- 必需媒体工具。

复用 domain 的 DeepSeek 绑定即可，不要求新增模型。限制无关工具，避免美术任务同时暴露工作流、插件管理、外部 Agent 等 50 多个工具。

P0 可先通过“新会话/新子任务”人工执行，P1 再固化成标准媒体任务入口。

## 6. P1：动画 SKILL 重构

修改项目中的 `quadruped-beast-gait` 技能，验证后再推广复用。

### 6.1 阶段化

```text
Stage 0  角色合同 + 锚点
Stage 1  4 个关键姿态
Stage 2  关键姿态审批
Stage 3  中间帧或运动视频
Stage 4  normalize
Stage 5  技术 audit + 动作 audit
Stage 6  pack + 游戏内预览
```

### 6.2 关键姿态

Run 先产出：

- contact
- down
- passing
- flight/up

`gen_frame_plan.py` 增加阶段输出，例如 `--stage=keyframe|inbetween`，关键姿态使用固定索引，完整 16 帧计划由程序生成，不让 LLM 手写 16 段长提示词。

提示词拆成：

```text
不可变身份块（由资产合同生成）
+ 固定机位/构图块
+ 单帧姿态变量
+ 上游支持的负向约束
```

身份主要由参考和编辑能力锁定，不靠每帧重复改写角色描述。

### 6.3 路线选择

- `image_edit` 可用：锚点 → 4 关键姿态 → 中间帧。
- 只有 `subject_reference`：先做小批能力探针，不能保证姿态时禁止直接 16 帧。
- 可接受视频成本：H3 首帧视频提供运动先验，选一个完整周期后抽帧。
- 不接受视频成本：必须配置真正的姿态编辑通道，不能静默改成 warp。
- warp 仅用于 idle/breathing/轻微摆动，Run 使用必须另行明确批准。

### 6.4 帧率与预览

- Run 默认以 20～24fps 验收。
- 不只检查 2048px 大图和接触表，还要在游戏实际显示尺寸下播放。
- 每阶段先展示，再推进；不得“ShowArtifact 后继续执行一串工具，最后才问”。

## 7. P2：验收体系重构

### 7.1 保留技术 audit

现有 normalize/audit/pack 继续负责：

- 帧数、尺寸、alpha；
- 锚点、中心漂移；
- 重复帧；
- 文件尺寸与加载；
- 图集和动作表结构。

技术 audit 通过只表示“可打包”。

### 7.2 新增 motion audit

至少增加：

1. 腿部区域变化占比，排除尾巴、鬃毛和纯背景变化。
2. 每条腿支撑期/摆动期是否完整。
3. 足底轨迹、抬脚高度、步幅，按体高或髋宽归一。
4. 所有相邻边（含循环边）的 P95/最大突变，不能靠旋转起播点藏起最差边。
5. 角色身份逐帧一致性：角、尾巴、主要斑纹、颜色、视角。
6. 游戏实际尺寸下的可读性。

### 7.3 每角色标定

为每个角色保存校准信息：

```yaml
view: front45
reference_hash: ...
hip_band: [...]
leg_rois: [...]
approved_motion_reference: ...
fps: 24
```

禁止所有角色共用固定 72%～79% 髋区。ROI 可由现有分割脚本辅助，但首次必须视觉确认。

### 7.4 视觉门

优先级：

1. 用户审批；
2. 独立多模态评委；
3. 当前执行 Agent 自评只能作辅助，不能作为唯一通过依据。

纯文本 workflow judge 不得给像素审美打分。没有可用视觉评委时保持 `needs_review`，不得自动 pass。

## 10. WorkBuddy 对擂与完成标准

### 10.1 对擂方法

- 至少 20 个代表性场景，覆盖单图、局部编辑、系列素材、正面奔跑、短视频、路线修改。
- 同原始参考、同任务文本、同语言模型、同媒体能力、同调用预算。
- 每类随机任务重复执行，禁止 BMA 无限重抽而 WorkBuddy 只跑一次。
- 隐藏产物来源，按角色一致性、审美、解剖、动作可读性、稳定性盲评。
- 记录耗时、token、调用次数、费用、硬失败率、返工率。

### 10.2 完成门槛

1. 指令回归场景 100% 通过。
2. 一次性任务指令写全局记忆为 0。
3. `task_id → 产物` 对账准确率 100%。
4. 未配置 provider/不支持能力的本地拦截率 100%。
5. 锚点未批准时进入下一阶段的次数为 0。
6. 立绘盲评 BMA 胜率不低于 50%，且身份硬失败率不高于 WorkBuddy。
7. 动画盲评 BMA 胜率不低于 50%，断腿、换角色等硬失败率不高于 WorkBuddy。
8. 技术 audit 全过但视觉未审，只能交付 `needs_review`，不能宣称完成。

只有达到以上条件，才能声称“达到 WorkBuddy 效果”。

## 13. 第一次试跑建议

第一轮不要直接重做 16 帧，按下面顺序验证：

1. 用原始参考图生成/选定一张锚点，角色合同不允许改写。
2. 展示锚点并停止，确认系统确实等待审批。
3. 批准后只生成 4 个关键姿态；若当前通道只支持 subject_reference，先验证其能力，不承诺局部编辑。
4. 检查每个产物的 task_id、参考 hash、实际尺寸和输出 hash。
5. 在同一会话输入“重新 AI 生图”，确认原审批、视角和角色合同仍在。
6. 输入“你不用开始工作，告诉我这个 skill 干嘛用的”，确认只回答，不生成、不写文件。
7. 检查 `user_profile.md` 和 `project_preferences.md` 在 shadow 下没有新增内容。
8. 以上全部正确后，再决定是否消耗额度生成中间帧或 H3 视频。

如果第一轮仍出现角色漂移，优先检查参考资产合同和编辑能力，不要继续改长提示词；如果仍出现旧路线回注，直接检查当轮 `llm_input` 中各轴、摘要和现行偏好来源。
