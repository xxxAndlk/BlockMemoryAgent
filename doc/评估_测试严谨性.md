# 评估：测试严谨性与多重确认

**评估时间**：2026-07-24
**评估对象**：第七评估项中"测试流程最为重要，查看现在的测试是否严谨与多重确认。"
**评估方法**：对比"修改前（无 verifyloop，靠主 Agent 提示词自觉）"与"修改后（verifyloop 原生状态机 + 阶段 5 抽象层）"的测试严谨性，定义量化指标，给出结论与改进建议。

---

## 一、量化指标定义

| 指标 | 定义 | 修改前 | 修改后 |
|---|---|---|---|
| **确认层数** | 一次产出经过多少道独立验证 | 0-1（依赖 LLM 自觉） | 2（自测 + 上级统一测试） |
| **修正闭环** | 验证失败后是否自动打回修正 | 否（LLM 可能直接放弃） | 是（Fixer 接口，最多 maxRounds 轮） |
| **往返上限保护** | 防止互相推诿死循环 | 无 | `verification_max_rounds` 默认 5 |
| **结论确定性** | 通过/未通过判定方式 | LLM 自由文本 | `[VERIFY:PASS/FAIL]` 标记 + `ParseAgentVerdict` 确定性解析 |
| **结论归一** | 不同验证器返回类型一致性 | 无（裸字符串） | `Verdict{Passed, Reason, Detail}` 结构化 |
| **失败原因可追溯** | 未通过时是否附失败原因 | 依赖 LLM 自觉 | `Verdict.Reason` + `Result.FailReason` 强制携带 |
| **父 Agent 感知** | 验证结果是否回传父 Agent | 依赖 LLM 自觉 | `Reporter.Report` 强制投递（通过 MsgInfo / 未通过 MsgEscalate） |
| **终结保护** | 父 Agent 终结前是否等待未决子 Agent | 否 | `PendingChildrenChecker` 阻塞等待 |
| **验证方式可插拔** | 是否支持非 Agent 验证（CLI/MCP/ComputerUse） | 否 | `Verifier` 接口 + 三类扩展口子 |
| **ctx 取消保护** | 长时验证可否中断 | 否 | `Run` 检查 `ctx.Err()` 快速返回 |

## 三、严谨性对比（修改前 vs 修改后）

### 修改前（无 verifyloop）
```
code Agent 完成 -> [mailbox 通知父] -> 父 Agent 自觉决定是否测试
                                          |
                                          v
                                    LLM 自由判断（可能跳过测试）
                                          |
                                          v
                                    测试结果 LLM 自由解读（可能误判）
                                          |
                                          v
                                    失败后 LLM 自觉修正（可能放弃）
```
**问题**：
1. 测试是否执行依赖 LLM 自觉，无强制
2. 测试通过/失败无确定性判定，LLM 可能误读
3. 失败后无强制修正闭环
4. 无往返上限，可能死循环
5. 父 Agent 无感知验证结果

### 修改后（verifyloop 状态机）
```
code Agent 完成 -> [OnSubAgentDone 钩子] -> verifyloop.Run
                                                  |
                          +-----------------------+-----------------------+
                          v                                               v
                    SelfTest (测试 Agent)                          maxRounds 上限保护
                          |                                               |
                +---------+---------+                             超限 -> Reporter MsgEscalate
                v                   v
            PASS                FAIL
                |                   |
                v                   v
        UnifiedTest            Fixer.Fix -> 回到 SelfTest
                |
        +-------+-------+
        v               v
      PASS            FAIL
        |               |
        v               v
  Reporter MsgInfo  Fixer.Fix -> 回到 SelfTest
```
**改进**：
1. 测试强制执行（钩子触发，不依赖 LLM）
2. 通过/失败确定性解析（`[VERIFY:PASS/FAIL]` 标记）
3. 失败强制修正闭环（Fixer 接口）
4. 往返上限防死循环（maxRounds）
5. 父 Agent 强制感知（Reporter 投递邮箱）
6. 终结保护防迟到消息丢失（PendingChildrenChecker）

## 四、多重确认语义对照

原文要求"先进行自测试，返回结果成功后返回给上级Agent，上级Agent按更大范围模块进行统一测试，哪个部分不行打回"。

| 原文要求 | 实现位置 | 覆盖 |
|---|---|---|
| 先进行自测试 | `Verifier.SelfTest` | ✓ |
| 自测成功后返回上级 | SelfTest PASS -> 进 UnifiedTest | ✓ |
| 上级按更大范围模块统一测试 | `Verifier.UnifiedTest`（模块/集成级） | ✓ |
| 哪个部分不行打回 | UnifiedTest FAIL -> Fixer.Fix -> 回 SelfTest | ✓ |
| 期间各Agent可以反复询问纠正 | maxRounds 循环 + send_message 询问 | ✓ |
| 被询问时开协程回复 | `servePooled` goroutine + WaitForMessage | ✓ |

**未覆盖**：
- "测试方向不明确时先把方案列出，给代码Agent确认逻辑" - 无方案确认前置步骤（当前直接进自测）
- "协程Agent常驻共享代码Agent记忆" - 实例池历史不跨 Agent 共享（见块记忆vs实例池评估）

## 五、当前严谨性短板

1. **方案确认前置缺失**：测试方向不明确时无"列方案->代码 Agent 确认->不符合纠正->符合才测试"这一轮。当前直接进自测，测试 Agent 可能测错方向。
2. **`[VERIFY:PASS/FAIL]` 标记依赖 LLM 自觉输出**：若测试 Agent 忘记输出标记，`ParseAgentVerdict` 判"missing verify marker"为失败。这是正确兜底，但无提示 LLM 补输出的机制。
3. **`DomainSelfTestEnabled` 未接线**：domain agent 完成后不触发 verifyloop，只有 code_assistant 触发。模块级验证覆盖不全。
4. **角色对硬编码**：bootstrap 硬写 `code_assistant`/`test_assistant`，其他角色（doc/ui）无验证闭环。
5. **无量化指标采集**：无"平均往返轮数"、"自测通过率"、"修正成功率"等指标埋点，严谨性无法持续监控。

## 六、改进建议（按优先级）

### 高
1. **接线 `DomainSelfTestEnabled`**：在 `service_react.runSession` 会话终态处触发 verifyloop，覆盖 domain agent 的模块级验证。
2. **角色对配置化**：config 增加 `verifyloop_role_pairs` 列表（如 `code_assistant->test_assistant`、`ui_assistant->test_assistant`），bootstrap 按列表注册多个 OnSubAgentDone 钩子。
3. **指标埋点**：`Orchestrator.Run` 结束时记录 `rounds`/`passed`/`failReason` 到 metrics（已有 `internal/agent/metrics.go` 框架可复用），为严谨性持续监控提供数据。

### 中
4. **方案确认前置步骤**：`Verifier` 接口增加 `PlanConfirm` 方法（可选），测试方向不明确时先列方案给产出方确认，确认后再进 SelfTest。默认实现可空操作。
5. **标记缺失补救**：`ParseAgentVerdict` 返回 missing 时，`AgentVerifier` 可追加一轮"请补输出 PASS/FAIL 标记"提示，而非直接判失败。

### 低
6. **CLIVerifier 实现**：接入 `domain/tool.Executor` 跑 `go test`/`go build`，为代码任务提供确定性验证（退出码 0/非 0），消除 LLM 标记依赖。
7. **ComputerUseVerifier 实现**：接入 computeruse 包，为前端任务提供截图对比验证。
8. **MCPVerifier 实现**：接入 MCP 客户端，为外部系统任务提供 MCP 工具验证。

---

## 七、最终结论

**修改后显著优于修改前**：
- 确认层数 0-1 -> 2（自测 + 统一测试）
- 修正闭环 否 -> 是（强制 Fixer）
- 结论确定性 裸字符串 -> 结构化 Verdict + 确定性解析
- 往返保护 无 -> maxRounds
- 父 Agent 感知 自觉 -> 强制 Reporter
- 验证方式 单一 Agent -> 可插拔接口（CLI/MCP/ComputerUse 口子）

**仍需改进**：方案确认前置、DomainSelfTest 接线、角色对配置化、指标埋点。

**严谨性评分**（满分 10）：
- 修改前：3/10（依赖 LLM 自觉，无强制）
- 修改后：7/10（原生状态机 + 双层确认 + 往返保护，缺方案确认前置与指标埋点）
- 目标：9/10（补齐高优先级改进后）
