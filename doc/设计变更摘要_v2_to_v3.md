# 设计变更摘要：从 v2 到 v3

> 本文档记录 BlockMemoryAgent 设计从 v2 到 v3 的核心变更，说明为什么变更、变更了什么、以及变更后的影响。

---

## 1. 变更背景

### 1.1 原始设计（v2）的出发点

v2 设计文档的核心假设：
- LLM 上下文窗口是"极度稀缺的资源"（默认控制 1000 token）
- 需要通过四层 Agent 编排（MetaAgent → DomainAgent → SubDomainAgent → Assistant）来管理上下文
- 所有决策（路由、Skill 选择、记忆压缩）都由 LLM 驱动
- 记忆压缩需要四级（Raw → Standard → Compact → Marker）

### 1.2 实际使用中的问题

在开发和使用过程中，发现以下问题：

| 问题 | 现象 | 影响 |
|------|------|------|
| 上下文预算太小 | 1000 token 无法容纳一个文件的完整内容 + 对话历史 | 模型无法有效推理 |
| 四层编排 overhead 过大 | 简单任务也要走 3-4 次 LLM 调用 | 延迟高、成本高 |
| 伪嵌入语义检索失效 | 哈希 bag-of-tokens 无法捕捉语义 | 跨会话记忆召回质量差 |
| 记忆写入链路断裂 | 回调触发机制不可靠，数据库里查不到记录 | 跨会话记忆无法复用 |
| 四级压缩过于复杂 | 阈值难调、容易出 bug、难以验证 | 压缩管线形同虚设 |
| 模型未分层选型 | 所有角色都用 deepseek-v4-flash | 小任务成本高 |
| 会话与消息混淆 | 每轮消息都开新会话 | 无法支持多轮对话 |

### 1.3 触发变更的真实痛点

项目作者在长期使用 Claude Code 时，遇到三个无法回避的问题：
1. **上下文超过 200K 后模型明显变笨**——长上下文中的有效注意力衰减
2. **多轮对话中夹杂不相干内容，污染当前任务**——线性上下文没有时间线/话题线隔离
3. **使用期限很短，需要频繁开新对话重置上下文**——没有跨会话记忆持久化

这三个痛点不是"模型上下文不够大"，而是"大上下文下有效注意力衰减"、"话题污染"、"跨会话遗忘"。这促使设计重新聚焦。

## 2. 核心变更

### 2.1 架构层级：从四层到三层

**v2**：
```
MetaAgent → DomainAgent → SubDomainAgent → Assistant
```

**v3**：
```
Router → Agent Core → Memory & Tools
```

| 维度 | v2 | v3 | 理由 |
|------|-----|-----|------|
| 层级数 | 4 | 3 | 减少 overhead |
| 路由方式 | LLM 动态拆分领域 | 规则优先（80%），LLM 兜底（20%） | 零成本路由简单任务 |
| 执行模式 | 纯 ReAct 循环 | Plan-Execute-Reflect（3-5 轮） | 全局规划 + 中途反思 |
| 动态创建 | 每次创建 DomainAgent/SubDomainAgent | 按需创建 Agent（只有复杂任务才创建） | 减少不必要的实例创建 |

**影响**：简单任务延迟从 3-5s 降低到 <1s，复杂任务成功率提升（有全局规划）。

### 2.2 上下文预算：从 1000 到 4K-8K

**v2**：
- 主 Agent 上下文控制在 1000 token 以内
- 包括：全局任务看板摘要（200）+ 当前活跃话题块摘要（300）+ 最近 3 轮必要交互（500）

**v3**：
- 输入 LLM 的上下文控制在 4K-8K token（可配置，根据模型能力调整）
- 包括：系统提示（1024）+ 当前任务（1024）+ 召回记忆（2048-4096）+ 计划状态（512）+ 预留缓冲（512-1024）

| 维度 | v2 | v3 | 理由 |
|------|-----|-----|------|
| 预算 | 1000 token | 4K-8K token | 1000 太少，无法容纳文件内容 |
| 分配方式 | 固定分配 | 结构化 TokenBudget | 各段独立控制，灵活调整 |
| 溢出处理 | 强制压缩/切换 | 渐进截断 + 会话拆分 | 更温和，避免中断任务 |

**影响**：模型可以完整看到 1-2 个文件的内容 + 召回的相关记忆，推理质量显著提升。

### 2.3 记忆写入：从回调到显式

**v2**：
```go
// 通过回调触发
memCallback.OnEnd(ctx, instID, sessionID, result)
```
- 回调触发点模糊
- 容易被遗漏（执行路径有分支时）
- 难以调试（不知道是否触发）
- 结果：TODO 明确记载"数据库里没有任何一条记录"

**v3**：
```go
// Agent 执行后的最后一行显式调用
func (a *Agent) Run(ctx, input) (*Result, error) {
    result := a.loop(ctx, input, memories)
    a.memory.SaveTrace(ctx, result.Trace)        // 同步写入，确保不丢
    go a.memory.SaveSummary(ctx, result.Summary) // 异步写入，不阻塞
    return result, nil
}
```
- 在 `return` 前的最后一行，100% 执行
- 同步写入中期记忆（失败立即报错，可重试）
- 异步写入长期记忆（不阻塞用户响应）

**影响**：记忆持久化从"可能没写入"变成"100% 写入"，跨会话记忆真正可用。

### 2.4 记忆压缩：从四级到两级

**v2**：
```
Raw → Standard → Compact → Marker
```
- 每级都有复杂的阈值和触发条件
- 渐进式压缩，实现复杂
- 难以验证（压缩是否触发？压缩后是否正确？）

**v3**：
```
原始记录（执行轨迹）          摘要（关键知识）
     │                            │
     │  保留 7 天                  │  永久保存（热点）
     │  用于调试/审计              │  或降级后删除（冷记忆）
     │                            │
     ▼                            ▼
┌─────────────┐            ┌─────────────┐
│  PostgreSQL  │            │  PostgreSQL  │
│  traces 表   │            │  long_term   │
│  完整对话    │            │  摘要 + 向量  │
│  工具输出    │            │  热点: 完整   │
│  执行结果    │            │  冷记忆: 删除 │
└─────────────┘            └─────────────┘
```

| 维度 | v2 | v3 | 理由 |
|------|-----|-----|------|
| 层级 | 4 | 2 | 简单、可预测、易验证 |
| 原始保留 | 渐进压缩 | 保留 7 天后直接删除 | 7 天足够调试，不需要渐进压缩 |
| 摘要生成 | 每级压缩时生成 | 会话结束后 LLM 生成 | 一次生成，质量更高 |
| 热点/冷记忆 | 无 | 热点保留完整细节，冷记忆降级删除 | 区分价值，避免无差别删除 |

**影响**：压缩管线从"复杂且不可验证"变成"简单且可预测"。

### 2.5 向量检索：从伪嵌入到真实嵌入（分阶段）

**v2**：
```go
// 伪嵌入：哈希 bag-of-tokens
emb := embed.PseudoEmbed(query, dim) // 不是真实语义向量
```
- 哈希 bag-of-tokens，无法捕捉语义
- 向量检索召回质量差（"商城页面"可能召回"商场页面"）

**v3**：
```go
// 前期：关键词匹配（简单、可靠、零成本）
// 后期：真实 embedding（text-embedding-3 / bge-m3）
```

| 阶段 | v2 | v3 | 理由 |
|------|-----|-----|------|
| 前期 | 伪嵌入（声称有语义检索，实际没有） | 关键词匹配（诚实、可靠） | 伪嵌入不如关键词匹配 |
| 后期 | 无计划 | 接入 text-embedding-3 / bge-m3 | 真实语义检索，质量提升 |

**影响**：前期关键词匹配的召回率比伪嵌入更高，后期真实 embedding 进一步提升。

### 2.6 模型选型：从全部统一到有分层

**v2**：
- 所有角色（MetaAgent、DomainAgent、代码助手、UI 助手）都用 `deepseek-v4-flash`

**v3**：
| 角色 | 模型 | 理由 |
|------|------|------|
| 路由判断 | 规则 + 轻量模型（gpt-4o-mini） | 简单分类，成本最低 |
| 计划生成 | 中等模型（gpt-4o） | 需要结构化推理 |
| 代码执行 | 强模型（o3-mini / Claude 3.5 Sonnet） | 代码质量要求高 |
| 摘要生成 | 轻量模型 | 不需要强推理 |
| Embedding | 专用模型（text-embedding-3） | 语义检索质量决定记忆效果 |

**影响**：简单任务成本降低 70%，复杂任务质量提升。

### 2.7 会话模型：从消息=新会话到会话=容器

**v2**：
- 每轮消息都开一个新会话
- 会话之间没有关联，每次从零开始
- 无法支持多轮对话

**v3**：
- 会话 = 主题容器（如"商城页面重构"），包含多轮消息
- 消息 = 用户输入 / 助手回复 / 工具结果
- 新消息加入当前会话的 Messages 列表
- 只有用户明确"新建会话"或主题完全不同，才创建新会话

**影响**：支持真正的多轮对话，跨会话记忆有明确的"主题"锚点。

### 2.8 话题隔离：从时间线隔离到话题块隔离

**v2**：
- 按时间线隔离（最近的 N 轮对话）
- 问题：修复 CSS 时中途问了一句函数文档，后续 CSS 修复被污染

**v3**：
- 每个话题/任务是一个独立的 SessionBlock
- 拥有独立的上下文（对话历史、工具输出、文件状态）
- 话题切换时旧话题归档，新话题从零开始（但可召回相关片段）
- 跨话题知识（编码规范、用户偏好）标记为 `global`，所有话题共享

**影响**：话题互不污染，跨话题知识自动共享。

## 3. 扩展设计变更（Agent 工作流平台）

### 3.1 从编程助手到工作流平台

**v2**：
- 定位：编程助手（代码编写、审查、重构）
- 场景：单一编程场景

**v3 扩展**：
- 定位：Agent 工作流平台
- 场景：编程、工作流编排、测试、研究、团队协作

**核心原则**：底层架构统一（记忆、路由、Agent Core），上层场景扩展（工作流模板、工具集、记忆类型）。

### 3.2 工作流编排

**新增**：
- 工作流定义：YAML 格式定义 DAG（节点、依赖、触发条件、审批门、失败回滚）
- 工作流执行：拓扑排序执行，处理并行和依赖，监控状态
- 工作流优化：基于历史数据自动优化（并行化、重试策略、资源瓶颈）
- 工作流记忆：工作流模板库、执行轨迹、失败模式、优化建议

### 3.3 测试自动化

**新增**：
- 测试设计：根据代码变更自动确定测试策略
- 测试生成：自动生成测试用例（基于代码分析、边界值、历史 Bug 模式）
- 结果分析：分析失败原因（代码变更引入、环境变化、flaky test）
- 修复建议：针对失败测试给出修复建议或自动修复
- 测试记忆：测试用例库、Bug 模式库、测试历史、flaky test 标记

### 3.4 研究模式

**新增**：
- 信息搜集：从多个来源（搜索引擎、数据库、API、文献）搜集信息
- 交叉验证：验证信息准确性（多个来源对比、事实核查）
- 分析归纳：分析趋势、发现模式、提炼结论
- 报告生成：生成结构化研究报告（摘要、发现、建议、引用）
- 研究记忆：研究方向、信息来源、研究结论、报告模板

### 3.5 团队协作

**新增**：
- 任务分配：根据团队成员技能和负载自动分配
- 进度跟踪：识别瓶颈、提醒风险、预测完成时间
- 评审参与：代码评审、文档评审，给出建议
- 沟通协调：在团队频道同步信息，协调跨团队依赖
- 团队记忆：成员档案、项目知识、任务管理、沟通记录、决策过程

## 4. 设计哲学变更

### 4.1 从"一切由 LLM 驱动"到"规则优先，LLM 兜底"

**v2**：
- 所有决策（路由、Skill 选择、记忆压缩）都由 LLM 驱动
- 禁止硬编码逻辑

**v3**：
- 简单任务：规则匹配（零成本，覆盖 80%）
- 模糊任务：轻量模型 LLM 判断（覆盖 20%）
- 硬编码规则用于确定性场景（路由、工具匹配）

**理由**：
- LLM 调用有延迟和成本，不是所有决策都值得用 LLM
- 规则更可靠（不会"误判"），LLM 有时会误判
- 80/20 原则：用 20% 的 LLM 调用覆盖 80% 的复杂场景

### 4.2 从"过度分层"到"扁平够用"

**v2**：
- 四层编排（Meta/Domain/Sub/Assistant）
- 每个层级都创建动态实例
- 复杂度高，overhead 大

**v3**：
- 三层架构（Router/Agent Core/Memory & Tools）
- 简单任务直接回答，不进入 Agent 循环
- 复杂任务才进入 Plan-Execute-Reflect
- 按需创建 Agent，不是每次都创建

**理由**：
- 现代 LLM（128K+）足够处理中等复杂度的任务规划
- 额外的分层没有带来"更智能"的决策，只是增加延迟和成本
- 扁平化架构更简单、可预测、可调试

### 4.3 从"完美压缩"到"简单够用"

**v2**：
- 四级压缩（Raw → Standard → Compact → Marker）
- 渐进式、复杂、难以验证

**v3**：
- 两级压缩（原始 7 天 + 摘要永久）
- 简单、可预测、可验证

**理由**：
- 7 天足够调试和审计，不需要渐进式压缩
- 摘要一次生成（LLM 生成），质量比渐进压缩更高
- 简单方案更容易正确实现，复杂方案更容易出 bug

### 4.4 从"通用 Agent 框架"到"聚焦长时稳定运行"

**v2**：
- 定位：通用 Agent 编排框架
- 对标：LangChain、AutoGen

**v3**：
- 定位：解决 Claude Code 做不到的事情（长时稳定运行、话题隔离、跨会话记忆）
- 对标：Claude Code 的"记忆外挂"
- 差异化：不是替代 Claude Code，而是和它配合使用

**理由**：
- 通用 Agent 框架市场上已有 LangGraph、AutoGen、CrewAI 等成熟产品
- 差异化才是生存之道：聚焦"长时稳定运行"这个细分场景
- 不做模型训练、不做代码补全、不做实时协作——只做记忆和上下文管理

## 5. 技术选型变更

| 组件 | v2 | v3 | 理由 |
|------|-----|-----|------|
| Agent 框架 | go-kratos Blades | 自研 Plan-Execute-Reflect | Blades 的 Flow/Graph 无法支持话题隔离和跨会话记忆 |
| 嵌入模型 | 伪嵌入（哈希 bag-of-tokens） | 前期关键词匹配，后期 text-embedding-3 | 伪嵌入没有语义，不如关键词匹配诚实 |
| 压缩策略 | 四级压缩 | 两级压缩 | 简单、可预测 |
| 写入机制 | 回调触发 | 显式同步写入 | 确保 100% 持久化 |
| 路由策略 | LLM 动态拆分 | 规则优先（80%）+ LLM 兜底（20%） | 减少 overhead |
| 会话模型 | 消息=新会话 | 会话=容器，消息=轮次 | 支持多轮对话 |
| 话题隔离 | 时间线隔离 | SessionBlock 话题隔离 | 防止话题污染 |
| TUI 设计 | 5 面板复杂布局 | 参考 Claude Code 简洁设计 | 主对话始终可见，更符合编程习惯 |
| 工具生态 | 7 个基础工具 | 本地工具 + MCP 协议 | 对接社区生态，无限扩展 |

## 6. 已废弃的设计

以下 v2 设计在 v3 中不再使用：

| 废弃设计 | 废弃原因 | 替代方案 |
|---------|---------|---------|
| SubDomainAgent 层 | overhead 过大，实测单任务 500+ events，5 分钟超时跑不完 | 三层扁平化，复杂任务直接拆分为子任务步骤 |
| 四级压缩（Raw→Standard→Compact→Marker） | 过于复杂，难以验证，阈值难调 | 两级压缩（原始 7 天 + 摘要永久） |
| 伪嵌入（PseudoEmbed） | 无法捕捉语义，召回质量差 | 前期关键词匹配，后期真实 embedding |
| LLM 动态创建 DomainAgent | 每次任务都创建实例，延迟高 | 按需创建，简单任务直接回答 |
| 纯 ReAct 循环 | 走一步看一步，容易陷入局部最优 | Plan-Execute-Reflect（全局规划 + 中途反思） |
| 回调触发记忆写入 | 触发点模糊，容易遗漏，难以调试 | 显式同步写入（`SaveTrace` + `SaveSummary`） |
| 5 面板 TUI 布局 | 过于复杂，未实现，不符合编程习惯 | 参考 Claude Code 的简洁设计 |
| 所有角色统一模型 | 小任务用大模型，成本高 | 按角色分层选型（路由/计划/代码/摘要） |

## 7. 保留的设计

以下 v2 设计在 v3 中继续保留：

| 保留设计 | 保留原因 | 改进点 |
|---------|---------|--------|
| 会话块（SessionBlock） | 核心机制，话题隔离的基础 | 改进为按话题切换归档，支持跨话题知识共享 |
| 三层记忆存储（短期/中期/长期） | 核心架构，记忆外部化的基础 | 写入机制从回调改为显式，压缩从四级改为两级 |
| 多信号相关性评分 | 检索质量的关键 | 语义相似度从伪嵌入改为真实 embedding（后期） |
| 任务看板（TaskBoard） | 协作和进度跟踪的基础 | 扩展为支持工作流编排、团队协作 |
| 邮箱通知（Mailbox） | Agent 间异步通信的基础 | 扩展为支持团队协作场景 |
| 角色配置（roles.yaml） | 灵活的配置驱动方式 | 改进为支持模型分层选型 |
| Watchdog 机制 | 上下文监控的基础 | 改进为更合理的阈值和更温和的处理策略 |

## 8. 影响评估

### 8.1 对现有代码的影响

| 模块 | 影响 | 处理方式 |
|------|------|----------|

## 9. 迁移建议

### 9.1 代码迁移

1. **保留 `internal/store/`**：PostgreSQL 和 Redis 存储层可以保留，表结构可以复用
2. **重写 `internal/graph/`**：从三层图状态机迁移到 Router + Agent Core
3. **重写 `internal/memory/`**：从回调写入迁移到显式写入，从四级压缩迁移到两级压缩
4. **重写 `internal/tui/`**：从 5 面板迁移到参考 Claude Code 的简洁设计
5. **调整 `web/`**：从单会话页面迁移到支持多轮消息、话题切换

### 9.2 数据迁移

1. **保留 `session_history`**：历史会话记录继续保留
2. **废弃 `agent_private_memory`**：不再写入新数据，查询时迁移到 `traces` 表
3. **新增 `messages` 表**：存储多轮消息（从 `session_history` 迁移）
4. **新增 `traces` 表**：存储执行轨迹（替代 `agent_private_memory`）
5. **保留 `global_knowledge` 和 `domain_archive`**：长期记忆和归档继续有效

### 9.3 配置迁移

1. **调整 `config/roles.yaml`**：增加模型分层选型配置
2. **调整 `config/config.yaml`**：增加 TokenBudget 配置（替代硬编码的 1000 token）
3. **保留 `.env`**：环境变量配置不变

## 10. 总结

v2 到 v3 的变更不是"小修小补"，而是**基于真实痛点的根本性重构**。核心变化：

1. **从四层到三层**：减少 overhead，简单任务更快
2. **从 1000 到 4K-8K**：合理的上下文预算，模型能真正推理
3. **从回调到显式**：记忆写入 100% 可靠，跨会话记忆真正可用
4. **从四级到两级**：压缩简单可预测，不再形同虚设
5. **从伪嵌入到真实**：前期关键词匹配，后期语义检索，召回质量提升
6. **从统一模型到分层选型**：小任务用便宜模型，复杂任务用强模型
7. **从消息=新会话到会话=容器**：支持多轮对话，跨会话记忆有锚点
8. **从编程助手到工作流平台**：场景扩展，但核心架构统一

**最终目标**：让你的 Agent 可以连续工作一周，上下文不膨胀，模型不衰减，话题不污染，跨会话不遗忘。
