## 1. 最终结论

**再次验收结论：整项不通过。当前版本不能标记为“Harness 根治完成”，也不应以此口径发布或部署。**

本轮确有实质进展：首轮新增的 6 个阻塞用例已全部通过，原事故合成回放 3/3 通过，后端编译和静态检查通过。但这些结果只说明上一轮点名的局部缺陷已针对性修复，不能证明整个 WP0～WP6 已完成。

本轮新增 4 个生产语义负面用例 **0/4 通过**，分别复现：

1. `semantic_edit_mode=enforce` 可通过省略 `semantic_kind` 回退到旧字面替换；
2. 正常任务结算会写入空 payload 的 `refined` 事件，导致事件流无法重放；
3. `committed` 权威审计写失败后，Action 仍返回成功；
4. 中文无空格请求 `修改src/a.css的间距` 被解析成错误路径和额外目录权限。

此外，Go→Node worker 的端到端测试仍失败，WP5 未实施，真实 DOM/截图采集器、管理 API/UI、桌面 worker 打包、真库/真实模型/性能验收均未完成。

## 4. 本轮新增阻塞缺陷

### P0-1：enforce 不是真正的语义编辑硬门

代码位置：`backend/internal/domain/tool/builtin.go:848-855`。

当前条件是 `semanticRequested && semanticMode != off` 才进入 worker。即使配置为 enforce，只要模型或调用方不传 `semantic_kind`，就继续走旧的 `old_string/new_string` 字面替换。

独立用例实测：未配置 worker、enforce 已开启时，普通 EditFile 仍把 `60px` 成功改为 `24px`，返回 `Success=true`。因此调用方可通过“不声明语义目标”绕过本轮新增的 AST/CSSOM 定位、唯一性、指纹和最小编辑保护。

**返修要求**：明确 enforce 的工具级契约。凡走 EditFile 的生产编辑必须满足语义定位与复验；不支持的语言/目标必须显式失败或走独立、可审计的受控通道，不能因参数缺失静默降级。补 Registry.Dispatch 级负面测试，而非只测 Executor 的内部happy path。

### P0-2：正常结算事件不可重放，事件底账与投影不一致

代码位置：

- `backend/internal/agent/logical_task.go:214-230`：正常结算用 `LogicalEventRefined` 推进 active → awaiting_verification；
- `backend/internal/team/task_manager.go:348-370`：通用 `Transition` 没有给事件填 `Payload`；
- `backend/internal/team/logical_task.go:695-701`：重放 `created/refined` 时必须 JSON 解码 payload；
- `backend/internal/store/logical_task_store.go:230-235`：PG AppendEvent 同样直接保存 `ev.Payload`。

独立用例实测：内存 store 中第二条 `refined` 事件 `Payload=""`，`RebuildProjection` 返回 `decode refined payload: unexpected end of JSON input`。PG 代码走同一空 payload 语义，但真库未运行，故 PG 结果标为静态确认而非真库实测。

**返修要求**：状态迁移事件与全量合同快照事件必须分型；若使用 refined，就必须写完整合同快照，若只是 awaiting_verification 状态迁移，就应使用不含合同替换语义的事件。所有生产写事件路径都要经过“写入后立即重放”的一致性测试。

### P0-3：提交审计丢失仍返回成功

代码位置：`backend/internal/domain/tool/action_pipeline.go:277-289,379-402` 等。只有授权和 checkpoint 使用 `emitCritical`；requested/resolved/executed/mutation/scope/committed 等仍忽略 `emit` 错误。

独立用例注入只在 `committed` 阶段失败的 sink，日志出现 `append event failed ... phase=committed`，但最终结果仍为 `Success=true`。这违反“enforce 下权威审计失败不得静默成功”，也使执行成功与事件底账可能永久不一致。

**返修要求**：为每个阶段定义明确的一致性/恢复协议，不能只把前半段改成 critical。提交事件失败时至少不得返回成功；需要持久化恢复意图、可诊断 outcome 和人工恢复路径，并覆盖 executed/mutation/scope/committed/rollback/manual_recovery 各阶段故障注入。

### P0-4：中文无空格路径解析会产生错误授权

代码位置：`backend/internal/team/scope_resolver.go:41-47,83-112`。

当前正则把中文动词也纳入路径字符。输入 `修改src/a.css的间距` 实测得到：

- 文件：`修改src/a.css`
- 目录：`修改src/**`

这既不是精确授权，也会让后续路径检查和语义目标归属失效。

**返修要求**：路径识别必须有可靠边界与候选验证，不应把任意中文字符贪婪并入路径。增加中文无空格、中英文混写、空格、标点、目录、相对/绝对路径、否定句和不存在的拟新建文件测试。

另外，原始事故式请求通常只说“改某个标题/间距”，不显式给路径。当前 resolver 对此仍保持空 WriteSet，enforce 会拒绝写入；这虽然比误改全部文件安全，但意味着原始使用方式仍未形成可用闭环。需要结合 repo map、语义目标候选与必要澄清完成定位，不能靠扩大 WriteSet 解决。

### P1-1：语义编辑复验忽略错误，且没有验证新值

代码位置：`backend/internal/domain/tool/semantic_edit.go:159-186`。

`applySemanticEdit` 写前应用 TextEdit 后再次调用 `planSemanticEdit`，但所有复验错误都被忽略并返回成功；只有“复验成功且旧 ExpectedValue 非空”才报错。worker 崩溃、解析失败、目标消失、歧义等均不会被区分为复验失败，也没有独立断言新值已经落在预期目标上。

**返修要求**：复验必须以新目标/新值为 oracle，任何无法证明结果的情况均 fail closed；补充错误偏移、worker 第二次调用失败、目标消失、目标歧义、新值未命中等负面用例。

### P1-2：接受结果存在选错任务的静态风险

代码位置：`backend/internal/agent/logical_task.go:171-180`。

无 active 时直接取 `ListTasks` 最后一项，但内存 store 按 revision 再按 task ID 排序，不是按创建/交付时间。旧任务若经历多次 refine，新任务 revision=1，最后一条可能是旧的 superseded 任务，导致最新 delivered-unverified 无法接受或错误操作旧任务。

**返修要求**：由存储层提供“当前可接受任务”的明确查询语义，按会话当前任务关系/交付事实选择，不得用排序数组末尾推断。补多任务、多 revision、superseded、并发接受测试。

## 7. 返修优先级与下一次验收门

### 第一优先级：恢复事实源与执行安全

1. 修复结算事件类型/payload，所有状态迁移写后立即重放；补 PG 同事务与重启恢复测试。
2. 将 Action 全阶段审计失败纳入一致性协议，逐阶段故障注入，禁止成功后静默丢底账。
