## 1. P0 级返修

### P0-1：enforce 成为真正的语义编辑硬门

**问题**（报告 §4 P0-1）：`useSemantic = semanticRequested && mode != off`——enforce 下只要不传 `semantic_kind`，就走旧字面替换，AST/CSSOM 定位、唯一性、指纹、最小编辑四项保护全部被绕过。

**修复**（`domain/tool/builtin.go`）：

```
semantic_edit_mode = enforce
  ├─ 传了 semantic_kind  → 语义通道（必须成功定位，失败 fail closed）
  ├─ 没传 semantic_kind
  │    ├─ 传了 semantic_literal_rationale（≥8 字）→ 受控字面通道（放行但留痕）
  │    └─ 否则 → 拒绝，错误里写明"必须声明语义目标"或"显式走受控通道"
  └─ 其它模式不受影响（off 逐字节等价；shadow 只对拍）
```

受控字面通道**不是**后门：

- 理由写进 `Result.Output`，随 `ArgsJSON` 进 `action_events` 底账；
- 仍受合同写范围 + 检查点 + 真实 diff + 越界回滚约束；
- 用例锁定"理由太短也拒绝"（避免模型用 `"x"` 敷衍）。

**证据**：`TestSemanticEnforceRejectsMissingSemanticKind`、`TestSemanticEnforceControlledLiteralChannelRequiresRationale`、`TestHarnessReacceptanceSemanticEnforceRejectsLiteralEdit`（原失败用例）。

### P0-2：事件分型——快照类与迁移类必须分开

**问题**：`settleLogicalTask` 用 `LogicalEventRefined` 做 active → awaiting_verification，而通用 `Transition` 不填 payload，重放时 `json.Unmarshal("")` 直接失败。事件底账与投影不一致（**事实源被破坏**）。

**修复**（三处，缺一不可）：

1. **新增事件类型** `LogicalEventAwaitingVerification = "awaiting_verification"`（纯状态迁移，无合同替换语义），结算改用它；
2. **`ApplyEvent` 显式区分**：`IsContractSnapshotEvent(kind)` 为真时 payload 为空 → 报错（"坏事件"不得静默跳过）；迁移类只改状态；
3. **`Transition` 防御性兜底**：调用方误传快照类 kind 时，自动补全量合同 JSON（写侧补全 > 产生不可重放事件）。

PG 实现（`store/logical_task_store.go`）走同一 `team.LogicalTaskEvent.Payload` 语义，无需额外改动；真库未跑，属静态确认。

**证据**：`TestSettlementTransitionReplays`（写入→立即重放，投影/状态/revision/hash 全等）、`TestTransitionWithSnapshotEventCarriesContract`、`TestApplyEventRejectsEmptySnapshotPayload`、`TestHarnessReacceptanceSettlementEventsCanReplay`（原失败用例）。

### P0-3：执行后权威审计失败不得静默成功

**问题**：只有授权与检查点用 `emitCritical`；`executed`/`mutation_observed`/`scope_verified`/`committed` 忽略 `emit` 错误——文件已改、底账缺行，却仍返回 `Success=true`。

**修复**（`domain/tool/action_pipeline.go`）：

- 新增 `emitAfterExecution`（= enforce 下必须成功的 `emitCritical`），覆盖 executed / mutated / scope_ok / committed；
- 新增 `auditLostOutcome`：审计丢失时返回 `Success=false` + `Category=execution_failed` + 保留 `Path`/`Output`（人工恢复靠它定位），错误文案明确"本次结果不可信，需人工核对变更并恢复底账"；
- `Outcome.RolledBack` 保持 `false`（不能把"审计失败"说成"已回滚"）；
- shadow/off 语义不变（仍只记日志）。

**边界如实记录**：文件确实已被改，系统无法自动证明"改了什么/该回滚什么"——所以此处选择**降级 + 人工恢复**，而不是假装回滚。

**证据**：`TestPipelinePostExecutionAuditFailuresBlockSuccess`（executed / mutation_observed / scope_verified / committed 四个子用例逐个注入失败，并断言磁盘确实已被写）、`TestPipelineShadowPostExecutionAuditFailureKeepsResult`、`TestHarnessReacceptanceCommitAuditFailureCannotReturnSuccess`（原失败用例）。

### P0-4：路径识别必须有可靠边界

**问题**：`修改src/a.css的间距` → 文件 `修改src/a.css` + 目录 `修改src/**`。两个根因：

1. 正则把 CJK 全部并入路径体，中文动词直接被吃进路径；
2. 目录 token 判定只看"以 `/` 结尾"，把 `src/`（文件路径中间的分隔符）当成目录授权。

**修复**（`team/scope_resolver.go` 重写）：

| 环节 | 规则 |
|---|---|
| 文件 token | 扩展名锚点反向回扫，**逐 rune**（全角标点/括号/引号终止）；不跨越前一个锚点末尾（`a.css和b.vue` 不会被吃成一个） |
| 边界修复 | 前导汉字段后紧跟 ASCII 路径字符 → 中文动词前缀，剥离；紧跟 `/` → 真实中文目录名，保留 |
| 目录 token | 必须**独立**：`/` 后不接路径字符才算目录；带 workDir 时必须真实存在 |
| 存在性校正 | 候选不存在 → 按 **rune 边界**取最长存在后缀（`改一下文档/样式/a.css` → `文档/样式/a.css`） |
| 安全边界 | 绝对路径 / 盘符 / `..` 一律拒绝；解析不到任何资源 → `Ambiguous`，写范围保持空（写入被拒） |

**证据**：`scope_resolver_test.go` 12 个用例（中文无空格、多文件、真实中文目录、中英混写、空格/全角括号/反引号、独立目录、不存在目录不授权、绝对/上跳路径、否定句进 Excluded、拟新建、无路径歧义、候选越界丢弃、边界单元规则）+ `TestHarnessReacceptanceChinesePathScopeIsExact`（原失败用例）。

**仍存在的解释边界**（报告点名，如实回答）：只说"改那个标题/间距"、不给路径时，resolver 仍返回 `Ambiguous`、写范围为空、enforce 下写入被拒。这是**有意为之**（宁拒绝不猜），闭环要靠 repo map + 语义目标候选 + 必要澄清——见 §7 未完成项，不能靠扩大写范围解决。

## 2. P1 级返修

### P1-1：复验以"新目标 + 新值"为 oracle

旧实现在应用后重新定位**旧**目标，且把所有复验错误当成功返回（`if err == nil { ... }`）——等于没有复验。

新实现（`domain/tool/semantic_edit.go` 的 `applySemanticEdit` / `verifySemanticEdit`）：

1. **未修改区域校验**：用 plan 的字节范围切 `前/编/后`，`out` 必须严格等于 `前 + NewText + 后`；
2. **新值 oracle**：把 `ExpectedValue` 换成 `NewValue`（模板节点换成 `Text=NewValue`、清空 anchor）重新定位，必须**唯一命中**；
3. **任何错误 fail closed**：worker 崩溃、解析失败、目标消失、歧义、新值未命中，一律 `post_edit_verification_failed`，不再"错误当成功"。

**证据**：`TestSemanticEnforceVerifiesNewValue`、`TestApplySemanticEditFailClosedOnVerifyError`、`TestSemanticEditEnforceAppliesMinimalTextEdit`（原有正例仍绿）。

### P1-2：接受必须按交付事实选任务

旧实现 `tasks[len(tasks)-1]`——`ListTasks` 按 revision 排序，旧任务被多次 refine 后 revision 更大，会选中已 superseded 的旧任务。

**修复**：

- `LogicalTaskStore` 新增 `FindAcceptable(ctx, sessionID)` 接口语义：**状态必须是 verified / delivered-unverified**，按创建/交付顺序取最新；
- 内存实现倒序遍历创建顺序（`m.order`）；PG 实现 `ORDER BY updated_at DESC, created_at DESC WHERE status IN (...)`；
- 新增 `TaskAcceptsUserDecision(status)` 作为唯一判定，`AcceptResult` 不再用数组末尾；
- `AcceptResult` 还新增"active 但状态不可接受"也走 `FindAcceptable`（此前 active 且尚未交付会被直接 Accept 掉）。

**证据**：`TestFindAcceptablePicksByDeliveryFact`（旧任务 revision=3 且 superseded，新任务 revision=1 且已交付 → 必须选中新的）、`TestFindAcceptableSkipsFailedAndActive`、`TestTaskAcceptsUserDecision`。

## 3. Go→Node worker E2E 不稳定的真因

报告实测失败（`unexpected end of JSON input` / `read: EOF`），本地连跑 5～12 次全绿——**不是环境差异，是竞态**：

`callLocked` 用 goroutine 读 `bufio.Reader` 并配 `time.After` 超时。超时返回后，那个 goroutine **仍在读同一条管道**；下一次调用又起一个新 goroutine——两个读者互相偷行，于是随机出现"读到半行 JSON"/"读到 EOF"。ping 阶段（StartTimeout 15s）在冷启动时最容易踩到。

修复（`domain/edit/worker.go`）：

1. **超时即杀进程**（`w.stopLocked()` 后再返回），让孤儿 goroutine 立刻收到错误退出；
2. **每次读取绑定局部 reader**（不再读 `w.stdout` 字段，避免 `stopLocked` 置 nil 造成字段级数据竞争）；
3. **空行跳过**而不是当响应解析（node/shim 偶尔抖一行空行），并带 deadline 上限；
4. **解码失败附原文片段 + worker stderr 尾**（`previewLine` / `withStderr`），不再只有一句无解的 JSON 错误。

**验证**：`go test ./internal/domain/edit -run TestWorker -count=1` 连续 12 次全部 ok；`-a`（禁缓存）重建同样通过。

同时把 `isWorkerUnavailable` 的判定与"业务错误不重试"分开保留，崩溃重启路径仍只有一次。
