## 1. P0 级返修

### P0-1 受保护目录的观察通道

**问题**：`checkpoint` 默认整目录排除 `.bma`，管线却只在快照 diff 里查 `.bma/verification`。
被排除的目录永远不进 manifest → Shell 改完验收规则后事务报告"零变更"。

**修复**：

- `checkpoint.Store` 新增强制观察清单（`WithForceInclude` / `AddForceInclude`），
  优先级高于排除清单：父目录被排除时仍向下遍历命中路径；
- 检查点自身存储（`<dir>`、`.bma/checkpoints`）永远排除，避免快照自我嵌套膨胀；
- `NewActionPipeline` 构造时把 `Protected` 目录自动注入 `forceInclude`——
  保护声明与观察能力从此绑定，不会再出现"声明了保护但看不见"。

**证据**：`checkpoint_guards_test.go::TestForceIncludeSeesProtectedDirsUnderExcludedParent`、
`TestForceIncludeExcludesOwnStorage`、`TestAddForceIncludeAfterConstruction`；
`test/coding/harness_acceptance_review_test.go::TestHarnessAcceptanceReviewProtectedShellMutation`（原失败用例）。

### P0-2 空/未知写范围不得被信任模式扩权

**问题**：两层叠加 —— 生产入口构造合同从不解析资源（WriteSet 恒空），
而 full-auto 又把 `ask` 一律当批准，于是"合同未知"等价于"任意写权限"。

**修复**：

1. `Authorization.EscalationNeeded`（范围未知/越界）**永不被信任模式自动批准**；
   只有合同里显式 `ask` 规则产生的确认才可被 full-auto 放行（`approvalSatisfied`）。
2. Shell/写入类动作在 WriteSet 为空时**执行前即拒**（不再"先写后回滚"）。
3. 新增 `team.ResolveScope`：从用户原话确定性解析写范围（文件/目录/`不要动 X`），
   `ensureLogicalTask` 创建/细化合同时写入 `WriteSet`/`ExcludedSet`；
   用户纠正时 `ReplaceWriteSet` 收回旧范围（避免"只扩权不收口"）。

**证据**：`action_test.go::TestPipelineFullAutoCannotApproveScopeEscalation`、
`TestPipelineExplicitAskRuleStillAutoApproved`；`team/scope_resolver.go`；
`test/coding/...ReviewEmptyWriteSetFailsBeforeExecution`（原失败用例）。

> 遗留（明确记录）：`ResolveScope` 是**规则解析**（用户原话里的路径/目录），
> 不做语义目标推断（"收货人标题"→具体模板节点仍需 worker/模型解析）。
> 解析不到时合同保持空写范围 → 写入被拒并提示补全，符合"宁拒绝不猜"。

### P0-3 证据必须与规则同 Kind 且绑定版本

**问题**：只按规则 ID 取证据，`rule-gap`（要求 DOM）拿到同 ID 的 static 证据即 verified。

**修复**：

- `evidenceKindSatisfies`：证据种类必须等于规则种类；唯一兼容是
  `integration` 规则接受 `api` 证据；`static` 永远不能满足 `dom/visual/unit/integration`；
- `Evidence` 新增 `TaskID/Revision/ContractHash/Collector/Artifact` 绑定字段，
  提供方声明了就必须与当前合同一致，否则记为陈旧证据（缺口）；
- `BuildOnlyWarning` 口径改为"已满足的必需规则全是 static 且仍有未满足规则"。

**证据**：`team/acceptance_eval.go` + 新增 `evidenceKindSatisfies`/`evidenceBindingMismatch`；
`team/acceptance_runner_test.go`；`test/coding/...ReviewEvidenceKindMustMatchRule`（原失败用例）。

### P0-4 失败任务不得进入 accepted

**修复**：`statusTransitionAllowed` 中 `failed/cancelled` 只允许 → `active`（显式重新激活）
或 → `superseded`；`accepted` 仍只接受 `verified/delivered-unverified`。

同时补上验收要求的**正常链路**：新增 `ReactService.settleLogicalTask`，
会话收尾按确定性规则推进（成功 → `delivered-unverified`；出错 → `failed`），
再进 Evolver 闸门。此前任务永远停在 `active`，`/accept` 无法使用、学习闸门永远阻断。

**证据**：`team/logical_task_test.go::TestStatusTransitions`（扩展）；
`test/coding/...ReviewFailedTaskCannotBeAccepted`（原失败用例）；
`agent/logical_task.go::settleLogicalTask`（在 `evolveSession` 之前调用）。

### P1-1 漂移判定覆盖存在性/类型/symlink/hash/mode

**修复**：新增 `externalDrift`，逐维度比较 after 快照与当前磁盘：

- 文件被外部删除（`Lstat` 不存在但 after 里有）→ 漂移，**不重建**；
- after 里没有却出现在磁盘上 → 外部新增，漂移；
- 文件类型/symlink 变化、内容 hash 变化、权限 mode 变化 → 漂移；
- `Lstat` 因权限/IO 失败 → 保守当作漂移（宁可不恢复也不覆盖未知状态）。

**证据**：`checkpoint_guards_test.go::TestExternalDeletionIsDrift`、
`TestExternalAppearanceIsDrift`、`TestModeOnlyChangeIsDriftAfterRestore`；
`...ReviewExternalDeletionIsDrift`（原失败用例）。

### P1-2 只有全部恢复到位才算 rolled_back

**修复**：`RestoreReport.Complete()` + `rollbackOutcome()`——
`Failed/Unavailable/Drifted` 任一非空或 restore 报错 → `manual_recovery_required`，
`out.RolledBack=false`，工具错误里附恢复明细；不再"部分回滚却声称已回滚"。

**证据**：`checkpoint_guards_test.go::TestRestoreReportCompleteSemantics`；
`action_test.go::TestRollbackOutcomeRequiresCompleteRestore`。

### P1-3 合同系统故障必须 fail closed

**修复**：`ActionPolicy.RequireContract`（bootstrap 由 `logical_task_mode=enforce` 派生）：
合同为 nil 时不再按 legacy 放行，而是 deny 并给出可恢复原因。
真正的 legacy（未启用合同系统）行为不变（有独立用例锁定）。

**证据**：`action_test.go::TestPipelineRequireContractFailsClosedWhenContractMissing`、
`TestPipelineLegacyWithoutRequireContractStillWorks`。

### P1-4 合同块按字段结构化装配

**修复**：`RenderContractBlock` 重写——安全段（header/Goal/WriteSet/ExcludedSet/
active 不变量含完整 ID 与期望值/纪律）先占预算且**永不裁剪**；
只有展示细节（目标资源列表、验收规则摘要）按剩余预算逐条取舍（整条跳过，不截半行），
超限时输出"另有 N 条展示细节未入预算（安全约束已完整注入）"。

**证据**：`test/coding/...ReviewContractBlockKeepsSafetySections`（原失败用例）。

### P1-5 审计失败、外部副作用与并发

- **审计**：`emit` 返回错误，`emitCritical` 在 enforce 下把授权/检查点事件写失败当阻断失败
  （shadow 保持"只记日志"不改变旧行为）；
- **外部副作用**：`resolveRequestedResourcesWithCaps` 把 `network`/`database`/
  `external_side_effect` 解析成独立 `ResourceRequest`（不再混进文件写），
  回滚失败/无法判定时事件标 `external_side_effects_not_reverted`；
- **并发**：blob 临时文件名改为 `<hash>.tmp-<pid>-<seq>` 且 rename 竞争视为成功；
  新增并发用例（并发快照同工作区 ID 稳定、并发写同一/不同 blob 不损坏、无 tmp 残留）。

**证据**：`action_test.go::TestPipelineEnforceRefusesWhenAuditUnavailable`、
`TestPipelineShadowToleratesAuditFailure`、`TestResolveResourcesClassifiesExternalEffects`；
`checkpoint_concurrency_test.go`（3 个用例）。

## 3. WP4 语义编辑接入生产路径

**新增** `backend/internal/domain/tool/semantic_edit.go`，`EditFile` 在生产路径上
按 `agent.semantic_edit_mode` 分支：

| 模式 | 行为 |
|---|---|
| `off`（默认） | 完全不介入，与改造前逐字节一致 |
| `shadow` | 仍走旧字面替换，额外跑一遍 worker 并把定位结果/偏差写进结果输出 |
| `enforce` | 必须由 worker 定位唯一目标并生成单条 TextEdit；失败 fail closed，**不回退字面替换** |

管线：`EditFile(semantic_*)` → worker 定位 → 指纹校验 → 单条 TextEdit 应用 →
写盘 → 仍经 Action 管线授权/检查点/真实 diff/回滚。

同时修掉的真实缺陷：

- **Go 客户端死锁**：`startLocked` 在持锁状态下调用 `callLocked`（后者再取同一非重入锁），
  实际表现就是验收报告里的 `semantic-edit: read: EOF`。拆成"起进程"与"ping"两步；
- **环境白名单误删版本管理器变量**：旧实现只保留 10 个变量，volta/fnm/nvm-windows
  的 shim 定位不到真实 node 就立刻退出。改为**黑名单剔除**（`NODE_OPTIONS`、
  `NODE_EXTRA_CA_CERTS`、`NODE_TLS_REJECT_UNAUTHORIZED` 等代码注入面），其余继承；
- **stderr 不再丢弃**：管道写满会阻塞 worker，且进程早退时的 stderr 是唯一诊断证据；
  现在后台消费并保留尾部 4KB，附在错误里。

**证据**：`backend/internal/domain/edit/worker_test.go`（含端到端 CSS 计划，现已通过）；
`backend/internal/domain/tool/semantic_edit_test.go`（7 个用例：off 透明、enforce 最小编辑、
无 worker fail closed、目标歧义拒绝、指纹过期拒绝、shadow 保留旧写、批量拒绝）。

**证据采集侧**（同步修复）：`configureSemanticEdit` 按模式装配 worker，
路径缺失只告警——enforce 下每次 EditFile 都会返回可诊断错误（不会静默降级）。
