# 共享记忆一致性改进计划

> 多 Agent 协作体系下，文件读写记忆的缓存一致性方案。本文档为规划稿，落地条目见 `doc/TODO.md` 第 9 项。

## 1. 问题本质

多 Agent 共享文件系统 ≈ CPU 多核共享内存。核心矛盾：

| CPU 多核 | 多 Agent 协作 |
|---|---|
| 多核心共享内存总线 | 多 Agent 共享 workspace/ |
| L1/L2 缓存 | LLM 上下文（"认知缓存"） |
| 缓存未命中 → 访问主存（昂贵） | 上下文未命中 → 读文件（token 昂贵） |
| 缓存脏读 → 过时数据 | 上下文过时 → 基于旧文件决策幻觉 |

不是"要不要缓存"，是"缓存的失效策略是什么"。

## 2. 当前 BMA 状态

```
Scheme 1 (Fresh Read)   部分 ── ReadFile session 级 dedup，但无 mtime 校验
Scheme 2 (Blackboard)   雏形 ── sharedKV 当黑板，但存的是摘要文本不是文件
Scheme 3 (MESI)         缺失 ── 无版本号、无失效广播
Scheme 4 (CRDT)         不适用
```

**关键 gap**：`sharedKV` 存的是 `path+line+signature+结论` 的自由文本摘要。子 Agent 改了文件后，KV 仍持有旧摘要 → 父 Agent 下次派发仍把旧摘要注入新子 Agent task → 幻觉。

涉及代码：

- `backend/internal/domain/memory/kv.go` - `InMemoryKV`，无版本/失效机制
- `backend/internal/domain/tool/shared_memory.go` - `WriteSharedMemory`，content 是自由文本
- `backend/internal/domain/subagent/dispatcher.go:757` - `injectKVMemory` 拼接前缀，不校验 staleness
- `backend/internal/domain/tool/registry.go` - `WriteFile` 成功后无 hook
- `backend/internal/domain/tool/builtin.go` - 无文件 mtime 记录

## 3. 业界方案对比

| 方案 | 代表 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| Fresh Read | Claude Code `context_files`、Thane `inject_files` | 零一致性风险 | token 爆炸 | 小文件、低频、强一致 |
| File Blackboard | 单写多读编排器 | 写冲突根本消灭 | 需编排器仲裁 | 绝大多数多 Agent 编码 |
| MESI 版本号+失效广播 | `agent-coherence`（token 节省 84~95%） | token 效率最高 | 实现复杂 | 大规模、高并发、长会话 |
| CRDT | `agentcrdt` | 支持并发写 | 工程极复杂；代码文件不可合并 | 结构化知识库 |

## 4. 选定方案

**Scheme 2（File Blackboard）为主 + Scheme 3 lite（版本戳 + 写后失效）**。

理由：

- BMA 已有 Scheme 2 雏形（workspace/ + sharedKV），缺的是失效信号
- 完整 MESI 状态机在 LLM 场景下收益不抵复杂度（Agent 间消息秒级 vs CPU 核心纳秒级）
- CRDT 对代码文件不可行

## 5. 落地分层

### Layer 1: WriteSharedMemory 结构化 + path 反查（最小可行）

**改动**：

- `WriteSharedMemory` 入参从 `content: string` 改为结构化 JSON：
  ```go
  type writeSharedMemoryInput struct {
      Files   []string `json:"files" description:"本次共享记忆涉及的文件路径列表"`
      Content string   `json:"content" description:"关键上下文摘要：路径/行号/签名/前置结论/验收标准"`
  }
  ```
- KV value 存 JSON：`{"files": [...], "content": "...", "mtime": {"path1": 1690000000}}`
- `WriteSharedMemory.Execute` 调用时 stat 各 path 记录 mtime

**收益**：为后续失效提供 path 反查索引。当前自由文本无法精确知道哪条 entry 引用了哪条 path。

**工程量**：1 天

### Layer 2: WriteFile hook 失效 KV

**改动**：

- `Registry.Dispatch` 中 `WriteFile` 成功后调用 `invalidateSharedMemoryForPath(path)`
- 失效逻辑：遍历 sharedKV（需暴露枚举接口或维护反向索引），删除引用该 path 的 entry
- 失效不删整条 entry，而是清空其 content 并标记 stale，下次 inject 时丢弃

**收益**：写后立即失效，下次派发子 Agent 不会拿到旧摘要。

**工程量**：半天（含反向索引设计）

### Layer 3: 版本戳 stat 校验（MESI lite）

**改动**：

- KV entry 携带 `mtime` map（Layer 1 已记录）
- `Dispatcher.injectKVMemory` 拼接前 stat 各 path 对比 mtime
- 任一 path mtime 不匹配 → 丢弃 KV 内容，降级为 fresh read（task 不拼前缀）

```go
func (d *Dispatcher) injectKVMemory(ctx context.Context, parentID, task string) string {
    if d.kvMemory == nil {
        return task
    }
    val, _ := d.kvMemory.Get(ctx, parentID+":shared")
    if val == "" {
        return task
    }
    var entry SharedEntry
    if json.Unmarshal([]byte(val), &entry) == nil {
        for path, stamped := range entry.Mtime {
            fi, err := os.Stat(path)
            if err != nil || fi.ModTime().Unix() != stamped {
                return task  // stale，丢弃
            }
        }
    }
    return kvMemoryKeyPrefix + entry.Content + "\n\n【当前任务】\n" + task
}
```

**收益**：每次派发 stat 几个文件，远低于重读全文；防 Layer 2 hook 漏写（如子 Agent 直接调 os.WriteFile 不经工具）。

**工程量**：半天

### Layer 4: 角色写目录分区（架构级，治本）

**改动**：

- `roles.yaml` 给每个角色配独立写目录：
  ```yaml
  fixed_roles:
    - id: code_assistant
      sandbox:
        allowed_write_paths: ["artifacts/code/"]
    - id: test_assistant
      sandbox:
        allowed_write_paths: ["artifacts/test/"]
  ```
- 共享文件（如 `status.md`）仅 MetaAgent 可写
- `SandboxConfig.AllowedPaths` 已支持，扩展为按角色区分

**收益**：从源头消灭写冲突，跨域读写靠文件黑板而非 KV。KV 失效只需关心"谁改了谁的领域"。

**工程量**：2-3 天（含 roles.yaml 重构 + sandbox 适配 + 测试）

### Layer 5: Mailbox 完成消息携带 dirty 文件列表（可选）

**改动**：

- `mailbox.Message` 增加 `FilesModified []string` 字段
- `Dispatcher.runSubAgent` 完成后从 `result.History` 提取 WriteFile 调用记录，填入 Mailbox 通知
- 父 Agent Drain 邮箱时失效 KV 中相关条目

**收益**：定向失效（MESI 的 RFO 对应），比 Layer 2 的写时广播更精确。

**工程量**：1 天

## 6. 落地优先级

| 步骤 | 收益 | 工程量 | 优先级 |
|---|---|---|---|
| Layer 1: WriteSharedMemory 结构化 + path 反查 | 高 | 1 天 | P0 |
| Layer 2: WriteFile hook 失效 KV | 高 | 半天 | P0 |
| Layer 3: 版本戳 stat 校验 | 中 | 半天 | P1 |
| Layer 4: 角色写目录分区 | 高（架构级） | 2-3 天 | P1（独立立项） |
| Layer 5: Mailbox dirty 文件上报 | 中 | 1 天 | P2 |

建议先做 Layer 1 + 2，验证有效后补 Layer 3。Layer 4 治本但需改 roles.yaml + sandbox + 测试，单独立项。

## 7. 不要做的事

1. **不做完整 MESI 状态机** - 4 状态 + 定向失效广播在 LLM 场景下收益不抵复杂度
2. **不 KV 存文件全文** - 等于把 LLM 上下文搬到 KV，没解决问题反而放大
3. **不依赖 LLM 自觉失效** - 提示词里写"如果文件改了请重读"不可靠，验证闭环已是这个教训
4. **不 CRDT 代码文件** - 三路合并都难，CRDT 更不行

## 8. 业界参考

- **Claude Code `context_files`**: Scheme 1 倾向，每次注入时读盘，靠 mtime 决定是否重读。简单可靠，适合文件少场景
- **Cursor Agent `@file` 显式引用**: 用户/Agent 显式 attach 文件到上下文，文件改了立即重读。本质是 Scheme 3 但失效信号是人显式触发
- **Aider repo map**: 不存全文，存 AST 摘要（类/函数签名树）。摘要变更时重新生成。可借鉴 ── BMA 的 sharedKV 摘要配 mtime 戳，相当于 LLM 级 repo map 的 cache invalidation
- **OpenAI Swarm handoff**: 不缓存，每次 handoff 重新传上下文。Scheme 1 极端版
- **agent-coherence 项目**: CPU MESI 协议直接映射到多 Agent 工件同步，工件=缓存行，Agent=核心，LLM 上下文注入=内存读取。每个工件对每个 Agent 都有一致性状态（M/E/S/I）。写入触发定向失效。Token 节省 84~95%
- **agentcrdt 库**: 多 Agent 并发写入同一份共享状态，按 `(domain, entity, attribute)` 内容寻址，版本号+时间戳仲裁。适合结构化事实，非源代码

## 9. 当前 BMA 已具备的基础

- `sharedKV` 进程级单实例（`bootstrap.go:243`），无需引入新存储
- `SharedMemoryStore` / `KVMemoryReader` 接口分离已就位，扩展不破坏现有依赖
- `ReadFile` session 级 dedup（`registry.go:313`）可复用 path 跟踪逻辑
- `WriteFile` 经 `Executor.writeFile`，hook 注入点明确
- `Dispatcher.injectKVMemory` 是单一注入点，加 stat 校验改动小
- `mailbox.Message` 已有 `ReplyTo`/`ThreadID`，加 `FilesModified` 字段是增量

## 10. 风险与回退

- **Layer 1 改入参 schema**：旧调用方传 `content` 字段会失效。需保证向后兼容（`files` 可选，缺省时退化为旧逻辑）
- **Layer 2 反向索引**：增加 sharedKV 复杂度，可能引入死锁。反向索引单独 mutex，不与 KV 主锁嵌套
- **Layer 3 stat 开销**：每次派发多 N 次 syscall，N 通常 < 5，可接受
- **Layer 4 角色写目录**：可能破坏现有 e2e 测试（如 snake 用例 code_assistant 直接写主目录）。需配套改测试 fixture
- **回退策略**：每层独立，可单独开关。`config.shared_memory_invalidation_enabled`（默认 true），出问题可关闭回退到当前行为
