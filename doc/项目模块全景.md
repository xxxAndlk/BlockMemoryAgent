## 1. 项目定位

BlockMemoryAgent 是一个以 Go 为后端的多 Agent 编排与执行系统。核心不是工作流图框架，而是：

- 单一 ReAct 执行循环，按角色绑定模型与工具；
- 主 Agent 通过 `call_sub_agent` 异步递归派发子 Agent，Mailbox 回传结果；
- 会话、消息、事件、Agent 树、长期记忆与多类运行状态持久化；
- HTTP Web UI、Bubble Tea TUI、Windows 桌面外壳三类交互入口；
- 在通用会话之外，提供 Goal/Loop 指令、可视化 Flow、批量生产 Workflow 三种不同粒度的编排能力；
- 插件、MCP、外部 Agent、技能、用户画像、项目偏好和长期记忆构成扩展与上下文治理层。

“Block Memory”是项目历史名称的一部分。当前 `agent.block_memory_write_enabled: false`，旧块记忆自动沉淀已默认停用，但数据模型、检索接口和兼容代码并未全部删除。当前长期记忆治理应以 `long_term_memory_items/events` 为准，不能继续按早期块记忆说明理解系统。

### 3.1 通用会话主链

1. Web/TUI 创建会话，`ReactService` 按 `fast/daily/cluster` 选择顶层角色，绑定工作目录、模型、工具和运行时上下文。
2. `ReActAgent` 组装系统前缀、压缩历史、当前指令、决策账本和动态上下文，调用角色模型。
3. 模型可直接回答，也可调用文件、命令、HTTP、Git、插件、Widget、Workflow 等工具。
4. `call_sub_agent` 进入 Dispatcher；子 Agent 拥有独立 ReAct 上下文，父 Agent 通过 Mailbox 接收摘要与失败信息。
5. 看板、Agent 树、任务台账和事件流分别承担计划展示、层级状态、派发账目和实时可观测性，不能互相替代。
6. 会话完成后可进入 Goal 评估、Loop 排程或经验候选生成；长期记忆是否实际写入由 `memory.write_mode` 决定。

### 3.2 三种编排能力不要混淆

| 能力 | 编排单位 | 真相源 | 适用场景 |
|---|---|---|---|
| 普通会话／子 Agent | ReAct 回合与 Agent 树 | 会话、消息、事件、树等数据表 | 开放式研究、编程、多 Agent 协作 |
| Goal／Loop | 一个会话的后续回合 | `session_directive`、`goal_reminders` | 目标未达成续跑、周期性执行、延迟跟进 |
| Flow | 有向节点图的一次运行 | `.bma/flows/*.json` + `flow_runs`、`flow_node_runs` | 确定的 LLM／工具／分支／审批流程 |
| Workflow | 名册中的“件 × 阶段”单元 | `.bma/workflows/*.yaml` + `workflow_runs`、`workflow_units` | 多阶段、多产物、带人审的批量生产 |
| DAG | 定时任务及依赖 | `dag_jobs` 等调度数据 | cron／间隔触发及任务依赖 |

Flow 与 Workflow 都是现行实现，但语义、状态机和存储不同，不应合并成一套文档或一套 API。

## 4. 核心大包内部职责

### 4.1 `internal/agent`：会话与 ReAct 核心

| 职责 | 主要代码锚点 | 边界说明 |
|---|---|---|
| Agent 核心循环 | `react_agent.go`、`react_types.go` | LLM → 工具 → 回填，历史裁剪、压缩、守卫、停滞与预算处理 |
| 会话服务 | `service_react.go`、`session_react.go`、`query_react.go` | 会话创建、发送、控制、恢复、查询、事件分发和依赖接线 |
| 执行引擎 | `engine.go` | ReAct、reflection、plan_execute 等执行方式及辅助评估 |
| 消息与历史 | `messages_store.go`、`memory_pipeline.go` | 完整消息、请求视图、压缩状态与历史恢复 |
| 会话经验演化 | `evolver.go`、`memory_lifecycle.go` | 偏好、项目经验、技能候选及 shadow/enforce 准入 |
| 长期记忆 | `memory_write_mode.go`、`memory_import.go` 等 | 生命周期、迁移、撤回、隔离、恢复和防复活 |
| 决策与指令 | `decision_ledger.go`、`decision_axes.go`、`directive.go` | 多轴用户决策注入、Goal 接口、不可被压缩掉的指令锚 |
| 上下文组成 | 项目、看板、台账、画像、技能、附件、媒体相关文件 | 将多种来源编排进模型上下文，不等于这些数据都由 agent 包持有 |

**修改原则**：会话状态与单次 ReAct 状态不要混放；持久化细节应留在 `store`；派发策略留在 `subagent`；具体工具执行留在 `tool`。`agent` 已承担较多横切职责，新功能应先判断是否能通过窄接口挂接。

### 4.2 `internal/domain/subagent`：派发与生命周期

| 职责 | 主要代码锚点 | 边界说明 |
|---|---|---|
| 派发主控 | `dispatcher.go` | 参数与权限校验、并发、树注册、工具装配、执行、暂停、恢复和父子生命周期 |
| 驻留与复用 | `idle_pool.go` | DomainAgent 热驻、冷恢复、TTL、复用和容量管理 |
| 计划确认 | `plan.go`、`plan_confirm.go` | 执行前计划提交、上级裁决和修订 |
| 验收与校验 | `acceptance.go`、`verify_levels.go` | 验收条目、分层校验、未验证状态及反馈 |
| 工作区隔离 | `worktree.go`、`merge_worktree.go` | Git worktree 副本、patch 生成、漂移检查和合并门 |
| 状态留痕 | `task_ledger.go`、Mailbox 相关文件 | 派发账目、回传和父子通信 |
| 失败处理 | `salvage.go`、`failure_prune.go`、`deadletter.go` | 结果打捞、失败裁剪、死信与部分产出 |
| 兼容路径 | `blackboard_uptake.go` 等 | 与旧块记忆／黑板相关的保留逻辑，不应误判为当前主写入链 |

`dispatcher.go` 单文件约七千行，是理解并发与生命周期时的核心，也是最高风险修改点。树、看板、台账、Mailbox 各自有独立语义；调整其中任何一个都要检查父子终止、重启恢复和迟到消息。

### 4.3 `internal/domain/tool`：工具注册、执行与扩展

| 职责 | 主要代码锚点 | 边界说明 |
|---|---|---|
| 注册与调度 | `registry.go` | Schema、Dispatch、可见性、挂载、角色授权和守卫链 |
| 内置执行器 | `builtin.go`、`executor.go` | 文件、目录、命令、搜索、HTTP、Git 等基础能力 |
| 安全 | `sandbox.go`、`guards.go`、`destructive.go` | 工作区边界、路径白名单、命令黑名单、破坏性操作审批 |
| 协作上下文 | 共享 KV／Spec、`ask_user`、消息相关工具 | 主从 Agent 规格共享、澄清和协作 |
| 任务与扩展 | 定时、跟进、外部 Agent、插件、挂载、tool forge | 把系统能力以统一工具协议暴露给模型 |
| 展示与生产 | Widget、产物展示、Workflow、记忆检索等 | 由装配层和 Dispatcher 继续补充角色可用工具 |

当前不能再写“14 个内置工具”。`NewBuiltinRegistry` 已包含文件、命令、HTTP、Git、共享记忆／Spec、提问、定时与跟进、gear、画像、知识检索、插件、挂载、Widget、工具锻造、外部 Agent 等多类工具，Dispatcher、角色和 Workflow 还会继续注册。角色真正可调用集合由注册表、角色白名单、插件可见性和运行时授权共同决定；当前 `role_tool_gate_enabled: true`。

### 5.6 包依赖规则

当前静态内部 import 显示：

- `pkg/*` 不依赖 `internal/*`；`pkg/types` 只依赖 `pkg/enums`。
- `bootstrap` 是全知装配层，允许依赖各子系统；业务包不应反向依赖 bootstrap。
- `server` 是适配器，可调用 agent、store、plugins、flow、goal、workflow，不应成为领域状态的权威持有者。
- `domain/memory` 依赖 `agent` 的接口，`domain/subagent` 也依赖 `agent`；这不是“domain 全部位于最底层”的分层。
- `domain/tool` 依赖 config、project、widgets 等较少内部包，是多数执行能力的汇聚点。
- `agent` 直接依赖 store、userprofile、server/eventkind 等属于历史形成的边界，修改公共签名时必须同步检查这些调用方。
- 完整逐包依赖见 `workspace/package_inventory.md`；该文件是静态 import 盘点，不是 `go list` 实测结果。

## 7. 数据、文件与运行时真相源

### 7.1 主要持久化类别

| 类别 | 权威位置 | 说明 |
|---|---|---|
| 会话与完整消息 | `session_history`、`agent_messages` | 会话元数据、MetaMemory、可恢复消息历史 |
| 实时事件与日志 | `session_events`、`session_logs`、Redis 热数据 | SSE 回放、LLM I/O、结构化诊断 |
| 历史压缩 | `agent_compress_states` | 压缩包与恢复状态 |
| Agent 层级 | `agent_tree_nodes` | 树节点元数据、终态、恢复与取消依据 |
| 用户决策 | `session_decisions` | 多轴指令、来源消息、替换关系 |
| 长期记忆 | `long_term_memory_items`、`long_term_memory_events` | 当前状态投影 + 只追加审计流 |
| 会话看板 | `session_boards` | 整板 JSONB 快照，mutator 后 UPSERT，重启惰性恢复 |
| Goal／Loop | `session_directive`、`goal_reminders` | 指令模式、排程与触发状态 |
| Flow | `.bma/flows/<id>.json`、`flow_runs`、`flow_node_runs` | 定义文件 + run 定义快照 + 节点轨迹 |
| Workflow | `.bma/workflows/*.yaml`、`workflow_runs`、`workflow_units` | 配方文件 + run 配方快照 + attempt 历史 |
| 技能与插件 | `config/skills*`、`config/plugins*.yaml`、相关表与目录 | 文件和运行状态并存，按各自管理器处理 |
| 工作区运行产物 | `<workdir>/.bma/` | 工具输出、图片、流程、配方、worktree、项目索引等 |

迁移当前到 `019_long_term_memory_lifecycle.sql`。启动时的 `Ensure*Schema` 与顺序 SQL 迁移共同存在；改表时必须同时检查模型、读写路径、迁移和旧数据升级，不能只加一张 SQL。

### 7.2 配置边界

- `config/config.yaml`：基础设施、ReAct、记忆、工具、安全、调度、Workflow／Flow／Goal 等运行参数。
- `config/models.json` 与 `config/roles.yaml`：模型连接条目和角色绑定；密钥通过环境变量引用。
- `.env`：本地密钥与连接参数，不纳入文档或交付物。
- `config/plugins.yaml`、`config/plugins.d/`、`config/external_agents.yaml`：扩展进程和外部 Agent。
- `config/soul.md`、`config/user_profile.md`、项目偏好文件：人格、画像和项目上下文；部分文件会由治理流程更新。
- `<workdir>/.bma/tester.yaml`：项目级测试助手配置，不是全局 `config.yaml` 字段。

### 7.3 现役、默认关闭与兼容能力

| 状态 | 能力 | 当前口径 |
|---|---|---|
| 现役 | ReAct、异步子 Agent、HTTP/SSE、TUI、Web、持久化、插件、Goal、Flow、Workflow | 有生产接线和对应管理入口 |
| 默认开启 | 角色工具硬门、DAG、会话预热恢复、Domain 热驻、Spec 强制、计划确认 | 以当前 `config/config.yaml` 为准，可按配置调整 |
| 默认关闭 | 旧块记忆自动写入、启动 LLM 探测、部分插件、部分验证扩展 | 关闭不等于源码删除 |
| 影子模式 | 长期记忆自动写入、部分决策点 | 生成／记录候选，不直接改现行长期记忆或硬行为 |
| 强制执行 | 长期记忆撤回、角色工具白名单 | 当前配置分别为 `retraction_mode: enforce`、`role_tool_gate_enabled: true` |
| 保留兼容 | 块记忆检索／黑板、verifyloop、旧路由、部分旧存储和迁移 | 读代码时先找生产接线，不以“文件存在”推断主链启用 |
| 有限实现 | Flow 重试／失败分支、Workflow 像素评委与升级产物回收、Goal 唤醒保证 | 详见对应专题，不得夸大语义 |

## 8. 桌面、部署与运维

- Windows 桌面端位于 `backend/cmd/desktop`，WebView2 不可用时退化 Edge／Chrome 应用窗口，最后退化默认浏览器。
- 桌面壳先探测 `/api/health`，未就绪则按 `app/current.json` 启动对应版本 `bma-server.exe`；默认服务地址 `127.0.0.1:10010`。
- 关窗默认隐藏到托盘，后端继续运行；托盘“退出（停止后台）”才停止本安装目录的后端。
- `bma-app.ps1` 提供 `pack/install/update/deploy/start/stop/restart/status/rollback`，采用不可变版本目录与 `current.json` 指针。
- 配置、插件、workspace、logs 属于用户数据，安装／更新只补缺，不覆盖既有数据；打包排除 `.env`、模型密钥配置和运行时学习数据。
- 更新健康门禁同时校验 `/api/health` 和 `build.version`，失败回滚 previous，默认保留三个版本。
- Docker Compose 当前包含 PostgreSQL、Redis、open_design、minimax-media；computer_use 是按需 Docker transport 插件，不是常驻 Compose 服务。
- `minimax-media` 把 MiniMax 图像／视频协议适配成 open_design daemon 已支持的接口形状，是协议桥，不是通用媒体生成引擎。

详见 [20 桌面端与发布运维](技术逻辑/20-桌面端与发布运维.md)。
