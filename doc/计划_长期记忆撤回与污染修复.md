# BMA 长期记忆撤回与污染修复方案

- 状态：待实施
- 适用范围：`user_profile.md` 用户画像、`.bma/project_preferences.md` 项目约定与项目经验，以及它们向 MetaAgent、子 Agent 的注入链路
- 关联文档：`doc/计划_媒体动画与记忆质量修复.md`
- 核心问题：**用户已经在后续对话中推翻某条偏好或经验，旧条目却仍留在“现行记忆”中并反复注入。**

本文只改长期记忆治理，不要求更换 DeepSeek1017。会话内的多轴决策由 `018_session_decision_axes.sql` 和多轴账本负责，不能用它替代跨会话长期记忆的撤回机制。

---

## 1. 先给结论

要彻底解决这个问题，不能只在提示词里写“最新指令优先”，也不能只把自动记忆改成 `shadow`。必须同时具备以下五项能力：

1. **记忆条目化**：每条记忆有稳定 ID、作用域、主题键、来源、状态和验证状态，不能只有一行自然语言。
2. **撤回即时化**：用户说“以后不要 X”“这条经验不对”“改成 Y”时，在处理该消息的当轮撤回或隔离旧记忆，不等会话结束。
3. **撤回与写入解耦**：`memory.write_mode=shadow/off` 只禁止新候选进入现行记忆，不能禁止用户明确要求的撤回。
4. **注入只看有效视图**：`retracted/superseded/quarantined` 条目不进入任何 Agent 的 prompt；归档区只用于审计。
5. **永久防复活**：撤回记录独立于容量有限的 Markdown 归档；后续摘要、SessionEvolver、人工合并不得换个措辞把同一旧结论写回来。

目标流程：

```text
用户纠正
→ 找出受影响的记忆条目
→ 同主题替换 / 明确撤回 / 有争议先隔离
→ 持久化撤回事件并刷新有效视图
→ 下一次 LLM 请求不再包含旧条目
→ 后续自动沉淀经过撤回检查，不能复活旧结论
```

其中“有争议先隔离”很重要：不确定旧经验是否被推翻时，宁可暂时不注入，也不要带着可疑旧经验继续执行。

## 2. 当前实现为什么还会污染

### 2.1 已有修复是有效的，但只解决了一部分

当前代码已经具备：

- `memory.write_mode=off|shadow|enforce`，默认配置为 `shadow`：`backend/internal/agent/memory_write_mode.go:24-52`、`backend/internal/config/config.go:767-788`。
- 全局画像要求长期意图，一次性任务选择不应晋升：`backend/internal/agent/memory_write_mode.go:54-79`。
- 归档小节在注入时剔除：`backend/internal/agent/react_agent.go:274-280`。
- 子 Agent 的项目偏好也剥离“经验归档”：`backend/internal/domain/subagent/dispatcher.go:1653-1670`。
- 自动行有人工行保护、时间戳和来源会话：`backend/internal/userprofile/merge.go:18-30`。
- `018_session_decision_axes.sql` 已存在，会话内路线修改应按轴替换，不再一刀切。

这些改动应保留。问题不是“归档区仍然直接注入”，而是**已被推翻的内容没有可靠地从现行区撤回**。

### 2.2 撤回发生得太晚

`SessionEvolver` 在会话结束时才生成 `rejected`，再让 Merge 模型尝试归档旧行：

- `backend/internal/agent/evolver.go:173-266`
- `backend/internal/agent/evolver.go:382-428`

因此，用户在同一会话中纠正旧经验后，旧经验仍可能存在于后续多轮请求中。会话被取消、进程退出、提取失败或 Merge 失败时，撤回甚至可能永远不发生。

**要求：撤回必须上移到用户消息入口，不能依赖会话结束任务。**

### 2.3 `shadow/off` 同时阻断了撤回

当前 `evolveSession` 在 `shadow` 下于 `backend/internal/agent/evolver.go:222-228` 提前返回，注释也明确说明“否决归档同样跳过”。

这意味着：

```text
shadow 能阻止新污染
但用户明确否定旧经验时，旧经验仍然保持 active
```

必须把两个开关拆开：

```yaml
memory:
  write_mode: shadow       # 控制新候选是否自动晋升
  retraction_mode: enforce # 控制用户明确撤回；不得随 write_mode 关闭
```

`retraction_mode` 第一版可以只提供 `enforce`，配置保留给紧急回滚；不能因为 `write_mode=off` 就停止处理撤回。

### 2.4 自然语言整段 Merge 不是可靠的事务

`backend/internal/bootstrap/profile_extractor.go:78-104` 让模型输出整个小节的最终列表，`ApplyMerge` 再整体替换自动行。问题包括：

- 模型可能漏掉应保留的旧行；
- 可能把不冲突的行误判为冲突；
- 可能无法识别换措辞后的同一经验；
- 没有条目 ID，无法证明“用户撤回的正是这一条”；
- Merge 失败时主要把新增量写入归档，不能保证旧现行行已撤回。

LLM 可以帮助识别语义冲突，但**最终状态变更必须由 Go 代码按条目 ID 执行并校验**，不能让模型直接决定整段文件命运。

### 2.5 防复活只防“同文本”，且墓碑会淘汰

`backend/internal/userprofile/merge.go:305-333` 只按完全相同文本阻止归档行复活，语义近似仍依赖模型自律。

同时：

- 单小节自动行上限为 30：`backend/internal/userprofile/store.go:50-53`；
- 归档区默认只保留 20 条：`backend/internal/userprofile/store.go:47-48`；
- 老归档会由于容量控制被移除。

归档可以用于审计，但不能兼任永久撤回索引。否则旧墓碑被裁掉后，旧结论可能再次进入现行区。

### 2.6 “效果不好”不等于“所有相关经验都被推翻”

当前强否定词和尾部消息截取只能做粗粒度保护：`backend/internal/agent/evolver.go:430-490`。它既不能精确撤回，也可能过度撤回。

必须区分：

| 用户原话 | 正确动作 |
|---|---|
| “以后不要用视频抽帧，改成逐帧生成” | 替换同作用域、同主题的路线记忆 |
| “这个项目不要视频” | 只撤回/替换当前项目的路线，不改全局画像 |
| “这次不要视频” | 只写会话决策，不改变长期记忆 |
| “你做得太差了” | 标记当前成果未验收；不能直接删除无关偏好 |
| “单图 warp 能做奔跑这条经验是错的” | 撤回该经验，并阻止近似结论复活 |
| “跑步幅度还是太小” | 记录当前产物反馈，不必推翻整条制作路线 |

## 3. 目标记忆模型

### 3.1 每条记忆必须具备的字段

```text
id               稳定条目 ID
owner            数据归属，遵守项目 owner 约定
scope            user | project
project_key      项目规范路径/hash；scope=user 时为空
memory_key       主题键，如 response.language、animation.method
content          当前有效表述
status           candidate | active | quarantined | superseded | retracted
origin           human | explicit_tool | evolver | legacy_import
verification     unverified | verified | rejected
source_session   来源会话
source_message   来源用户消息 ID；无法确认时为空，禁止伪造
revision         乐观锁版本
created_at       创建时间
updated_at       状态/内容最后变更时间
```

`memory_key` 表示“同一件事”，不是简单关键词。例如：

```text
response.language
response.confirmation
project.package_manager
animation.method
animation.anchor_approval
asset.identity
```

通用的、互不排斥的工艺经验可使用 `lesson.<稳定主题>`；不能为了分类把不相关经验强行归到一个 key。只有同一 `scope + project_key + memory_key` 才允许自动替换。

### 3.2 状态语义

- `candidate`：shadow 候选，只供审阅，不注入。
- `active`：当前有效，可进入注入视图。
- `quarantined`：疑似过期、冲突或无法安全裁决，临时不注入。
- `superseded`：被同主题的新条目替换，不注入。
- `retracted`：被用户或管理员明确撤回，不注入。

`verified` 只表示证据状态，不能覆盖 `status`。一个 `verified` 的旧条目被撤回后仍然不得注入。

### 3.3 权威顺序

同一请求中按以下顺序裁决：

```text
最新真实用户消息
> 用户明确撤回/替换操作
> 当前会话多轴决策
> 当前项目人工约定
> 当前项目 active 且适用的经验
> 全局 active 用户偏好
> 历史摘要与工具记录
```

补充规则：

1. 项目级条目可在本项目覆盖同 `memory_key` 的全局条目，但不能泄漏到其他项目。
2. “这次/本次/当前”优先进入会话账本，不修改长期记忆。
3. 同一层出现无法裁决的冲突时，相关条目都转为 `quarantined`，不能简单以时间最新者获胜。
4. 摘要和工具输出没有长期记忆写入权，也没有撤回权。

## 4. 数据库与审计设计

新增 `migrations/019_long_term_memory_lifecycle.sql`。`evolution_log` 继续记录进化流水，但它只有文本摘要，不能承担有效记忆状态和精确撤回，因此不直接复用为唯一存储。

建议 DDL：

```sql
CREATE TABLE IF NOT EXISTS long_term_memory_items (
    id              TEXT PRIMARY KEY,
    owner           VARCHAR(64) NOT NULL DEFAULT '',
    scope           VARCHAR(16) NOT NULL,
    project_key     TEXT NOT NULL DEFAULT '',
    memory_key      TEXT NOT NULL,
    content         TEXT NOT NULL,
    content_hash    TEXT NOT NULL,
    status          VARCHAR(16) NOT NULL DEFAULT 'candidate',
    origin          VARCHAR(24) NOT NULL DEFAULT 'evolver',
    verification    VARCHAR(16) NOT NULL DEFAULT 'unverified',
    source_session  TEXT NOT NULL DEFAULT '',
    source_message  TEXT NOT NULL DEFAULT '',
    revision        BIGINT NOT NULL DEFAULT 1,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    CHECK (scope IN ('user', 'project')),
    CHECK (status IN ('candidate', 'active', 'quarantined', 'superseded', 'retracted')),
    CHECK (verification IN ('unverified', 'verified', 'rejected')),
    CHECK (scope = 'project' OR project_key = '')
);

CREATE UNIQUE INDEX IF NOT EXISTS idx_long_term_memory_active_key
    ON long_term_memory_items(owner, scope, project_key, memory_key)
    WHERE status = 'active';

CREATE INDEX IF NOT EXISTS idx_long_term_memory_effective
    ON long_term_memory_items(owner, scope, project_key, status, memory_key);

CREATE INDEX IF NOT EXISTS idx_long_term_memory_hash
    ON long_term_memory_items(owner, scope, project_key, content_hash);

CREATE TABLE IF NOT EXISTS long_term_memory_events (
    id              BIGSERIAL PRIMARY KEY,
    owner           VARCHAR(64) NOT NULL DEFAULT '',
    memory_id       TEXT,
    event_type      VARCHAR(24) NOT NULL,
    actor           VARCHAR(16) NOT NULL,
    source_session  TEXT NOT NULL DEFAULT '',
    source_message  TEXT NOT NULL DEFAULT '',
    reason          TEXT NOT NULL DEFAULT '',
    payload         JSONB NOT NULL DEFAULT '{}'::jsonb,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    CHECK (actor IN ('user', 'system', 'admin'))
);

CREATE INDEX IF NOT EXISTS idx_long_term_memory_events_item
    ON long_term_memory_events(owner, memory_id, id);
```

实施要求：

1. 新表和新字段必须带 `owner`，查询必须带 owner 条件。
2. `long_term_memory_events` 只追加，不更新、不物理删除。
3. `items` 是当前状态投影；完整历史由 events 保留。状态可更新，历史不可抹除。
4. 撤回、替换和事件写入放在同一数据库事务中。
5. 替换时使用 `revision` 做乐观锁，防止并发会话用旧快照覆盖新决定。
6. `payload` 只存前后状态、目标 ID、替换 ID、匹配依据等，不写密钥或整段隐私上下文。
7. `content_hash` 对规范化文本计算；撤回 tombstone 不因 Markdown 归档容量被淘汰。
8. 在 `backend/internal/store/schema.go` 增加对应的幂等 schema 确保逻辑，与现有迁移方式一致。

## 5. 用户纠正的当轮处理流程

### 5.1 接入位置

在顶层会话接收新用户消息、记录多轴决策之后、首次构建本轮 LLM 请求之前接入 `MemoryLifecycleService`：

- `backend/internal/agent/service_react.go`
- `backend/internal/agent/session_react.go`
- 新增 `backend/internal/agent/memory_lifecycle.go`
- `backend/internal/bootstrap/bootstrap.go` 负责装配

暂停后补充指令、审批回答和恢复执行也必须走同一入口。只处理**真实用户消息**，不能把 Agent 文本、工具结果或压缩摘要当撤回指令。

### 5.2 处理步骤

```text
1. 读取当前 user/project 的 active 条目，生成紧凑候选视图。
2. 判断最新消息是否包含长期记忆撤回、替换或范围修正。
3. 命中条目后生成结构化操作，不允许模型输出 SQL 或整段 Markdown。
4. Go 校验 scope、project_key、memory_key、目标 ID、来源消息和当前 revision。
5. 执行 retract / supersede / quarantine / replace。
6. 同事务追加 event，提交后刷新 Store 快照和注入 revision。
7. 本轮及后续请求使用新的有效视图。
8. 返回简短、可核对的处理结果，例如“已停用项目经验 M-123：……”。
```

如果撤回服务失败：

- 不得报告“已忘记/已撤回”；
- 对明确指定 ID 或精确文本的条目，走确定性撤回路径；
- 语义匹配不可用时，将本轮标记 `memory_reconcile_required`，保留当前用户指令为最高优先级，并提示旧记忆尚未完成清理；
- 不得静默继续宣称长期记忆已经更新。

### 5.3 三档裁决，避免误删

#### A. 可直接撤回或替换

满足任一条件：

- 用户明确给出条目 ID；
- 用户引用内容与某条 active 条目精确匹配；
- 用户明确说“以后/本项目不再 X，改为 Y”，且目标具有相同 scope、project_key、memory_key。

执行：

```text
旧条目 → retracted 或 superseded
新条目 → active（仅长期意图；一次性指令只进会话账本）
```

#### B. 先隔离，再确认

仅语义相似、模型无法保证目标完全对应时：

```text
疑似旧条目 → quarantined（立即停止注入）
事件记录匹配依据
向用户展示条目 ID 和原文，允许确认撤回或恢复
```

隔离不等于永久删除，也不会丢失审计历史。这样既避免旧经验继续污染，也避免一次语义误判永久删掉正确偏好。

#### C. 不改长期记忆

以下情况只写会话反馈或会话决策：

- “这次不用”“当前角色先这样”；
- “幅度太小”“颜色再亮点”等产物修改；
- 没有明确对象的“太差了”；
- Agent 自己认为某条经验可能过时。

对于“做得太差”，可以把**来源会话中尚未验证且实际用于该成果的经验**标为 `verification=rejected`，必要时再设为 `status=quarantined`，但必须能证明来源和使用关系；不能按关键词清空所有项目经验。

### 5.4 一个完整例子

旧项目经验：

```text
ID=M-123
scope=project
memory_key=animation.method
content=四足奔跑默认使用单底图 warp
status=active
```

用户说：“这个项目以后不要单图 warp，改成关键姿态逐帧生成。”

结果：

```text
M-123：active → superseded
M-456：animation.method = 四足奔跑使用已批准锚点和关键姿态逐帧生成，active
events：记录用户原文来源、旧 ID、新 ID、原因
```

下一条请求的 MetaAgent 和子 Agent prompt 中均不得再出现 M-123。若用户只说“这次别用 warp”，则不创建 M-456，只更新当前会话的 `animation_method`。

## 6. 注入链路必须统一走“有效视图”

### 6.1 不再直接注入 Markdown 原文

当前入口：

- 用户画像：`NewUserProfileInjector` / `NewSectionInjector`，`backend/internal/agent/react_agent.go:233-280`。
- 项目偏好：MetaAgent persona 链和 `Dispatcher.projectPrefsPrefix`，`backend/internal/domain/subagent/dispatcher.go:1653-1670`。
- 当前装配：`backend/internal/bootstrap/bootstrap.go:903-1000`。

改为统一调用：

```go
EffectiveMemories(ctx, MemoryQuery{
    Owner:      owner,
    ProjectKey: projectKey,
}) ([]MemoryItem, error)
```

渲染规则：

1. 只查询 `status=active`。
2. 同 key 的项目条目覆盖全局条目。
3. candidate、quarantined、superseded、retracted 一律不出现，连“已废止：……”也不注入。
4. 经验只保留与当前项目、当前任务适用域相关的内容，不无限全文注入。
5. 注入可附紧凑 ID 和作用域，例如 `[M-123 project]`，便于用户指出要撤回的对象。
6. 预算超限时按必要性和验证状态裁减，不能最后对整段字符串硬截断。
7. 每次构建请求都读取最新有效视图；撤回提交后更新原子快照，不等待重启。

“与用户当前指令冲突时以用户为准”可以保留为防御性提示，但它不是撤回机制的替代品。**已经确认撤回的内容必须物理缺席于本次 prompt，而不是同时注入新旧两条让模型自己猜。**

### 6.2 子 Agent 和已有会话都不能漏

验收必须同时检查：

- 新会话 MetaAgent；
- 当前已有会话的下一次 LLM 请求；
- 当前会话恢复/暂停后继续；
- 新派发子 Agent；
- 热驻留或复用的子 Agent；
- 项目切换后的缓存；
- 后端重启后的首次请求。

缓存键至少包含 `owner + project_key + effective_revision`。撤回后 revision 必须变化，不能继续命中旧 prompt 前缀中的记忆快照。

## 7. 新记忆写入与防复活

### 7.1 写入分两步，不再自动直写现行区

```text
SessionEvolver / remember_preference
→ candidate
→ 确定性准入
→ 撤回与冲突检查
→ 用户明确要求或满足 enforce 条件后 active
```

具体要求：

1. `shadow`：全部只生成 candidate；撤回服务仍正常运行。
2. `off`：不调用 SessionEvolver；显式用户撤回仍正常运行。
3. `enforce`：只有满足准入条件的候选可自动 active。
4. `remember_preference`：仍只处理用户明确偏好，但要写结构化条目，不能只 `Append` 一行文本。
5. SessionEvolver 失败时不得经备用提取路径绕过同一准入和撤回检查。
6. `mixed/failed` 不自动晋升项目经验；用户后来验收时也不能仅靠 Agent 自报成功，需要真实用户消息或明确验证证据。

### 7.2 防复活检查

候选进入 active 前依次检查：

1. **同 hash 检查**：与已撤回内容规范化后相同，拒绝激活。
2. **同 key 检查**：同作用域同主题已有撤回事件时，必须判断是“明确的新替代”还是“旧结论换措辞”。无法证明是新替代则只保留 candidate。
3. **语义近似检查**：与 tombstone 高度近似只产生 `resurrection_suspect`，不得自动 active。
4. **归档不是权威**：是否可复活只查长期 memory events/items，不查会被裁剪的 Markdown 归档。
5. **显式恢复**：只有用户或管理员针对具体 tombstone 执行 restore 才能恢复，并追加新 event；不得删除原撤回事件。
6. **摘要无权复活**：压缩摘要、工具日志和 evolution_log 中的旧句子不能直接成为 active 记忆。

新替代与旧结论复活要区分。例如“这个项目现在重新允许视频抽帧”是明确的新用户决定，可以新建 active；“根据历史经验，视频抽帧可能更好”则不允许绕过 tombstone。

### 7.3 作用域修正

一次性指令污染全局画像时，不只是删除，还要支持：

```text
全局 active 条目
→ retracted（原因：scope_correction）
→ 可选在当前项目/会话创建正确作用域条目
```

禁止把“这个角色”“这张图”“这个项目”的选择写入全局用户画像。跨项目全局经验必须有明确长期意图，项目经验必须绑定规范化的 `project_key`，不能因会话工作目录字符串略有不同而串项目。

## 8. 旧文件与旧数据迁移

不要直接清空用户画像和项目经验，也不要双写后长期维护两套互相覆盖的权威。

### 8.1 迁移前

1. 备份实际部署目录的 `config/user_profile.md`。
2. 备份各实际工作目录的 `.bma/project_preferences.md`。
3. 记录文件 hash 和迁移时间。
4. 保持 `memory.write_mode=shadow`，先停止新增自动污染。
5. 不读取或输出 `.env`、密钥等无关敏感信息。

### 8.2 导入规则

1. 无时间戳的人工行标记 `origin=human`；自动行标记 `origin=legacy_import`。
2. 能确认来源会话的保留 `source_session`，无法确认的 `source_message` 留空，不能伪造。
3. 已位于“反馈记录/经验归档”的内容只导入审计/tombstone，不进入 active。
4. 已被后续指令明确推翻的现行行直接导入为 `retracted`。
5. 无法确认是否仍有效的自动项目经验先导入为 `quarantined`，经人工勾选后恢复。
6. 稳定且明确的人工约定可为 active；未验证的自动经验不能因为“原来就在现行区”自动获得 `verified`。
7. 为旧条目回填 `memory_key` 时，模型只能给建议；同 key 自动合并前必须人工确认或满足精确规则。
8. 原文件保留为迁移备份和审计，不物理删除历史。

### 8.3 权威切换

迁移完成后：

- PostgreSQL items/events 是自动记忆生命周期权威；
- Markdown 可生成为人类可读投影，但注入不再读取原始全文；
- 现有 `GET/PUT /api/profile` 和项目偏好接口需要兼容：PUT 不应无声绕过 events，应转为明确的人工导入/修订操作；
- 禁止后台 SessionEvolver 与人工 HTTP 编辑同时无版本覆盖同一文件；
- 手工修改磁盘文件后，必须经过显式 reload/import，生成新 revision 和审计事件。

第一版若暂不做 Markdown 投影，可让现有页面直接展示有效条目和历史事件，避免制造“数据库已撤回、页面却仍显示现行”的假状态。

## 9. 管理接口与可观测性

### 9.1 最小管理接口

建议在现有 profile/project preferences API 旁增加：

```text
GET  /api/memory/items?scope=project&status=active
POST /api/memory/items/{id}/retract
POST /api/memory/items/{id}/quarantine
POST /api/memory/items/{id}/restore
GET  /api/memory/items/{id}/events
```

要求：

- 所有写操作记录 owner、操作者、来源和原因；
- restore 必须针对具体条目，不提供“清空全部墓碑”；
- 不提供物理删除历史接口；
- 页面能区分“有效、候选、已隔离、已替换、已撤回”；
- 用户可以看到“为什么这条记忆存在、来自哪个会话、当前是否参与注入”。

### 9.2 日志与指标

每次请求记录紧凑的记忆注入清单：

```text
session_id
owner
project_key
effective_revision
memory_ids
memory_hashes
```

线上常规日志不必输出完整画像内容；排障时可在受控 debug 中检查实际 `llm_input`。至少统计：

- 各状态条目数；
- 每轮撤回/隔离/替换数量；
- `resurrection_suspect` 数量；
- 撤回后仍注入旧 ID 的次数，目标必须为 0；
- 撤回失败和 `memory_reconcile_required` 数量；
- 一次性指令进入全局 active 的数量，目标必须为 0。

## 12. 完成标准与回滚

### 12.1 完成标准

只有同时满足以下条件才算修复完成：

1. 用户明确撤回后，**下一次 LLM 请求**不再包含目标旧记忆。
2. MetaAgent、所有子 Agent、已有会话、新会话和重启后结果一致。
3. `shadow/off` 只影响候选写入，不影响撤回。
4. 一次性任务指令进入全局 active 的数量为 0。
5. 已撤回内容换措辞自动复活的数量为 0；疑似项必须留在 candidate/quarantined。
6. 无关记忆不误删，项目与全局作用域不串。
7. 所有撤回、替换、隔离、恢复都有可追溯 events，历史不物理删除。
8. 撤回服务失败时不假报成功。

### 12.2 回滚

- 新记忆自动激活异常：将 `memory.write_mode` 调回 `shadow`，保留撤回服务。
- 语义匹配误判：关闭自动语义撤回，只保留 ID/精确文本撤回和“疑似先隔离”；不能回退到旧记忆无条件注入。
- 新有效视图异常：可临时只注入人工确认的 active 条目，不直接回滚到原始 Markdown 全文。
- 数据库新增表可保留；回滚代码不得删除 items/events，不得清空 tombstone。
- 任何回滚都必须保持“用户明确撤回优先”，不能为了恢复旧功能重新引入已知污染。

## 13. 最小可行版本建议

如果希望先做一个改动较小但能验证核心价值的版本，按以下范围实施：

1. 完成 019 两张表和 EffectiveMemories。
2. 先支持“明确同 key 替换、精确文本撤回、疑似语义冲突隔离”，暂不做复杂自动语义撤回。
3. 撤回接入用户消息入口，shadow/off 下仍启用。
4. MetaAgent 和 Dispatcher 全部只注入 active 视图。
5. 激活候选前做 hash + key + tombstone 检查。
6. 跑通“旧经验 → 用户推翻 → 当轮消失 → 新会话仍消失 → 重启仍消失 → 近义候选不复活”的完整链路。

这个最小版本已经能解决最主要的污染问题。复杂语义判断、管理界面和自动经验晋升都可以后做，**不要先做一个更聪明的提取提示词，却继续让旧经验没有稳定 ID、没有即时撤回、没有永久墓碑。**
