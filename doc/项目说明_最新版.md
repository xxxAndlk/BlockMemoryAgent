## 0. TL;DR

BlockMemoryAgent 是一套用 **Go + CloudWeGo Eino** 构建的**记忆原生、上下文纯净的多 Agent 协同智能体编排系统**。它通过**四层 Agent 分级编排**（MetaAgent → DomainAgent → SubDomainAgent → Assistant）、**会话块隔离 + 记忆外部化**（短期 Redis / 项目 pgvector / 长期 pgvector + 四级压缩）、**LLM 全权决策的 Skill 装配**、**任务看板 + 邮箱异步协同**、**Watchdog 上下文看门狗**，追求让 Agent 连续工作一周仍保持"清晰记忆"与"专注力"。

一句话定位：
> 四层 Agent 编排 + 会话块记忆隔离 + LLM 驱动 Skill 装配 + 看板邮箱协同 + 上下文看门狗，以最小 token 维持长期工作的记忆与专注。

---

## 1. 它要解决什么问题

LLM Agent 框架的两个根本痛点：

1. **长上下文遗忘**：对话历史、工具输出、系统提示词堆积超过模型有效注意力范围后，模型对中间信息的提取准确率急剧下降，出现"迷失在中间"。
2. **Skill 选择困难**：技能库膨胀后，Agent 在海量功能里难以精准定位所需技能，重复/无关技能白白占用上下文与推理资源。

项目硬指标：**主 Agent 连续工作一周后，上下文不溢出、不遗忘关键信息**；多话题并行时上下文完全隔离；Agent 能由 LLM 自主选择 Skill 而非僵硬路由。

## 2. 核心设计理念（三条）

1. **一切选择由 LLM 驱动**——Skill 选择、话题总结、记忆压缩、Agent 路由全部交给 LLM 推理，禁止硬编码，只提供结构化上下文作决策依据。
2. **上下文即稀缺资源**——把 LLM 上下文窗口当昂贵的"工作内存"，所有记忆组件围绕"最小 token 提供最大信息密度"设计。
3. **多 Agent 分级编排**——主 Agent 唯一面向用户，按需动态生成领域 Agent，领域 Agent 再按需生成子领域/功能 Agent；Agent 之间绝不直接共享上下文。

灵感来源：MemPalace（空间记忆 + 主动回忆 → 会话块机制）、gbrain/llm_wiki（RAG 知识注入）、firecrawl（Web 搜索工具）、字节 Eino（编排基座）。

## 3. 系统架构

### 3.1 四层 Agent

```
Layer 1   MetaAgent           唯一调度中枢，每会话一个
   │ 动态创建
Layer 2   DomainAgent         每个业务领域一个，会话级，承载领域上下文+Skill子集
   │ 按需创建
Layer 2.5 SubDomainAgent      领域过复杂时再细分（如商城页面→头部/列表/底部）
   │ 按需创建
Layer 3   Assistant           单一职责原子执行者
            ├─ 固定助手：roles.yaml 预定义（代码/UI/提示词审查/测试/文档 5 个）
            └─ 动态助手：LLM 实时生成角色定义，任务级即生即灭
```

**MetaAgent（`internal/graph/meta_agent.go`）**
- 分析用户目标识别业务领域（LLM 路由，0 温度）
- 创建/切换/销毁 DomainAgent 会话块
- 每轮跑 Watchdog（上下文监控）+ processMailbox（广播邮件转交）
- 维护任务看板、跨领域协调、定期会话总结
- 简单寒暄类问题直接 LLM 一问一答短路，不走 Graph

**DomainAgent（`internal/graph/domain_agent.go`）**
- 拥有独立上下文、私有记忆快照、专属 Skill 库
- `ensureSkillSet` 首次执行时按领域装配 Skill 子集
- `analyzeTasks` 拆解子任务，`shouldSplitToSubDomains` 判断是否再细分
- 并行调度 Assistant（`dispatchAssistantsParallel`），汇总结果

**SubDomainAgent（`internal/graph/subdomain_agent.go`）**——复用 DomainAgent 的助手调度逻辑，完成后弹调用栈回父。

**Assistant（`internal/graph/assistant.go`）**——执行单一任务，通过 CallStack 被调用，结果写回所属会话块。

### 3.2 Graph 执行引擎（`internal/graph/three_layer_graph.go`）

不是声明式 DAG，而是**状态机循环**（最多 200 步）：
- 每个节点 `Invoke` 返回 `*ThreeLayerState`，带 `NextAction ∈ {Continue, Switch, Escalate, Finish}`
- `determineNext` 按当前节点类型 + NextAction 决定下一个节点
- `CallStack` 实现嵌套调用（DomainAgent→SubDomainAgent→Assistant）
- 终止节点：`EscalationHandlerNode`（升级仲裁）、`sinkerNode`（强制 Finish）

### 3.3 Runtime 聚合（`internal/runtime/runtime.go`）

v3 把 5 个运行时组件聚成单一 `Runtime` 对象，`main.go` 一次构造、注入图、透传给动态节点：

```
Runtime
 ├─ Boards    *board.Manager      任务看板
 ├─ Mailbox   *mailbox.Mailbox    异步邮箱
 ├─ Skills    *skill.Registry     Skill 池 + 装配表
 ├─ Soul      *soul.Loader        人格 + 温度
 └─ Watchdog  *watchdog.Watchdog  上下文看门狗
```

## 4. 记忆体系（项目灵魂）

### 4.1 三层存储

| 层 | 引擎 | 内容 | 生命周期 |
|---|---|---|---|
| 短期记忆 | Agent 上下文 + Redis | 当前任务最近 N 轮、实时状态、待处理事件 | 任务结束/压缩即释放 |
| 项目记忆 | PostgreSQL + pgvector | 项目文档、Skill 定义、会话块摘要、模块输出 | 与项目同生命周期，跨会话持久 |
| 长期记忆 | PostgreSQL 向量库 + 元数据索引 | 跨项目用户偏好、通用知识、成功案例模板 | 永久，带访问频率衰减 |

### 4.2 会话块（Conversation Chunks）机制

借鉴 MemPalace 空间记忆，把对话历史按**话题边界**切成独立会话块，每块含话题摘要、关键实体与决策、原始对话向量嵌入、时间戳与活跃度评分。注入规则：新问题到来时计算与所有块的语义相关性（向量相似 + 实体重叠 + 时间衰减），仅取 Top-1~2 块（+必要前置依赖）摘要注入，完全无关块不加载。

### 4.3 智能压缩与遗忘

- 每 X 轮（默认 10）触发后台压缩：轻量模型重写摘要，保留关键事实+未解决问题
- 私有记忆快照在 Agent 被切出时压缩为"最近 K 步完整细节 + 远期抽象摘要"
- 长期记忆 LRU + 重要性评分双淘汰
- **四级压缩**（`pkg/types/types.go`）：Raw（原始）→ Standard（摘要+Facts）→ Compact（一句话）→ Marker（仅存在性标记）

### 4.4 连续一周不遗忘的实现方案

四条措施叠加：
1. **上下文总量控制**：主 Agent 上下文只含"全局看板摘要(200 token)+当前话题块摘要(300 token)+最近3轮交互"，硬控 ≤1000 token
2. **记忆外部化**：历史/知识全存 Postgres 向量库+Redis，按需检索；主 Agent 上下文本质是"指针集合"而非数据仓库
3. **领域上下文隔离**：DomainAgent 完成任务后销毁/压缩成项目记忆一条摘要，空间立即回收
4. **Watchdog 机制**：实时监控上下文长度，超安全阈值强制压缩/切换

记忆管线四阶段（`internal/memory/`）：
`write.go`（重要性评分+话题绑定）→ `compress.go`（4 级压缩）→ `search.go`（多信号相关性：pgvector语义+实体重叠+因果链+时间衰减）→ `assembler.go`（4 段上下文组装 + TokenBudget）→ `snapshot.go`（Redis 热加载 + Postgres 持久化）

## 5. Skill 管理体系

### 5.1 装配流水线（核心创新）

```
config/skills.yaml ─► skill.Pool
                        │ FilterByDomain(domain)   规则预筛
                        ▼
                   候选 Skill 子集（≤N 直接返回，否则 LLM 二选）
                        │ Pool.AssembleSet
                        ▼
                  types.SkillSet (≤8)
                        │ Registry.Bind(agentInst)
                        ▼
      DomainAgent.executeAssistantTask 取 PromptList()
                        │ skill_brief 注入 system prompt
                        ▼
        LLM ──tool_call──► ToolExecutor.Execute(toolRef)
```

铁律：严禁把整个 SkillPool 暴露给子 Agent，只下发该领域筛选后的 ≤8 个 Skill 名称+一句话描述。

### 5.2 内置 Skill 池（`skill.BuiltinPool`）

ReadFile / WriteFile / ListDir / RunCommand / SearchInFiles / HTTPGet / HTTPPost——后两个专为 AIOps 测试场景加的。

### 5.3 LLM 驱动选择

DomainAgent 执行任务时：上下文只看到专属 Skill 列表 → LLM 推理出最合适的 → 输出调用指令 → 不存在则向主 Agent 请求"扩展技能"（仍只补必要的一两个）。

## 6. 提示词与人格体系

### 6.1 三层提示词
- 基础层（固定）：角色定义、安全准则、输出格式
- 任务层（动态）：当前任务目标、上下文摘要、可用工具列表
- 示例层（按需）：Few-Shot + Chain-of-Thought 引导复杂推理

### 6.2 人格 soul.md（`config/soul.md`）

`soul.Loader` 启动加载、支持热重载，`Inject()` 把人格作为前置段落拼到 system prompt 之前。当前人格是"专业耐心细致的多 Agent 编排助手"，强调简洁分点、先复述目标、上下文稀缺原则。

### 6.3 Temperature 动态调节

6 种 `TaskKind` 映射推荐温度：routing=0、summarize=0、code=0.15、analysis=0.3、creative=0.8、generic=用角色配置温度。`InferKind(text)` 启发式从任务文本推断类别。`model.GenerateWithTemperature` 对实现 `TemperatureAware` 接口的 EinoClient 做 per-call 覆盖。

## 7. 多 Agent 协同：看板 + 邮箱

设计哲学：**Agent 之间绝不直接共享上下文**，只用异步消息解耦，保证并发执行不交叉污染。

### 7.1 任务看板（`internal/board/`）
每个活跃话题一个结构化看板：话题 ID、目标、状态（NEW/IN_PROGRESS/DONE/FAILED）、子任务列表、全局约束。MetaAgent 在 `handleInitial` 创建，把 LLM 推断的领域名作顶层子任务；`MarkDone/MarkFailed/MarkBlocked` 原子重算整体状态；`Brief(maxTasks)` 输出 ≤200 token 紧凑视图可注入子 Agent 上下文。

### 7.2 邮箱通知（`internal/mailbox/`）
- 直发：`Send` → `Drain(target)` 按 Priority 降序、CreatedAt 升序
- 广播：`To=="*"` 进广播桶 → MetaAgent `processMailbox` 每轮拉取，按目标 domain 转给具体 DomainAgent，escalate 类型自动转 `EventEscalation` 投回 SessionBlock
- 5 种消息类型：milestone / request / info / escalate / dependency

### 7.3 并发模型
Go goroutine：MetaAgent 并发激活多个 DomainAgent，各跑各的 goroutine，共享记忆存储连接池，看板原子操作保一致。`dispatchAssistantsParallel` 用 `sync.WaitGroup` 并行调度多个 Assistant。

## 8. 工具执行器与防幻觉

### 8.1 工具集（`internal/graph/tool_executor.go`）
7 个本地沙箱工具。跨平台 RunCommand（Windows `cmd /c`，Unix `sh -c`），mkdir 特判走 `os.MkdirAll`；输出统一截断 10KB；支持 snake_case 工具名归一化。

### 8.2 工具调用循环（`internal/graph/llm_tools.go`，8 轮上限）
工程亮点防幻觉机制：
- **完成门控**：任务要求写文件时，必须见到成功的 WriteFile 才算完成
- **幻觉检测**：LLM 声称"已写文件"但无 WriteFile 记录 → 强制再逼一次落盘
- **连续失败干预**：同一工具连续失败 ≥3 次强制放弃；中途换工具则重置计数
- **失败信息回流**：失败时把 stdout/stderr 带给 LLM，避免只看到 exit code 反复试错变种

## 10. 配置体系（三层，优先级：系统环境变量 > .env > config.yaml 默认值）

- **`.env`**：OPENAI_API_KEY / ANTHROPIC_API_KEY / POSTGRES_DSN / REDIS_ADDR / HTTP_ADDR(:10010)
- **`config/config.yaml`**：基础设施（DSN、pgvector 维度、Redis、HTTP、memory 间隔），`${VAR:default}` 语法
- **`config/roles.yaml`**：MetaAgent（轻量模型 max_blocks=10 summary_interval=5）+ DomainAgent（共用模型）+ 5 个 fixed_roles（每个独立模型配置+system_prompt+skills+keywords+tools+can_be_called）+ dynamic_templates
- **`config/soul.md`**：人格
- **`config/skills.yaml`**：Skill 池

**降级策略**：Store 和 Skill 池不可用时优雅降级（告警日志、nil 化），服务器无 Postgres/Redis/API Key 也能启动；无 Key 走 `mockClient`，领域分析/任务拆解/Skill 装配全走规则回退。

## 11. 入口与启动流程（`backend/main.go`）

```
config.Load → NewPostgresStore/NewRedisStore（失败降级 nil）
  → pkgconfig.LoadRoleConfig → model.NewModelFactory(...).WarmUp
  → graph.NewRoleRegistry + NewRoleFactory
  → skill.LoadFromYAML（失败回退 BuiltinPool）
  → runtime.New(soulPath, skillPool)            ← 五合一 Runtime
  → graph.NewThreeLayerGraphBuilder 注入 ModelFactory + Runtime
  → server.NewSessionManager(graph, registry)   ← 注入 tool/progress 回调
  → sessionMgr.RestoreSessions（从 session_history 恢复）
  → 注册 HTTP 路由（见下）
  → httpServer.ListenAndServe(:10010)
```

启动命令：
```bash
GOTOOLCHAIN=local go run ./backend \
  -config config/config.yaml -roles config/roles.yaml \
  -env .env -soul config/soul.md -skills config/skills.yaml
# → http://localhost:10010
```

### 已知偏差与限制
1. **会话块向量检索未启用**：v3 §4.2 的语义 Top-K 注入需 Embedding API，当前仍按重要性排序粗选；`/api/memory/search` 暂用关键词评分兜底。
2. **温度调节范围有限**：仅 MetaAgent 路由用 0 温度，DomainAgent/Assistant 代码/创意路径未按 InferKind 自动调温。
3. **Mailbox 内存实现**：进程重启丢失，未落 Redis Stream。
4. **Watchdog 估算精度**：4 字符≈1 token 粗估，中文偏低 30%，靠阈值余量硬扛（默认 soft=12000/hard=20000）。
5. **Web 管理页面部分 mock**：知识库搜索、会话历史、人格配置、Skill 库管理后端接口待补。
